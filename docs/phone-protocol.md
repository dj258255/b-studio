# 휴대폰 암호 통로 프로토콜 (v1)

휴대폰 앱(#1484)은 이 문서만 보고 만들 수 있어야 합니다. 서버 쪽 구현은 `apps/studio/lib/server/phone/`(`crypto.ts` 부품, `gateway.ts` 판정, `listener.ts` 귀)이고, 결정과 근거는 [ADR-249](decisions.md)입니다. 문서와 서버가 어긋나면 서버 시험(`phone.test.ts`의 고정 벡터)이 먼저 깨집니다.

## 한눈에

- 휴대폰은 **얇은 화면**입니다. 데스크톱의 b-studio가 세션 터미널을 돌리고, 휴대폰은 그 화면을 받아 보여 주고 키를 보냅니다.
- 전송은 평문 HTTP(같은 와이파이)입니다. **모든 내용은 앱 계층에서 암호화**합니다: X25519 + XSalsa20-Poly1305(NaCl `box`/`secretbox`, 앱은 `tweetnacl`을 씁니다). 인증서는 필요 없습니다 — 서버 공개 키를 QR로 받기 때문입니다.
- 순서: ① desk가 QR을 보임 → ② 휴대폰이 QR을 읽고 **짝 맺기**(기기 키 등록, 기기 토큰 받음) → ③ 쓸 때마다 **세션 열기**(임시 키 교환) → ④ 세션 열쇠로 **요청(rpc)**을 보냄.
- 권한: 기기는 **짝을 맺을 때 desk를 쓰던 사람**의 권한으로만 움직입니다(관리자 권한이 아닙니다). 서버 방식에서 남의 세션 터미널에는 쓰지 못합니다.
- 밖(LTE)에서는 Tailscale 같은 사설망을 사람이 설치해 쓰고, 프로토콜은 같습니다. 서버는 사설 네트워크 주소(10.x, 172.16~31.x, 192.168.x, 100.64~127.x, 169.254.x)에만 귀를 엽니다.

## 용어와 기본 규칙

| 말 | 뜻 |
|---|---|
| 서버 키(`SK`) | 서버의 장기 X25519 키 쌍. 공개 키 `SPK`는 QR에 실립니다. 비밀 키는 서버의 설정 폴더(`~/.config/b-studio/phone/server-key.json`, 0600)에만 있습니다 |
| 기기 키(`DK`) | 휴대폰이 만들어 폰에만 두는 장기 X25519 키 쌍. 공개 키 `DPK`를 짝 맺을 때 서버에 등록합니다 |
| 기기 id / 기기 토큰 | 짝 맺기의 답으로 받습니다. id는 32자 16진수, 토큰은 64자 16진수 문자열이고 서버에는 SHA-256만 남습니다 |
| 임시 키 | 세션을 열 때마다 양쪽이 새로 만드는 X25519 키 쌍. 세션 열쇠는 여기서 나옵니다(앞으로의 비밀 — 장기 키가 나중에 새도 지난 세션은 못 엽니다) |
| 세션 열쇠(`K`) | `nacl.box.before(상대 임시 공개 키, 내 임시 비밀 키)`. 32바이트 |

- **base64**: 표준 base64, 패딩 `=` 포함(RFC 4648 §4). 서버는 모양이 정확히 맞지 않는 값(공백·줄바꿈·URL-safe 글자·패딩 누락·남는 비트)을 열지 않고 `400`으로 거절합니다. 앱도 같은 방식으로 보내야 합니다.
- **JSON**: UTF-8, 최상위는 객체. 모르는 필드는 서버가 무시합니다.
- **시각**: 서버 시각은 참고용입니다. 어떤 판정도 폰의 시계에 기대지 않습니다(재전송은 번호와 도전값으로 막습니다).
- 서버 오류 응답은 `{"error": "<코드>"}` 한 필드입니다(아래 오류 표).

## QR 내용

QR의 글(UTF-8)은 이 JSON 한 줄입니다.

```json
{"t":"b-studio-pair","v":1,"k":"<SPK base64 44자>","c":"<짝 코드 10자>","a":["192.168.0.5:38917","10.0.0.7:38917"],"n":"<컴퓨터 이름>"}
```

| 필드 | 뜻 |
|---|---|
| `t` | 항상 `"b-studio-pair"`. 다르면 이 앱의 QR이 아닙니다 |
| `v` | 프로토콜 버전. 앱이 모르는 버전이면 "앱을 업데이트하세요"로 멈춥니다 |
| `k` | 서버 공개 키(base64, 32바이트). **이 키만 믿습니다** — 앞으로의 모든 통신은 이 키로 서버를 확인합니다 |
| `c` | 짝 코드. 알파벳 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` 10자. **2분 안에, 한 번만** 쓸 수 있고 틀리면 5번째에 코드가 죽습니다 |
| `a` | 서버가 귀를 연 `주소:포트` 목록(같은 포트). 앱은 차례로 시도해 `GET /phone/v1/hello`에 먼저 답하는 주소를 씁니다. 짝 맺은 뒤에도 주소 목록은 앱이 저장해 두고, 안 닿으면 같은 와이파이에서 다시 짝 맺기 전에 사용자가 주소를 고칠 수 있게 합니다 |
| `n` | 컴퓨터 이름(보이기용, 40자까지) |

앱은 QR을 읽은 글을 위 형식으로 해석합니다. `t`·`v`가 맞지 않거나 `k`가 32바이트 base64가 아니거나 `a`가 비어 있으면 짝 맺기를 시작하지 않습니다. (QR을 못 읽는 폰을 위한 글 붙여 넣기 입력은 앱이 선택으로 둘 수 있습니다. desk는 지금 QR만 보입니다.)

## 경로

모두 `http://<주소:포트>/phone/v1/...`입니다. 서버는 이 네 경로 말고는 `404`입니다. 쿼리 문자열도 받지 않습니다. 쿠키·CORS·인증 헤더는 쓰지 않습니다.

| 경로 | 메서드 | 쓰임 | 본문 상한 |
|---|---|---|---|
| `/phone/v1/hello` | GET | 일회용 도전값 받기 | 없음 |
| `/phone/v1/pair` | POST | 짝 맺기(기기 등록) | 8 KiB |
| `/phone/v1/open` | POST | 세션 열기 | 8 KiB |
| `/phone/v1/rpc` | POST | 암호화된 요청 하나 | 512 KiB |

본문은 `application/json` 글자입니다(헤더는 서버가 보지 않습니다). 상한은 읽기 전에 `Content-Length`로, 선언이 없거나 거짓이면 읽는 동안 셉니다. 넘으면 `413`입니다.

**켜짐 스위치**: 데스크톱에서 휴대폰 연결을 끄면 서버는 귀 자체를 닫습니다(연결이 거절됩니다). 켜진 채여도 설정이 꺼져 있으면 모든 경로가 `404 not_found`입니다.

## 1. 짝 맺기 (`POST /phone/v1/pair`)

폰은 처음 한 번 기기 키 쌍 `DK`를 만들어 안전한 저장소(Keychain/Keystore)에 둡니다.

요청:

```json
{"v":1,"pk":"<DPK base64>","n":"<nonce 24바이트 base64>","c":"<box base64>"}
```

- `n`: 새 무작위 24바이트(재사용 금지).
- `c`: `nacl.box(utf8(JSON), n, SPK, DSK)`. 평문 JSON은 `{"code":"<QR의 c>","name":"<폰 이름>"}`입니다. 이름은 40자 안으로 서버가 다듬습니다(제어·방향 문자 제거).

서버는 `SSK`와 `DPK`로 상자를 열고(열리지 않으면 거절), 코드를 확인합니다. 코드는 **맞으면 그 자리에서 지워집니다(한 번만)**. 없음·만료·틀림은 모두 같은 `403 rejected`이고, 같은 주소에서 실패가 60초 안에 10번 쌓이면 `429`입니다.

성공 응답(`200`):

```json
{"v":1,"n":"<nonce base64>","c":"<box base64>"}
```

`c`를 `nacl.box.open(c, n, SPK, DSK)`로 열면 `{"deviceId":"<32 hex>","token":"<64 hex>","user":"<사용자>"}`입니다. **`deviceId`와 `token`을 `DK`와 함께 안전한 저장소에 둡니다.** 토큰은 다시 볼 수 없습니다. 같은 `DPK`로 두 번 짝 맺으면 `409 already_paired`, 기기가 10대면 `409 device_limit`입니다.

## 2. 세션 열기 (`GET /hello` → `POST /open`)

쓸 때마다(앱을 켜거나 `401 session`을 받으면) 새 세션을 엽니다.

1. `GET /phone/v1/hello` → `{"v":1,"challenge":"<32 hex>","serverTime":<ms>}`. 도전값은 **한 번만, 30초 안에** 씁니다.
2. 폰은 새 임시 키 쌍 `EK`를 만들고 `POST /phone/v1/open`:

```json
{"v":1,"d":"<deviceId>","n":"<nonce base64>","c":"<box base64>"}
```

`c = nacl.box(utf8(JSON), n, SPK, DSK)`(장기 기기 키로 서명), 평문 JSON은 `{"token":"<기기 토큰>","challenge":"<도전값>","epk":"<EK 공개 키 base64>"}`입니다.

서버는 기기가 목록에 있고 사용자가 아직 유효한지, 상자가 열리는지, 도전값이 살아 있는지(쓰면 지움), 토큰의 SHA-256이 같은지를 봅니다. 하나라도 틀리면 같은 `403 rejected`입니다.

성공 응답(`200`): `{"v":1,"n":"...","c":"..."}`. `c`를 `nacl.box.open(c, n, SPK, DSK)`로 열면 `{"sid":"<32 hex>","epk":"<서버 임시 공개 키>","expiresInSec":43200,"idleSec":1800}`입니다. 이 상자가 열렸다는 것이 서버가 진짜 서버라는 증거입니다. 이제 `K = nacl.box.before(epk, EK 비밀 키)`이고, `EK`의 비밀 키는 바로 지웁니다.

세션은 만든 뒤 12시간, 마지막 사용 뒤 30분이면 끝납니다(서버가 `401 session`으로 알립니다). 한 기기에 세션은 4개까지이고, 넘치면 가장 오래 안 쓴 것부터 닫힙니다. 서버를 다시 띄우면 세션이 모두 사라지니 다시 엽니다.

## 3. 요청 (`POST /phone/v1/rpc`)

```json
{"s":"<sid>","q":<번호>,"c":"<secretbox base64>"}
```

- `q`: 이 세션에서 쓰는 **요청 번호**. `1`부터 시작해 **요청마다 1 이상 커져야** 합니다(서버는 지금까지 받은 가장 큰 번호보다 큰 번호만 받습니다). 안전한 정수여야 합니다(`2^53` 미만).
- `c = nacl.secretbox(utf8(평문 JSON), nonce, K)`. **nonce 24바이트**는 `[종류 1][0 7][번호 8바이트 빅엔디언][0 8]`입니다. 요청의 종류는 `1`, 번호는 `q`입니다.
- **번호는 보내는 차례대로 닿아야 합니다.** 서버는 번호가 앞선 요청을 먼저 받으면 뒤처진 요청을 `409 replay`로 거절합니다. 긴 기다림(`stream.read`, 최대 25초)을 하는 연결과 입력을 보내는 연결이 따로 있어도 번호는 **하나의 카운터**에서 받고, 번호를 받은 바로 그 순간 요청을 내보냅니다(그 사이에 `await`를 두지 않습니다).
- **같은 번호로 다시 보내지 않습니다.** 처음 보낸 요청이 `409`를 받았다면 서버가 그 요청을 **실행하지 않은 것**입니다(앞선 번호가 먼저 닿았을 뿐). 새 번호로 다시 보내면 됩니다. 요청을 보냈는데 응답을 못 받았다면(연결 끊김) 서버가 실행했는지 알 수 없습니다. 읽기는 새 번호로 다시 보내고, **터미널 입력은 화면을 읽어 반영됐는지 보고 나서** 다시 보냅니다.

응답(`200`): `{"q":<같은 번호>,"c":"<secretbox base64>"}`. `c`를 같은 `K`와 nonce(**종류 `2`**, 같은 번호)로 열면 평문 JSON입니다. 서버는 상자가 열려야만 번호를 올립니다(위조 메시지가 번호를 올려 진짜 요청을 막지 못합니다).

### 평문 요청과 응답

모든 평문에는 `op`가 있습니다. 서버 오류는 `{"ok":false,"error":"<코드>"}`입니다.

| `op` | 요청 필드 | 응답 |
|---|---|---|
| `ping` | | `{"ok":true,"now":<ms>}` |
| `http` | `method`(`GET`/`POST`), `path`(쿼리 포함), `body`(JSON, 256 KiB까지) | `{"ok":true,"status":<안쪽 HTTP 상태>,"json":<본문>}` 또는 JSON이 아니면 `"text"` |
| `stream.open` | `path` | `{"ok":true,"stream":"<id>"}` |
| `stream.read` | `stream`, `after`(받은 다음 번호, 처음 `0`), `waitMs`(0~25000, 새 소식이 없으면 이 시간까지 기다림) | `{"ok":true,"events":[{"i":<번호>,"data":"<글>"}],"next":<다음 번호>,"gap":true?,"closed":true?}` |
| `stream.close` | `stream` | `{"ok":true}` |

`http`의 안쪽 상태는 b-studio의 기존 라우트가 낸 상태입니다(`403`: 남의 세션, `404`: 없는 세션 등). 응답이 4 MiB를 넘으면 `{"ok":false,"error":"too_large"}`입니다.

### 부를 수 있는 라우트(허용 목록)

정확히 이것만 됩니다. 쿼리는 `GET /api/sessions`만 받고 글자는 `A-Za-z0-9_=&.-`뿐입니다(`%`·`..`·`/` 없음). 세션 id는 `[A-Za-z0-9_-]{1,64}`입니다. 그 밖은 `{"ok":false,"error":"route_not_allowed"}`입니다.

| 쓰임 | `op` | 메서드·경로 |
|---|---|---|
| 세션 목록 | `http` | `GET /api/sessions` (`?projectId=&limit=`) |
| 세션 상태 | `http` | `GET /api/sessions/<id>/status` |
| 지금 변경(diff) | `http` | `GET /api/sessions/<id>/changes` |
| 터미널 입력·크기 | `http` | `POST /api/sessions/<id>/terminal` — 본문 `{"action":"input","data":"..."}`, `{"action":"resize","cols":80,"rows":24}`, `{"action":"open",...}` |
| 터미널 화면 받기 | `stream.open` | `GET /api/sessions/<id>/terminal` |
| 에이전트 목록(대기 알림) | `http` | `GET /api/agents` |
| 에이전트 변화 흐름(대기 알림 이벤트) | `stream.open` | `GET /api/agents/stream` |

권한은 기존 라우트가 그대로 판정합니다. 서버 방식(인증을 켠 서버)에서 터미널 열기·입력·크기는 **세션을 만든 사람의 기기만** 됩니다. 관리자의 기기도 남의 세션에는 쓸 수 없습니다(`http` 응답의 `status: 403`).

### 흐름 읽기

서버는 안쪽 SSE 흐름을 받아 두고(기기마다 4개, 전체 16개까지), 앱이 긴 기다림으로 가져갑니다. 앱이 WebSocket·스트리밍 `fetch` 없이도 되도록 일부러 고른 방식입니다.

1. `stream.open`으로 `stream` id를 받습니다.
2. `stream.read {stream, after:0, waitMs:20000}`을 되풀이합니다. 응답의 `events`를 `i` 순서대로 처리하고, 다음에는 `after = next`를 보냅니다(받았다고 알리는 뜻이라 서버가 그 앞은 버립니다).
3. `events[].data`는 안쪽 SSE의 `data:` 줄 글입니다. 터미널 흐름의 글은 JSON이고 출력은 base64입니다(`TerminalMessage`, `apps/studio/lib/server/session-terminal.ts`). 처음 연결하면 최근 출력과 지금 상태를 한꺼번에 받습니다.
4. `gap: true`는 서버가 받아 두는 상한(2000개·2 MiB)을 넘겨 앞부분을 버렸다는 뜻입니다. 터미널이면 `stream.close` 뒤 다시 `stream.open`해 처음부터 받습니다.
5. `closed: true`면 흐름이 끝났습니다(세션 멈춤, 연결 끊김, 기기 끊김). 서버는 그 흐름을 지웁니다.
6. 60초 동안 `stream.read`를 안 하면 서버가 그 흐름을 닫습니다.

## 오류

HTTP 상태와 `error` 코드입니다. 이 표에 없는 값은 앱이 "알 수 없는 오류"로 다룹니다.

| HTTP | `error` | 뜻 | 앱이 할 일 |
|---|---|---|---|
| 400 | `bad_request` | JSON·base64·필드 모양이 틀림 | 앱 버그. 재시도하지 않음 |
| 400 | `unsupported_version` | `v`를 서버가 모름 | 앱 업데이트 안내 |
| 401 | `session` | 세션이 없거나 만료·끊김·서버 재시작·기기 끊김 | `open`부터 다시. `open`도 `403`이면 짝이 풀린 것 |
| 403 | `rejected` | 짝 코드 틀림·만료·소진, 상자가 안 열림, 토큰 틀림, 기기 없음 | 같은 이유로 알려 주지 않음. 짝 맺기면 QR을 다시 받게 함 |
| 404 | `not_found` | 없는 경로, 또는 휴대폰 연결이 꺼짐 | "데스크톱에서 휴대폰 연결을 켜세요" |
| 405 | `method_not_allowed` | | 앱 버그 |
| 409 | `replay` | 번호가 지금까지 받은 가장 큰 번호 이하 | 처음 보낸 요청이면 실행되지 않았으니 새 번호로 다시 |
| 409 | `already_paired` / `device_limit` | 같은 기기 키가 이미 있음 / 기기 10대 | 데스크톱에서 기기를 끊고 다시 |
| 413 | `too_large` | 본문 상한 초과 | 입력을 쪼갬(입력 한 번은 256 KiB까지) |
| 429 | `rate_limited` | 실패가 쌓여 잠시 막힘, 또는 도전값이 너무 많음 | 1분 뒤 |
| 500 | `internal` | 서버 오류 | 잠시 뒤 |

`409 replay`는 위 "요청" 절의 규칙대로 다룹니다.

상자가 열리지 않는 `rpc`(위조·변조·다른 기기의 열쇠)는 `403 rejected`이고 번호를 올리지 않습니다.

## 끊기와 회수

- 데스크톱의 휴대폰 탭에서 기기를 끊으면 서버가 그 자리에서 목록에서 지우고 그 기기의 세션을 닫고 열린 흐름을 끊습니다. 그 뒤 모든 요청은 `401 session`, 새 세션은 `403 rejected`입니다. 앱은 `403`을 받으면 저장한 키·토큰을 지우고 처음 화면으로 돌아갑니다.
- 인증을 켠 서버(token)에서 운영자가 그 사용자를 토큰 목록에서 빼거나 무효화하면 그 사용자의 기기도 같은 방식으로 거절됩니다.
- 데스크톱에서 연결을 끄면 귀가 닫히고 모든 세션이 사라집니다.

## 앱이 지킬 것

- 기기 비밀 키와 토큰은 OS 보안 저장소에만 둡니다. 로그에 찍지 않습니다.
- 서버 공개 키는 **QR로 받은 것만** 믿습니다. `open` 응답의 상자가 그 키로 열리지 않으면 연결을 닫습니다.
- nonce를 만드는 무작위는 `nacl.randomBytes`(OS 난수)를 씁니다. `pair`·`open`의 nonce는 요청마다 새로 만듭니다.
- 요청 번호는 세션마다 `1`부터이고 **새 세션이면 다시 1**입니다. 번호를 영구 저장할 필요는 없습니다.
- 한계(프로토콜이 막지 못하는 것): 같은 와이파이의 공격자는 연결을 막거나 보낸 요청을 **붙잡았다가 나중에** 전달할 수 있습니다(번호가 아직 앞서 있으면 받아들여집니다). 내용을 읽거나 바꾸거나 만들 수는 없습니다. 터미널 입력처럼 때가 중요한 요청은 이 한계를 알고 쓰고, 사용자에게는 같은 와이파이를 믿을 만한 곳으로 한정하라고 안내합니다.

## 버전

- 이 문서는 `v: 1`입니다. 모든 짝 맺기·세션 열기 본문에 `v`가 있고, 서버는 모르는 버전을 `400 unsupported_version`으로 거절합니다.
- 호환을 깨는 변경(상자·nonce 틀·경로)은 `v`를 올립니다. 새 `op`나 새 허용 라우트는 `v`를 올리지 않고 더합니다(모르는 `op`는 `unknown_op`).
- 서버가 새 허용 라우트를 더하면 이 문서의 표와 `gateway.ts`의 `HTTP_ROUTES`·`STREAM_ROUTES`를 함께 고칩니다.
