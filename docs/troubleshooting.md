## 1. Ctrl+C 한 번에 신호가 여러 번 들어와 정리가 중간에 끊길 수 있음

**구분:** 첫 실행 뒤 프로세스 구조를 확인하다가 발견 → 수정 후 재현 테스트로 검증

### 현상
`pnpm studio up`은 프로세스가 `pnpm → tsx → node` 순서로 이어져 있습니다.

```
50124  node .../tsx/dist/cli.mjs apps/cli/src/main.ts up examples/orders
50130  node --require .../tsx/dist/preflight.cjs --import ... apps/cli/src/main.ts ...
```

터미널에서 Ctrl+C를 누르면 SIGINT가 프로세스 그룹 전체에 전달되고, tsx도 받은 신호를 자식 node에 다시 전달합니다. 그래서 **실제 CLI 프로세스는 SIGINT를 두 번 이상 받을 수 있습니다.**

처음 코드는 신호 처리기를 `process.once`로 등록했습니다.

```ts
process.once('SIGINT', () => void cleanup());
```

`once`는 첫 신호를 처리한 뒤 처리기를 지웁니다. 그 상태에서 두 번째 SIGINT가 오면 Node의 기본 동작(즉시 종료)이 실행돼, **`docker compose down`이 끝나기 전에 프로세스가 죽고 컨테이너와 볼륨이 남을 수 있습니다.**

### 해결
정리 함수 자체를 **멱등하게** 만들고, 신호 처리기는 계속 등록해 둡니다.

```ts
/** 여러 번 호출돼도 한 번만 실행하고 같은 Promise를 돌려준다 */
function once<T>(fn: () => Promise<T>): () => Promise<T> {
  let result: Promise<T> | undefined;
  return () => (result ??= fn());
}

const cleanup = once(async () => { /* abort + sandbox.destroy() */ });
const onSignal = () => void cleanup();
process.on('SIGINT', onSignal);
process.on('SIGTERM', onSignal);
```

### 검증
샌드박스가 준비된 상태에서 **tsx 부모와 node 자식 양쪽에 SIGINT를 보내** 중복 신호를 재현했습니다.

```
== SIGINT -> node child=52941, tsx parent=52935
studio │ 샌드박스를 정리합니다 (studio-orders-2b242c)
containers left: 0
sandbox volumes left: 0
shared caches: b-studio-cache-gradle b-studio-cache-pnpm
```

### 배운 점
이 버그는 단위 테스트로는 잡을 수 없었습니다. **실제 프로세스 트리를 띄워 보고 나서야** 신호가 어떤 경로로 전달되는지 보였습니다.

## 2. Next dev 첫 요청이 준비 확인 시간을 넘김

**구분:** 실제 실행에서 발견

### 현상
준비 확인 로그가 이렇게 바뀌었습니다.

```
web │ 준비 확인: UND_ERR_SOCKET (컨테이너 running)
web │ 준비 확인: The operation was aborted due to timeout (컨테이너 running)
web │ 준비 확인: HTTP 200 (컨테이너 running)
```

Next.js dev 서버는 **페이지를 처음 요청받을 때 컴파일**합니다. 그래서 첫 요청이 확인 요청의 제한 시간(2초)을 넘깁니다. 포트는 열렸지만 서버가 아직 요청을 처리하지 못하는 동안에는 `UND_ERR_SOCKET`도 발생합니다.

### 해결
1. **판정 규칙**: 연결 에러와 타임아웃은 "실패"가 아니라 "기동 중"으로 보고, 서비스별 `timeoutSeconds`까지 기다립니다. 반대로 컨테이너가 죽었을 때는 즉시 실패로 봅니다. ([ADR-007](decisions.md#adr-007-서비스-준비-판정-규칙))
2. **로그 정리**: `AbortSignal.timeout`이 던지는 `DOMException(TimeoutError)`을 `TIMEOUT`으로 짧게 표시합니다. `instanceof Error`보다 먼저 `name`으로 확인하도록 했습니다.

수정 후 로그:

```
web │ 준비 확인: UND_ERR_SOCKET (컨테이너 running)
web │ 준비 확인: TIMEOUT (컨테이너 running)
web │ 준비 확인: HTTP 200 (컨테이너 running)
web │ 준비 완료 → http://127.0.0.1:32770
```

## 3. 공유 캐시를 써도 두 번째 기동이 크게 빨라지지 않음

**구분:** 실제 실행에서 발견. 측정 후 원인별로 대응 ([ADR-021](decisions.md#adr-021-기동-최적화-입력-파일-해시로-찾는-스냅샷-볼륨))

### 현상
Gradle과 pnpm 캐시를 공유 볼륨으로 유지했는데도, 두 번째 기동은 **늦어도 43초 안에** 준비되는 수준이었습니다(첫 확인 시점 기준 상한값). 극적인 차이는 없었습니다.

### 처음 세운 가설
`node_modules`가 샌드박스 전용 볼륨이라 매번 새로 설치되기 때문이라고 보고, 토스 TOI의 `packageSetHash`처럼 **lockfile 해시로 설치가 끝난 상태를 재사용**하려 했습니다.

### 측정: 가설대로 고치기 전에 단계별 시간부터 쟀다
기동 단계별 시간을 재는 `pnpm bench:boot`를 만들어 공유 캐시가 채워진 상태로 두 번 띄웠습니다(준비까지 17.9초, 13.4초). 두 번째 기동의 내역입니다.

| 서비스 | 단계 | 시간 |
|---|---|---|
| 공통 | 이미지 확인과 컨테이너 생성(`compose up`) | 3.7초 |
| web | `pnpm install` (패키지 354개 연결) | 3.1초 |
| web | Next dev 기동, 첫 요청 컴파일 | 0.3초, 2.0초 |
| api | 첫 로그부터 `compileJava` 시작까지 (Gradle 기동·설정) | **5.2초** |
| api | 컴파일, Spring 기동 | 2.0초, 약 1초 |
| | 준비 완료 | web 9.9초, **api 13.4초** |

준비 시간은 **늦게 뜨는 api가 정했고**, api에서 가장 큰 비용은 의존성 설치가 아니라 Gradle 기동과 설정이었습니다. 가설대로 `node_modules`만 재사용했다면 web만 빨라지고 준비 시간은 그대로였을 것입니다.

### 후보별 실험
컨테이너 안에서 `date +%s%N`으로 각 단계만 잘라 쟀습니다.

| 실험 | 결과 |
|---|---|
| 빈 `node_modules`에 `pnpm install` | 3.5초 |
| 설치가 끝난 `node_modules`(459MB, 파일 25,307개)를 새 볼륨으로 복사 | 0.77초 (방금 설치해 페이지 캐시가 있는 상태) |
| 복사한 `node_modules`에서 `pnpm install` | 0.65초 ("Already up to date") |
| `compileJava`, 빈 `.gradle`·`build` (지금 방식) | 7.5초 |
| + Gradle 빌드 캐시에서 가져오기 (`FROM-CACHE`) | 6.6초 |
| + 프로젝트 `.gradle`을 유지해 설정 캐시 재사용 | 4.5초 |

### 첫 적용: 오히려 빨라지지 않음
두 볼륨(`node_modules`, Gradle `.gradle`) 모두 스냅샷으로 만들고 다시 쟀더니, 스냅샷에서 시작한 기동도 **13.6초, 13.4초로 그대로**였습니다.
- `pnpm install`은 0.45초로 줄었지만 `node_modules` 복사가 2.7초 걸렸습니다. 실험 때(0.77초)와 달리 스냅샷을 처음 읽을 때는 페이지 캐시가 비어 있었습니다. 같은 스냅샷을 복사 방식별로 다시 재 보니, 처음 읽을 때는 busybox `cp` 2.4초·debian `cp` 1.2초였고 두 번째에는 둘 다 약 1.05초였습니다. `tar` 파이프는 약 3초로 더 느렸습니다.
- 복사가 `compose up` 전에 끝나야 해서, **빨라진 api까지 web 복사를 기다렸습니다.** api는 Gradle 준비가 5.2초에서 2.7초로 줄었지만 시작이 약 2.3초 늦어져 효과가 사라졌습니다.
- 이미지 빌드(`compose build`)는 캐시가 있으면 0.2~0.4초라, 복사를 빌드와 병렬로 돌려도 복사 시간을 흡수하지 못했습니다.

### 해결
- 스냅샷은 **이득이 측정된 볼륨에만** 켭니다. 예제에서는 Gradle 프로젝트 `.gradle`(복사 0.2~0.7초로 설정 단계 약 2.5초 절약)만 켜고 `node_modules`는 끕니다.
- Gradle 빌드 캐시와 설정 캐시를 템플릿의 `gradle.properties`로 켭니다.
- 스냅샷 복사는 이미지 빌드와 동시에 합니다.

### 수정 후 검증
Gradle 스냅샷만 켠 상태에서 `pnpm bench:boot examples/orders 3`으로 세 번 띄웠습니다.

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 준비까지 | 13.4초 | **10.9초, 10.9초, 10.8초** |
| api 첫 로그부터 `compileJava` 시작까지 | 5.2초 | 2.7~3.0초 (`Reusing configuration cache.`) |
| `compileJava` | 컴파일 | `FROM-CACHE` |
| 스냅샷 복사 (`.gradle`) | - | 0.2~0.3초 |
| 기동 후 남은 샌드박스 볼륨 | 0개 | 0개 (미리 만든 볼륨도 `down --volumes`로 삭제됨) |

### 배운 점
- **전체 시간은 가장 늦은 서비스가 정합니다.** 빠른 서비스를 더 빠르게 만드는 최적화는 숫자에 드러나지 않습니다.
- **실험 환경과 실제 경로의 조건이 다를 수 있습니다.** 방금 설치한 볼륨을 복사한 실험(0.77초)은 페이지 캐시 덕분이었고, 실제 기동에서는 3배 넘게 걸렸습니다. 최적화는 실험값이 아니라 적용 후 전체 기동으로 확인해야 합니다.

## 5. 검증 게이트가 컴파일 에러가 있는 코드를 "준비 완료"로 통과시킴

**구분:** 에이전트 e2e 실행에서 발견 → 원인을 실측으로 확인 → 수정 후 재검증

### 현상
e2e 시나리오 A는 **일부러 오타를 넣은 코드**(`return customerNam;`)를 쓰고 턴을 끝냅니다. 기대한 흐름은 "api 컴파일 실패 → 게이트 실패 → 수정 → 통과"였습니다. 그런데 결과는 이랬습니다.

```
▶ A. 주문 목록 API와 화면 (컴파일 에러 → 게이트 실패 → 수정 → 통과)
  게이트: 5개 파일 → 재시작·계약 비교
    검증 통과
    - web: 재시작 후 준비 완료
    - api: 재시작 후 준비 완료
    - api 계약:
        계약 변경 없음
  결과: done · 2턴 · 게이트 실패 0회 · 11.2s
  ✗ 게이트 [실패, 통과] (실제: true)
  ✗ API 응답에 시드 데이터 ({"timestamp":"2026-09-10T12:45:05.694Z","status":404,"error":"Not Found","path":)
```

- 게이트 전체가 11초 만에 끝났고, 새 API를 추가했는데도 계약이 "변경 없음"이었으며, `/api/orders`는 404였습니다. **새 코드가 아니라 옛 코드가 떠 있었다**는 뜻입니다.
- 몇 분 뒤 시나리오 B에서 api를 재시작하자 **A의 오타가 그제서야** 컴파일 에러로 드러났습니다.

```
/app/src/main/java/com/example/api/orders/CustomerOrder.java:32: error: cannot find symbol
        return customerNam;
               ^
```

게이트가 틀린 결과를 통과시키는 것은 게이트가 없는 것보다 위험합니다. 시나리오에 **"실패해야 하는 경우"**를 넣어 두지 않았다면 발견하지 못했을 버그입니다.

### 가설
colima의 기본 마운트는 sshfs이고, Lima 문서에 따르면 sshfs 캐시는 기본으로 켜져 있으며 호스트 변경이 제때 반영되지 않을 수 있습니다. 게이트는 파일을 쓰고 1초도 안 돼 서비스를 재시작했습니다. 그래서 빌드 도구가 **새 폴더와 파일이 반영되기 전의 소스 목록**을 보고, 이전에 컴파일해 둔 클래스(`api-build` 볼륨)로 앱을 띄웠다고 추정했습니다.

### 측정: 추측으로 고치지 않고 먼저 확인
호스트에서 파일을 바꾼 뒤, **같은 VM 마운트를 붙인 새 busybox 컨테이너**에서 반영될 때까지 0.5초 간격으로 확인했습니다.

**1차: 경로로 파일을 직접 열어 내용 확인**

| 경우 | 반영까지 |
|---|---|
| 기존 파일 수정 (크기 변경) | 1.7초 |
| 기존 파일 수정 (같은 크기) | 0.2초 |
| 기존 폴더에 새 파일 | 0.2초 |
| 새 폴더에 새 파일 | 0.2초 |

이 결과만 보면 지연이 짧아서 11초 동안 옛 코드가 돈 이유를 설명하지 못합니다. 그런데 빌드 도구는 파일을 경로로 여는 게 아니라 **디렉터리 목록과 파일 속성**으로 변경을 감지합니다.

**2차: 빌드 도구처럼 목록과 속성 확인 (직전에 한 번 읽어 캐시를 채운 상태)**

| 경우 | 반영까지 |
|---|---|
| 기존 폴더에 새 파일 → `ls` 목록 | **21.6초** |
| 새 폴더 → 상위 폴더 `ls` 목록 | **20.2초** |
| 기존 파일 크기 변경 → `stat` 크기 | **21.8초** |
| 새 파일 → `find` 재귀 탐색 | **20.9초** |

목록과 속성은 **약 20초 동안 옛 상태**로 보였습니다. 파일을 쓴 직후 재시작한 서비스가 옛 소스 목록을 볼 수 있는 조건이 실제로 존재한다는 뜻입니다.

### 해결
재시작 전에 **샌드박스 쪽에서 바뀐 파일이 보일 때까지 기다리는 동기화 지점** `Sandbox.sync(files)`을 추가했습니다([ADR-014](decisions.md#adr-014-재시작-전에-샌드박스가-바뀐-파일을-보는지-확인한다)).
- 디렉터리 목록에 이름이 보이는지와 내용 sha256이 호스트와 같은지를 함께 확인합니다. 1차 측정처럼 경로로 직접 여는 확인만으로는 이 버그를 막지 못합니다.
- 검증 게이트와 `restart_service` 도구가 재시작 전에 호출합니다.
- 반영이 60초 안에 확인되지 않으면 재시작하지 않고 게이트 실패로 처리합니다.

### 수정 후 검증
같은 e2e를 다시 실행했습니다.

```
▶ A. 주문 목록 API와 화면 (컴파일 에러 → 게이트 실패 → 수정 → 통과)
  게이트: 5개 파일 → 재시작·계약 비교
    검증 실패
    - 샌드박스 파일 반영 확인: 15.9초
    - web: 재시작 후 준비 완료
    - api: 준비 실패 — 컨테이너가 종료됐습니다 (마지막 확인: ECONNRESET, 컨테이너 exited)
      마지막 로그:
        > Task :compileJava FAILED
        /app/src/main/java/com/example/api/orders/CustomerOrder.java:29: error: cannot find symbol
                return customerNam;
  게이트: 4개 파일 → 재시작·계약 비교
    검증 통과
    - 샌드박스 파일 반영 확인: 0.7초
    - api: 재시작 후 준비 완료
    - api 계약:
        ＋ operation-added GET /api/orders
        ＋ schema-added OrderResponse
  결과: done · 4턴 · 게이트 실패 1회 · 33.5s
```

- 첫 게이트는 반영을 **15.9초** 기다린 뒤 재시작했고, 이번에는 컴파일 에러를 정확히 잡아 로그와 함께 돌려줬습니다. 2차 측정의 약 20초 지연과 같은 규모입니다.
- 두 번째 게이트는 **지난 게이트 이후 바뀐 파일과 실패했던 api만** 다시 확인했고, 이미 통과한 web은 재시작하지 않았습니다.
- 캐시가 이미 새 상태일 때는 확인이 0.2~3.0초 만에 끝났습니다(시나리오 B 3.0초, C 0.2초). 지연이 없는 환경에서는 비용이 작습니다.
- 시나리오 A~C의 확인 항목이 모두 통과했습니다.

### 배운 점
- **1차 측정에서 멈췄다면 "지연은 1~2초뿐"이라는 틀린 결론을 냈을 것입니다.** 문제를 재현하려면 빌드 도구가 파일을 *어떻게* 보는지(목록과 속성)를 그대로 흉내 내야 했습니다.
- colima를 virtiofs 마운트로 바꾸는 방법도 있지만 직접 검증하지 않았고, 사용자 환경을 강제할 수도 없습니다. 그래서 환경과 무관하게 동작하는 동기화 지점을 기본으로 두었습니다.

## 6. 미리보기 iframe의 HMR WebSocket 연결이 계속 실패함

**구분:** 스튜디오 UI를 브라우저로 검증하다가 발견 → 문서로 원인 확인 → 수정 후 핸드셰이크와 콘솔로 재검증

### 현상
스튜디오 화면 자체에는 문제가 없었지만, 미리보기 iframe 안의 Next.js dev 서버가 HMR 연결을 계속 다시 시도하면서 콘솔 에러가 수십 개 쌓였습니다.

```
WebSocket connection to 'ws://127.0.0.1:32788/_next/hmr?id=...' failed:
Error during WebSocket handshake: net::ERR_INVALID_HTTP_RESPONSE
```

같은 요청을 `curl`로 직접 보내자 **HTTP 응답 없이 연결이 끊겼습니다.**

### 원인
Next.js 16의 `allowedDevOrigins` 문서에 따르면, dev 서버는 **시작된 호스트 이름이 아닌 출처에서 오는 개발용 요청을 기본으로 막습니다.** 샌드박스의 dev 서버는 컨테이너 안에서 `--hostname 0.0.0.0`으로 시작하고, 미리보기는 `127.0.0.1:<빈 포트>`로 접속합니다. 페이지 요청은 통과했지만 개발용 HMR 연결은 막혔습니다. 원인은 문서의 동작 설명과 수정 결과로 확인했고, Next.js 내부 코드까지 추적하지는 않았습니다.

### 해결
Next.js 템플릿과 예제의 `next.config.ts`에 미리보기 출처를 허용했습니다.

```ts
allowedDevOrigins: ["127.0.0.1"],
```

### 검증
새 세션에서 같은 핸드셰이크를 보내자 이번에는 연결이 수락됐습니다.

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
```

샌드박스가 준비된 뒤 브라우저 콘솔 에러는 **0개**였습니다. 서비스가 재시작되는 몇 초 동안의 연결 거부는 컨테이너가 교체되는 동안 생기는 정상적인 에러입니다.

## 7. 로그 탭에 unknown이라는 서비스가 생김

**구분:** 스튜디오 UI 검증 중 발견

### 현상
로그 탭의 서비스 필터에 `web`, `api`, `db` 외에 `unknown`이 나타났습니다. 브라우저에서 해당 줄을 뽑아 보니 22줄이었고, 이런 형태였습니다.

```
"\x1b[Kapi-1 exited with code 143"
"\x1b[Kweb-1 has been recreated"
""
```

### 원인
`docker compose logs --follow`는 일반 로그(`api-1  | 타임스탬프 메시지`) 사이에 **컨테이너 수명 주기 알림**을 섞어 보냅니다. 이 알림에는 `|`와 타임스탬프가 없고, `--no-color`를 줘도 줄 앞에 **줄 지우기 제어 코드(`ESC[K`)**가 붙습니다. 파서는 타임스탬프가 있는 형식만 알고 있었습니다.

### 해결
- 제어 코드를 먼저 지우고, 내용이 없는 줄은 건너뜁니다.
- `<서비스>-<번호> <내용>` 형태의 상태 줄은 해당 서비스의 로그로 분류합니다.
- 로그 본문에 있는 `[api]` 같은 대괄호를 제어 코드로 오인해 지우지 않는지 테스트로 고정했습니다.

### 함께 고친 것
처음 작성한 정규식에는 ESC 문자가 **보이지 않는 문자 그대로** 들어가 있었습니다. 동작은 맞았지만 편집 도구로 문자열을 찾지 못해 수정이 한 번 실패했고, 리뷰에서도 놓치기 쉽습니다. 그래서 눈에 보이는 `\u001b` 이스케이프로 바꿨습니다.

## 8. 서비스가 재시작되면 미리보기에 입력한 경로가 초기화됨

**구분:** 스튜디오 UI 검증 중 발견

### 현상
API 탐색기에서 `/api/orders`를 선택해 두었는데, 에이전트 요청이 끝난 뒤 경로가 `/`로 돌아가 있었습니다.

### 원인
서비스가 재시작되는 동안 상태가 "준비 확인 중"으로 바뀌면, 미리보기 영역이 대기 화면으로 **교체**됐습니다. 그래서 준비가 끝나면 미리보기 컴포넌트가 새로 만들어졌고, 입력해 둔 경로와 요청 상태가 사라졌습니다.

### 해결
한 번이라도 주소를 받은 서비스는 재시작 중에도 **미리보기를 그대로 두고 위에 상태 배너만** 띄웁니다. 재시작 중에는 API 요청 버튼을 비활성화합니다. 대기 화면은 아직 한 번도 준비되지 않은 서비스에만 보여 줍니다.

### 검증
미리보기 경로에 `/orders`를 입력하고 에이전트 요청을 실행했습니다. 서비스가 재시작돼 포트가 32796에서 32799로 바뀐 뒤에도 경로는 `/orders`로 남았고, iframe은 `http://127.0.0.1:32799/orders`를 불러와 주문 표를 보여 줬습니다.

## 9. "//"로 시작하는 경로가 다른 호스트를 가리킴

**구분:** 구현 중 코드를 검토하다 발견한 보안 문제 (실제 공격을 받은 것은 아님)

### 현상
서비스 주소와 경로를 합칠 때 `new URL(path, base)`를 썼습니다. 그런데 경로가 `//`로 시작하면 **호스트가 바뀝니다.**

```js
new URL('//evil.example/x', 'http://127.0.0.1:32789').toString()
// → 'http://evil.example/x'
```

같은 방식으로 경로를 합치는 곳이 세 군데 있었습니다.
- 에이전트의 `http_request` 도구: 모델이 서비스 밖으로 요청을 보낼 수 있음
- API 탐색기 프록시: 스튜디오 서버가 임의의 호스트로 요청을 대신 보낼 수 있음
- `studio.yaml`의 준비 확인·계약 추출 경로

### 해결
- 요청 URL을 만든 뒤 **origin이 서비스 주소와 같은지** 비교하고, 다르면 거부합니다.
- `studio.yaml`의 경로 필드는 `^\/(?!\/)` 정규식으로 `//`를 거부합니다.

### 검증
- API 탐색기 프록시에 `//example.com/x`를 보내면 400(`서비스 밖의 주소로는 요청할 수 없습니다`)을 반환합니다.
- 도구와 스키마 단위 테스트로 같은 경우를 고정했습니다.

---

## 10. 다시 연결하면 체크포인트 목록이 중복됨

**구분:** 체크포인트 기능을 브라우저로 검증하다가 발견

### 현상
요청을 모두 실행한 뒤 기록 탭을 열자 같은 체크포인트가 두 번씩 보였습니다.

```
요청: 주문에 배송 메모 필드 추가해줘   668fb7d, 현재
요청: 주문 목록 API와 화면을 만들어줘   f6c3cb7
요청: 주문에 배송 메모 필드 추가해줘   668fb7d
요청: 주문 목록 API와 화면을 만들어줘   f6c3cb7
세션 시작                               5c79494
```

브라우저 콘솔에는 React key 중복 에러가 12개 쌓였습니다.

```
Encountered two children with the same key, `668fb7d81bac59fb18db35d2032840d42ce9e742`.
```

### 원인
[ADR-015](decisions.md#adr-015-스튜디오-서버-nextjs-단일-앱과-server-sent-events)에서 "연결하면 스냅샷부터 기록을 다시 보내고, 리듀서는 스냅샷에서 초기화하므로 중복이 없다"고 설계했습니다. 그런데 이 전제는 **스냅샷을 바꾸는 이벤트가 모두 멱등할 때만** 성립합니다.
- 서비스 상태(`service`)나 세션 상태(`status`) 이벤트는 값을 **대입**하므로 여러 번 적용해도 결과가 같습니다.
- 체크포인트(`checkpoint`) 이벤트는 목록 앞에 **추가**합니다. 서버는 체크포인트를 스냅샷에 먼저 반영한 뒤 이벤트를 기록에 남기므로, 페이지를 연 브라우저는 "이미 들어 있는 스냅샷" 위에 같은 체크포인트를 한 번 더 추가했습니다.

### 해결
체크포인트 이벤트는 같은 SHA가 이미 목록에 있으면 추가하지 않습니다. "스냅샷에 이미 반영된 체크포인트가 기록 재생으로 다시 들어오는" 경우를 단위 테스트로 고정했습니다.

### 검증
세션 페이지를 새로 불러오자 체크포인트 3개가 한 번씩만 보였고, 콘솔 에러는 0개였습니다.

### 배운 점
"스냅샷 + 기록 재생" 구조에서는 **모든 이벤트가 두 번 적용돼도 안전한지**를 이벤트를 추가할 때마다 확인해야 합니다. 이 원칙을 ADR-015에 덧붙였습니다.

## 11. 서비스를 재시작할 때마다 브라우저 콘솔에 HMR 연결 실패가 쌓임

**구분:** 로컬 로그인 계정 모드를 실제 모델과 브라우저로 검증하다가 발견

### 현상
요청 두 개를 처리한 뒤 브라우저 콘솔에 에러가 10개 있었습니다. 모두 같은 종류였습니다.

```
WebSocket connection to 'ws://127.0.0.1:32819/_next/hmr?id=...' failed: Error in connection establishment: net::ERR_CONNECTION_REFUSED
WebSocket connection to 'ws://127.0.0.1:32821/_next/hmr?id=...' failed: Error during WebSocket handshake: net::ERR_CONNECTION_RESET
```

### 원인
에러가 난 위치부터 확인했습니다. 10개 모두 **미리보기 앱이 보낸 요청**(`127.0.0.1:<web 포트>/_next/static/...`)이었고, 스튜디오 코드에서 난 에러는 없었습니다.
- 검증 게이트가 web을 재시작할 때마다 호스트 포트가 바뀝니다. 이번 세션에서는 32819 → 32821 → 32822로 바뀌었습니다.
- 재시작하는 동안 사용자가 입력한 경로를 잃지 않도록 미리보기 iframe을 그대로 둡니다([8번](#8-서비스가-재시작되면-미리보기에-입력한-경로가-초기화됨)). 그 사이 이전 페이지의 Next.js 개발 클라이언트가 사라진 포트로 다시 연결을 시도합니다.
- 재시작 한 번에 5개씩 쌓였고, 에러의 포트는 모두 이전 포트였습니다. 준비가 끝난 뒤 iframe은 새 주소(`http://127.0.0.1:32822/`)로 옮겨 가 바뀐 화면을 정상적으로 보여 줬습니다.

### 판단
기능 문제는 아니어서 이번에는 고치지 않았습니다. 재시작하는 동안 iframe을 비우면 에러는 사라지지만, 그동안 미리보기가 빈 화면이 됩니다. 사용자가 콘솔 에러를 스튜디오 오류로 오해하는 일이 생기면 "재시작 중에는 iframe을 비우고 경로만 기억하는" 방식으로 바꿀 계획입니다.

### 배운 점
콘솔 에러는 개수만 세지 않고 **어느 origin에서 났는지**부터 봐야 합니다. 미리보기처럼 다른 앱을 품은 화면에서는 에러가 스튜디오 것이 아닐 수 있습니다.

### 이후 달라진 점
네트워크 격리([ADR-024](decisions.md#adr-024-네트워크-격리-샌드박스의-출입구를-하나로-만든다))부터는 서비스 포트를 edge 컨테이너가 공개합니다. edge는 서비스를 재시작해도 그대로이므로 **호스트 포트가 바뀌지 않습니다.** 브라우저로 데모 요청 A를 다시 실행해 확인했습니다.
- web·api를 재시작한 뒤에도 미리보기 포트는 33020, 33021 그대로였습니다.
- 콘솔의 WebSocket 연결 실패는 web이 재시작하는 동안의 2건뿐이었습니다. 이후 미리보기 앱이 같은 포트로 `[HMR] connected`를 남겼습니다.

이전 포트로 계속 재연결하느라 에러가 쌓이던 원인이 사라져, 따로 고치지 않습니다.

## 12. 체크포인트로 되돌린 뒤 DB 스키마가 코드와 달라짐

**구분:** 데이터 기능을 설계하다가 의심하고, 데모 시나리오로 재현해 확인

### 현상
배송 메모(V2 마이그레이션)를 추가한 체크포인트에서 그 전 체크포인트로 되돌린 뒤 상태를 확인했습니다.

| 확인 | 결과 |
|---|---|
| 작업 복사본의 마이그레이션 | `V1__create_orders.sql`만 남음 |
| DB의 `flyway_schema_history` | 1, **2** (V2 적용 기록이 남음) |
| api를 다시 띄웠을 때 Flyway | `Schema "public" has a version (2) that is newer than the latest available migration (1) !` 경고만 남기고 기동 |

코드는 V1 시점인데 DB에는 `memo` 열과 V2 기록이 남아, **코드와 스키마가 다른 상태로 작업이 이어졌습니다.** 이 상태에서 같은 요청을 다시 하면 이미 있는 열을 추가하는 마이그레이션이 충돌할 수 있습니다.

### 원인
체크포인트 되돌리기가 파일만 되돌리고 샌드박스 안의 DB는 그대로 뒀습니다. Flyway는 기본 설정에서 "코드보다 앞선 버전"을 오류로 보지 않아 문제가 드러나지 않았습니다.

### 해결
체크포인트마다 `pg_dump`로 DB 상태를 남기고, 되돌릴 때 같은 시점의 덤프로 DB를 다시 만듭니다([ADR-022](decisions.md#adr-022-데이터베이스-브랜치-체크포인트마다-db-상태를-함께-남긴다)).

### 수정 후 검증
같은 시나리오(A 주문 목록 → B 배송 메모 → C 호환 깨짐으로 차단 → A로 되돌리기)를 다시 실행했습니다.

| 확인 | 결과 |
|---|---|
| 체크포인트별 덤프 | 세션 시작, A, B마다 1개씩. 차단된 C는 체크포인트도 덤프도 없음 |
| C를 되돌릴 때 DB | 지금 상태와 B 덤프가 같아 **건드리지 않음** (비교 129ms) |
| A로 되돌릴 때 DB | 0.5초 만에 다시 만듦. `flyway_schema_history`는 1만 남고 `memo` 열 없음, A 시점의 주문 2건 유지 |

## 13. 되돌린 뒤 api가 지운 파일을 찾다가 기동하지 못함

**구분:** DB 브랜치를 검증하다가 발견. 원인을 세 번 잘못 짚은 뒤 스택 트레이스로 확정

### 현상
배송 메모 체크포인트에서 그 전 체크포인트로 되돌리면, DB는 올바르게 되돌아가는데 api가 기동하지 못했습니다. 스튜디오 되돌리기에서 설정과 무관하게 매번 같았습니다.

```
> Task :processResources FAILED
> Cannot access input property 'rootSpec$1' of task ':processResources'. Accessing unreadable inputs or outputs is not supported.
   > java.nio.file.NoSuchFileException: /app/src/main/resources/db/migration/V2__add_order_memo.sql
```

### 가설과 검증: 세 번 잘못 짚었다
에러에 지운 파일이 나오고, 직전 PR에서 Gradle 설정 캐시와 `.gradle` 스냅샷을 켰고, 이 환경에는 파일 공유 캐시 지연([5번](#5-검증-게이트가-컴파일-에러가-있는-코드를-준비-완료로-통과시킴))도 있어서 후보가 여럿이었습니다.

| 가설 | 실험 | 결과 | 판단 |
|---|---|---|---|
| Gradle 설정 캐시 | Gradle 컨테이너만 따로 띄워 리소스 파일 삭제 → 반영 확인 → 빌드 | 성공 | 재현 안 됨 |
| Gradle 설정 캐시 | 스튜디오와 같은 제공자 경로(`sandbox.sync` → `sandbox.restart`)에서 설정 캐시만 바꿈 | 켬: 실패, 끔: 성공 | 원인처럼 보였지만, **켠 쪽만 `.gradle`을 스냅샷에서 채워 조건이 둘 달랐음** |
| Gradle 설정 캐시 | 스튜디오 되돌리기를 설정 캐시를 끄고 실행 | **실패** | 원인 아님 |
| `.gradle` 스냅샷 | 스냅샷도 끄고 설정 캐시도 끔 | **실패** | 원인 아님 |
| 반영 확인 지연 | 호스트에서 지운 파일이 루트를 붙인 컨테이너와 서비스 폴더를 붙인 컨테이너에서 사라져 보이는 시점 | 세 번 모두 20.5~21초로 같음 | 두 컨테이너는 같은 상태를 봄 |
| 반영 확인 지연 | 되돌린 직후 두 마운트에서 목록과 `stat` 확인 | V2 없음, 반영 확인은 1.6초 기다려 통과 | 반영 확인 자체는 정상 |

### 원인: 스택 트레이스로 확정
`org.gradle.logging.stacktrace=all`로 실패한 빌드의 스택 트레이스를 받았습니다.

```
Caused by: java.io.UncheckedIOException: java.nio.file.NoSuchFileException: .../V2__add_order_memo.sql
    at org.gradle.internal.snapshot.impl.DirectorySnapshotter$PathVisitor.doVisitFileFailed(DirectorySnapshotter.java:473)
    at org.gradle.internal.snapshot.impl.DirectorySnapshotter.snapshot(DirectorySnapshotter.java:127)
```

Gradle이 저장해 둔 캐시가 V2를 기억한 것이 아니었습니다. **새로 뜬 api 컨테이너가 리소스 폴더를 훑는 순간 디렉터리 목록에는 V2가 있었고, 파일을 읽으려 하자 없었습니다.** 같은 시각 반영 확인 컨테이너는 이미 V2가 사라진 목록을 봤습니다(시각을 맞춰 기록한 결과, 반영 확인 통과 1.5초 뒤 빌드 시작). 두 컨테이너가 서로 다른 목록을 본 파일 공유 계층 내부의 정확한 이유는 확인하지 못했습니다. 체크포인트 기능을 처음 검증할 때 "세션 시작"으로 되돌려 마이그레이션 폴더가 통째로 사라진 경우는 문제가 없었고, 폴더는 남고 파일 하나만 지워질 때 났습니다.

### 해결
- 서비스를 재시작했는데 실패했고, **로그가 이번 변경에서 지운 파일을 "없다"고 가리키면** 3초 뒤 한 번만 다시 재시작합니다. 컴파일 에러처럼 무관한 실패는 다시 시도하지 않아 에이전트가 받는 피드백이 늦어지지 않습니다.
- 검증 보고서와 대화에 "한 번 더 재시작"을 표시합니다.
- 원인으로 의심해 잠시 껐던 Gradle 설정 캐시와 `.gradle` 스냅샷은 원인이 아니었으므로 다시 켰습니다.

### 수정 후 검증
같은 되돌리기를 세 가지 Gradle 설정으로 실행했습니다.

| 설정 | 되돌리기 | api | 되돌린 뒤 상태 |
|---|---|---|---|
| 설정 캐시 끔 | 21.7초 | 한 번 더 재시작 후 준비 | `GET /api/orders` 200 (주문 2건, `memo` 없음), Flyway 기록 1만, `memo` 열 없음 |
| 설정 캐시 켬 | 19.6초 | 한 번 더 재시작 후 준비 | 같음 |
| 설정 캐시 켬 + `.gradle` 스냅샷에서 시작 | 18.4초 | 한 번 더 재시작 후 준비 | 같음 |

### 배운 점
- **"한 조건만 바꾼 비교"가 실제로 한 조건만 바꿨는지 확인해야 합니다.** 설정 파일 내용이 스냅샷 키에 들어가서, 설정 캐시를 바꾸자 스냅샷 사용 여부도 함께 바뀌었습니다. 이 비교를 믿고 문서에 원인을 적었다가 고쳤습니다.
- **에러 메시지로 추측을 이어가기 전에 스택 트레이스부터 받아야 했습니다.** 스택 트레이스 한 번이 실험 네 번보다 확실했습니다.
- 파일을 지우는 경로(되돌리기)도 기동과 캐시 변경의 검증 대상에 넣어야 합니다.

## 14. 한 서비스가 기동에 실패해도 다른 서비스의 준비 확인이 끝나지 않음

**구분:** 메모리 한도를 일부러 작게 걸어 검증하다가 발견

### 현상
api 메모리 한도를 300MiB로 걸고 샌드박스를 띄우자, api는 5.5초 만에 메모리 부족으로 종료되고 `start()`도 실패를 돌려줬습니다. 그런데 확인 스크립트는 샌드박스 정리까지 출력한 뒤 **2분이 넘도록 끝나지 않았습니다.**

### 원인
`start()`는 서비스별 준비 확인을 `Promise.all`로 기다립니다. api 확인이 실패하면 `Promise.all`은 곧바로 실패하지만, **web의 준비 확인은 멈추지 않고** 1초마다 계속 돌았습니다. 샌드박스를 지운 뒤에도 web 확인은 연결 실패를 "기동 중"으로 보고 web의 제한 시간(300초)까지 기다렸고, 그동안 프로세스가 끝나지 않았습니다.

스튜디오와 CLI는 세션을 멈출 때 중지 신호를 보내 이 확인을 끊기 때문에 드러나지 않았습니다. 하지만 기동 실패를 알린 뒤에도 남은 서비스가 헛되이 확인을 계속하고 상태 이벤트를 보냈습니다.

### 해결
- 한 서비스라도 준비에 실패하면 `start()` 안에서 나머지 서비스의 준비 확인도 함께 중단합니다. 호출한 쪽이 넘긴 중지 신호와 내부 중단 신호를 합쳐 모든 확인에 넘깁니다.
- 처음 고친 뒤 다시 돌려 보니, 멈춘 web에 `실패: The operation was aborted`가 떴습니다. web은 자기 문제로 실패한 것이 아니므로 "api 서비스가 준비에 실패해 확인을 멈췄습니다"처럼 원인 서비스를 알리게 했습니다.

### 수정 후 검증
api 한도를 150MiB로 건 같은 확인은 api가 5.7초에 실패한 뒤 **스크립트 전체가 9초 만에 끝났습니다.**

## 15. 네트워크를 격리하자 web이 기동 3초 만에 종료됨

**구분:** 네트워크 격리를 실제 Docker로 검증하다가 발견

### 현상
서비스를 외부로 나갈 수 없는 internal 네트워크에 두고 출입구 컨테이너(edge)를 붙인 첫 실행에서, api와 db는 떴는데 web이 **기동 3초 만에** 실패했습니다.

```
status web failed 컨테이너가 종료됐습니다 (마지막 확인: UND_ERR_SOCKET, 컨테이너 exited)
web Error: Error when performing the request to https://registry.npmjs.org/pnpm/-/pnpm-10.29.3.tgz
web   [cause]: Error: connect ECONNREFUSED 172.20.0.4:3128
```

### 원인
구현 전에 인터넷을 완전히 끊고 예제를 띄워 본 실험에서 두 서비스의 차이를 확인해 두었습니다.

- api는 공유 Gradle 캐시가 채워져 있으면 **인터넷 없이 기동했습니다** (네트워크 오류 0건).
- web은 매번 실패했습니다. `corepack`이 새 컨테이너마다 pnpm을 내려받으려 하고, 이름 풀이부터 막혀 `EAI_AGAIN registry.npmjs.org`로 끝났습니다. corepack이 받은 pnpm은 볼륨이 아니라 컨테이너 파일 시스템에 남기 때문입니다.

그래서 web은 edge의 프록시(3128 포트)로 저장소에 나가야 합니다. 이번에는 이름 풀이 오류가 아니라 **연결 거부**였고, 주소 `172.20.0.4`는 edge 컨테이너였습니다. compose는 `depends_on`이 없는 서비스를 동시에 시작합니다. edge의 Node 프로세스가 3128 포트를 열기 전에 corepack이 요청을 보냈고, corepack은 다시 시도하지 않고 끝났습니다. 개발 컨테이너에는 재시작 정책이 없어 그대로 종료됐습니다.

### 해결
- edge에 3128 포트로 TCP 연결을 확인하는 `healthcheck`를 넣었습니다. 시작 직후에는 0.2초 간격으로 확인합니다.
- override에서 모든 compose 서비스에 `depends_on: { b-studio-edge: { condition: service_healthy } }`를 겁니다.
- 사용자의 compose가 목록 형식(`depends_on: [db]`)을 써도 override의 맵 형식과 합쳐지는지 `docker compose config`로 확인했습니다. 결과는 `db: service_started`와 `b-studio-edge: service_healthy`가 둘 다 남는 것이었습니다.

### 수정 후 검증
같은 실행에서 web은 11초, api는 13초 만에 준비됐습니다(기동 12.8초). edge가 공개한 포트로 web `/` 200, api `/actuator/health` 200, `/v3/api-docs` 200을 받았습니다.

같은 검증 스크립트에서 HMR 확인이 멈춘 일도 있었습니다. 원인은 격리가 아니라 확인 방법이었습니다. 맨 WebSocket 업그레이드 요청을 보냈더니 edge를 거친 경우와 **web 컨테이너 안에서 `localhost:3000`으로 직접 보낸 경우 모두** 5초 동안 응답이 없었습니다. 그래서 HMR은 브라우저로 확인합니다.

## 16. 서비스를 재시작하면 로그 탭에 같은 줄이 두 번 쌓임

**구분:** 네트워크 격리를 브라우저로 검증하며 README용 화면을 찍다가 발견

### 현상
데모 요청 A를 실행한 뒤 로그 탭을 `b-studio-edge`로 걸러 보니, 같은 감사 로그가 두 번씩 있었습니다. 목록 중간에 edge 시작 줄(`{"edge":"started",...}`)이 다시 나오고, 그 뒤로 `01:06:31.076Z`부터 `01:07:40.755Z`까지의 줄이 시각까지 똑같이 반복됐습니다. edge 컨테이너는 세션 동안 한 번도 재시작하지 않았습니다.

### 원인
스튜디오는 서비스가 재시작 후 준비되면 로그 구독을 끊고 `--tail 20`으로 다시 붙습니다. `compose logs`는 새로 만든 컨테이너를 기존 구독에서 따라가지 않기 때문입니다. 그런데 다시 붙을 때 `--tail`은 **재시작하지 않은 컨테이너의 최근 줄까지** 다시 보냅니다. 스튜디오는 받은 줄을 모두 새 줄로 기록했습니다.

이 코드는 웹 스튜디오를 처음 만들 때부터 있었습니다. db 컨테이너의 줄도 같은 방식으로 중복됐을 텐데, db는 준비된 뒤 로그가 거의 나오지 않아 눈에 띄지 않았습니다. edge는 요청마다 감사 로그를 남기므로 드러났습니다.

### 해결
다시 붙는 순간 버퍼에 있는 로그의 서비스, 시각, 내용 조합을 모아 두고, 새 구독에서 받은 줄 중 셋이 모두 같은 줄은 건너뜁니다. compose 로그 시각은 밀리초까지 남기므로, 시각이 다른 같은 내용(예: 반복되는 `GET / 200`)은 그대로 남습니다.

### 수정 후 검증
새 세션에서 데모 요청 A를 다시 실행했습니다. 게이트가 web과 api를 재시작해 로그 구독도 다시 붙었습니다. 그 뒤 로그 탭을 `b-studio-edge`로 걸러 화면에 나온 줄과 edge 컨테이너의 `docker logs`를 정렬해 비교했습니다. **둘 다 18줄이고 내용도 같았습니다.** edge 시작 줄도 한 번만 나왔습니다.

같은 밀리초에 `fonts.gstatic.com` 허용 기록이 여러 줄 있는 것은 중복이 아닙니다. 폰트 파일을 동시에 받는 연결마다 edge가 남긴 줄이고, `docker logs` 원본에도 같은 수만큼 있습니다.

## 17. base64로 인코딩한 시크릿 값은 가려지지 않음

**구분:** 시크릿 가림을 실제 샌드박스에서 검증하다가 발견

### 현상
예제 복사본에 `PAYMENT_API_KEY`를 선언하고 에이전트 도구 `run_in_service`로 `sh -c 'echo "$PAYMENT_API_KEY" | base64; printenv PAYMENT_API_KEY'`를 실행했습니다. 둘째 줄은 `[PAYMENT_API_KEY 가림]`으로 나왔지만, 첫 줄의 `c2tfdGVzdF9iX3N0dWRpb180ZjlhMmM3MQo=`는 그대로 모델에게 가는 출력에 남았습니다. 이 문자열을 디코딩하면 값이 나옵니다.

### 원인
처음 구현은 원래 값과 URL 인코딩한 값만 찾았습니다. base64는 앞뒤 바이트에 따라 결과가 달라진다는 이유로 설계할 때 뺐고, 한계로 적어 둘 생각이었습니다. 하지만 명령 하나로 가림을 우회할 수 있다는 것이 실측으로 드러났습니다.

단순히 `base64(값)`을 함께 찾는 것으로는 부족합니다. base64는 3바이트씩 묶어 4글자로 바꾸므로 **값 앞에 몇 바이트가 붙느냐(0~2)**에 따라 같은 값도 다른 글자가 됩니다. 뒤에 붙는 바이트도 마지막 글자와 패딩을 바꿉니다. 위 출력도 `echo`가 붙인 줄바꿈 때문에 `base64(값)`과 끝 세 글자가 달랐습니다. Basic 인증 헤더처럼 `사용자:`가 앞에 붙으면 전체가 달라집니다.

### 해결
앞에 붙는 바이트 수 0, 1, 2 각각에 대해, 앞뒤 바이트의 비트가 섞이지 않고 값만으로 정해지는 base64 구간을 만들어 원래 값·URL 인코딩과 함께 가립니다. 가린 자리 옆에 경계 글자 1~2개가 남지만 그것으로 값을 복원할 수는 없습니다. 같은 형태를 검증 게이트와 체크포인트 커밋의 확인에도 쓰므로, base64로 파일에 쓴 값도 막힙니다.

단위 테스트는 실측에서 새어 나간 문자열이 `[PAYMENT_API_KEY 가림]Qo=`가 되는지와, 앞에 `a`, `ab`, `user:`, `api-client:`가 붙은 경우를 확인합니다.

### 수정 후 검증
같은 확인 스크립트를 실제 샌드박스에서 다시 돌렸습니다. `run_in_service` 결과의 첫 줄이 `[PAYMENT_API_KEY 가림]Qo=`, 둘째 줄이 `[PAYMENT_API_KEY 가림]`으로 나왔습니다. 나머지 확인(override 파일, 명령 출력, 로그, `read_file`, 게이트, 커밋 거부)도 이전과 같이 통과했습니다.

## 18. gVisor(runsc)에서 서비스 이름을 풀지 못함

**구분:** gVisor 격리를 실험하다가 발견. 사용자의 다른 컨테이너가 도는 colima 데몬은 건드리지 않고, 격리된 Docker-in-Docker 데몬에만 runsc를 등록했습니다

### 현상
runsc로 띄운 busybox 컨테이너에서 같은 네트워크의 컨테이너를 이름으로 부르자 `wget: bad address 'web:8080'`가 났습니다. 같은 컨테이너를 IP로 부르면 응답이 왔습니다. `/etc/resolv.conf`는 runc와 똑같이 `nameserver 127.0.0.11`이었습니다.

b-studio는 모든 연결을 서비스 이름에 기댑니다(`b-studio-edge` 프록시, `db`, 등록한 사내 API 별칭). 이대로는 샌드박스가 뜨지 않습니다.

### 원인
세 가지 설정을 일반 네트워크와 `internal` 네트워크에서 비교했습니다.

| 런타임 | 이름으로 연결 | IP로 연결 | 일반 네트워크에서 `1.1.1.1:443` | internal 네트워크에서 이름 / `1.1.1.1:443` |
|---|---|---|---|---|
| runc | 됨 | 됨 | 연결됨 | 됨 / 차단 |
| runsc (기본) | **`bad address`** | 됨 | 연결됨 | **`bad address`** / 차단 |
| runsc `--network=host` | 됨 | 됨 | 연결됨 | 됨 / 차단 |

gVisor 문서는 기본 모드가 "자체 네트워크 스택(netstack)을 쓰며 호스트 네트워크 스택과 격리된다"고 설명하지만, Docker 내장 DNS는 따로 다루지 않습니다. 이름 풀이만 실패하고 IP 연결은 되며, 호스트 네트워크 스택을 쓰는 `--network=host`에서는 이름 풀이가 됩니다. 이 결과로 볼 때, 내장 DNS(`127.0.0.11`)로 가는 경로가 gVisor 자체 네트워크 스택에서는 처리되지 않는 것으로 판단했습니다.

### 해결
runsc를 `runtimeArgs: ["--network=host"]`와 함께 등록하도록 안내하고, 이 설정으로 실제 샌드박스를 띄워 확인합니다. 샌드박스를 만들기 전에 `docker info`로 런타임이 등록됐는지 확인하고, 없으면 등록된 런타임 목록과 함께 거부합니다.

### 감수한 것
gVisor 문서에 따르면 `--network=host`는 "호스트에 대한 격리를 줄인다"고 합니다. 패킷을 gVisor가 아니라 컨테이너 네트워크 네임스페이스의 커널이 처리하기 때문입니다. internal 네트워크의 외부 차단은 세 설정 모두에서 유지됐습니다.

## 19. gVisor에서 파일을 고쳐도 미리보기가 바뀌지 않음

**구분:** gVisor 격리를 실제 override로 검증하다가 발견. 18번과 같은 격리된 Docker-in-Docker 데몬에서 edge와 Next web을 띄웠습니다

### 현상
runsc(`--network=host`)로 띄운 Next web에서 `app/page.tsx`의 표시 문구를 바꿔도 화면이 바뀌지 않았습니다. 수정 후 2초 간격으로 40초 동안 확인했지만 계속 옛 문구였습니다. runc에서는 10초 안에 새 문구가 나왔습니다.

### 원인 조사
1. **파일 변경 알림:** busybox `inotifyd`로 비교했습니다. 호스트 쪽에서 고친 내용과 새 파일은 runsc 안에서도 보였습니다. 하지만 inotify 이벤트는 runc에서 5건, runsc에서는 0건이었습니다. Next 개발 서버는 이 알림으로 수정을 알아채므로 변경을 놓칩니다.
2. **폴링 환경 변수:** 처음에는 `WATCHPACK_POLLING=true`를 켰는데, 10초 뒤 404가 나왔습니다. 이 변수가 Turbopack에 영향을 주는지는 확인할 수 없었습니다.
3. **Next 설정으로 폴링:** Next 16.3.4 코드를 확인하니 Turbopack 개발 서버는 `next.config`의 `watchOptions.pollIntervalMs`를 파일 감시기에 넘깁니다. 네이티브 바인딩 주석에는 "기본 파일 감시가 동작하지 않을 때(예: docker) 이 간격으로 폴링한다"고 적혀 있습니다. 이 값을 1000ms로 켜고 다시 쟀습니다.
   - 처음 다시 잰 결과는 버렸습니다. 스크립트에서 환경 변수가 `docker compose`가 아니라 앞의 `cd`에만 적용돼 폴링이 켜지지 않은 상태였고, 컨테이너 안에서 값이 비어 있는 것으로 알았습니다.
   - 값이 `1000`으로 들어간 것을 확인하고 다시 쟀습니다. 수정 후 4초까지는 옛 문구가 나왔고, **6초부터 40초까지 계속 404**였습니다. 수정은 감지했지만 페이지를 잃었습니다. 404가 나는 원인은 확인하지 못했습니다.
   - 이어서 파일을 교체 방식(`sed -i`)으로 고친 경우도 쟀지만, 이미 404가 된 상태에서 시작해 40초 내내 404였으므로 따로 판단할 수 없었습니다.
   - 대기 중 web 컨테이너 CPU 사용률은 폴링 없이 0.04%, 폴링을 켜면 16.73%였습니다.
4. **컨테이너 재생성:** 폴링 없이 수정한 뒤 검증 게이트의 재시작과 같은 방식(`up --no-deps --force-recreate`)으로 web을 다시 만들자, 5초 뒤 새 문구가 나왔습니다.

### 해결
폴링은 자동으로 켜지 않습니다. 페이지를 잃고, 대기 중에도 CPU를 계속 쓰기 때문입니다. gVisor에서는 에이전트 요청이 끝나고 검증 게이트가 바뀐 서비스를 다시 띄울 때 미리보기에 반영됩니다. 이 동작은 원래 모든 요청에서 실행되는 경로입니다. 세션 헤더의 gVisor 배지에 이 동작을 안내합니다.

## 20. Kubernetes에서 web이 edge 이름을 풀지 못해 기동 14초 만에 종료됨

**구분:** Kubernetes 제공자를 kind 클러스터(agent-sandbox v1.0.2, gVisor RuntimeClass)에서 처음 실측하다가 발견

### 현상
여기까지는 모두 됐습니다.
- 이미지 빌드와 `kind load`
- 네임스페이스·Secret·Sandbox 적용
- edge Pod 준비와 port-forward 연결

그런데 web은 시작하고 14초 뒤에 준비 확인이 실패했습니다.

```
status web failed 컨테이너가 종료됐습니다 (마지막 확인: UND_ERR_SOCKET, 컨테이너 exited)
web Error: Error when performing the request to https://registry.npmjs.org/pnpm/-/pnpm-10.29.3.tgz
web   [cause]: Error: getaddrinfo EAI_AGAIN b-studio-edge
```

같은 로그에 edge의 `{"edge":"started", ...}` 줄은 있었습니다.

### 원인
Docker 제공자에서 겪은 [15번](#15-네트워크를-격리하자-web이-기동-3초-만에-종료됨)과 같은 순서 문제입니다. 다만 증상이 조금 달랐습니다.
- **Docker:** compose `depends_on: service_healthy`로 edge가 준비된 뒤에 서비스를 띄우게 해 두었습니다.
- **Kubernetes:** 매니페스트를 한 번에 적용하면 Pod가 동시에 뜹니다. agent-sandbox가 만드는 헤드리스 Service는 Pod가 준비돼야 이름에 주소가 붙습니다. 그래서 edge가 준비되기 전에 뜬 web의 corepack이 연결 거부가 아니라 **이름 풀이 실패**로 끝났고, 컨테이너가 종료됐습니다.
- **준비 확인:** 컨테이너가 종료된 상태를 보면 곧바로 실패로 판단합니다. 그래서 Kubernetes가 컨테이너를 다시 띄우기 전에 실패로 끝났습니다.

### 해결
서비스 Pod마다 busybox init 컨테이너(`until nc -z b-studio-edge 3128; do sleep 1; done`)를 넣었습니다. edge 프록시에 연결될 때까지 기다린 뒤 서비스가 뜹니다. edge Pod에는 넣지 않고, 매니페스트 단위 테스트로 고정했습니다.

### 수정 후 검증
같은 실측 스크립트를 다시 돌리자 web이 **33.9초 만에 준비**됐습니다. 이 시간에는 init 대기, 이미지 적재, 새 Pod의 pnpm 설치, Next 개발 서버 기동이 포함됩니다.

## 21. Kubernetes 미리보기 요청이 3번에 2번꼴로 멈춤

**구분:** Kubernetes 제공자를 kind 클러스터에서 실측하다가 발견 (20번을 고친 뒤)

### 현상
web은 준비됐지만, 제공자가 돌려준 port-forward 주소로 보낸 요청이 **"실패, 실패, 성공"을 규칙적으로 반복**했습니다. 실패는 모두 시간 초과였습니다. web을 다시 띄운 뒤에는 컨테이너가 `running`인데도 준비 확인이 600초 동안 한 번도 통과하지 못했습니다.

### 원인 조사
가설 다섯 개를 차례로 실측해 모두 배제했습니다.

| 가설 | 확인 방법 | 결과 |
|---|---|---|
| port-forward 프로세스가 죽고 새 포트로 다시 열린다 | 요청마다 kubectl 프로세스와 로컬 포트를 기록 | 프로세스와 포트가 그대로라 **아님** |
| 재사용한 keep-alive 연결이 멈춘다 | 매번 새 연결을 여는 `curl`과 연결을 재사용하는 `fetch` 비교 | `curl`도 5번 중 3번 실패해 **아님** |
| edge가 다시 뜬 web의 옛 Pod IP로 연결한다 | 재시작 동안 2초마다 edge Pod 안에서 이름 풀이·직접 연결, EndpointSlice 확인 | 새 IP로 풀리고 직접 연결은 매번 성공, `ready=true`라 **아님** |
| kubectl 클라이언트(v1.30.5)와 클러스터(v1.36.1)의 버전 차이 | 서비스가 준비된 뒤 두 버전으로 각각 port-forward를 새로 열어 10번씩 요청 | 두 버전 모두 10/10이라 **아님** |
| edge가 대상에 연결하지 못한 연결을 RST로 끊는다 | 일반 Pod로 RST(`destroy`)와 FIN(`end`) 두 방식을 재현 | 오류를 겪은 뒤에도 둘 다 20/20이라 **아님** |

실패하는 쪽과 성공하는 쪽의 차이는 결국 **요청의 성격**이었습니다.
- 같은 시점 비교에서 **제공자가 연** port-forward는 4/12, 새로 연 port-forward는 12/12였습니다.
- 제공자가 연 port-forward는 기동하는 동안 준비 확인 요청을 받았습니다. 준비 확인은 1초마다 보내고, 2초가 지나면 클라이언트가 요청을 끊습니다.

그래서 web을 다시 띄우는 50초 동안 port-forward 두 개에 서로 다른 요청을 보냈습니다.

| port-forward | 재시작 중 받은 요청 | 재시작 뒤 12번 요청 | kubectl 에러 출력 |
|---|---|---|---|
| A | 1초마다, 2초에 **끊음** (준비 확인과 같음) | **8/12** | `error creating error stream for port 50878 -> 20000: Timeout occurred` |
| B | 3초마다, 끊지 않음 | 12/12 | 없음 |
| C | 재시작 뒤 새로 엶 | 12/12 | 없음 |

**클라이언트가 중간에 끊은 요청을 받은 kubectl port-forward 프로세스는 계속 살아 있지만, 이후 새 연결에 필요한 에러 스트림을 만들지 못해 일부 요청이 멈춥니다.**

### 해결
준비 확인은 요청을 끊을 수밖에 없고, 브라우저도 페이지를 옮기거나 새로 고칠 때 요청을 취소합니다. 그래서 요청을 끊지 않게 만드는 대신, 망가진 port-forward를 새로 엽니다.
- 기동과 재시작의 준비 확인이 끝나면 port-forward를 **같은 로컬 포트로** 다시 엽니다. 미리보기 주소는 바뀌지 않습니다.
- 그 뒤에도 kubectl이 `error creating error stream` 같은 에러를 내면, 프로세스를 끝내고 같은 포트로 다시 엽니다. 판정 문구는 실측에서 나온 에러 줄로 단위 테스트했습니다.

### 수정 후 검증
같은 실측 스크립트를 다시 돌렸습니다.
- 기동 직후 요청 12번이 **12/12**, 응답은 62~67ms였습니다. 새로 연 port-forward도 같은 로컬 포트(`51422:20000`)라 미리보기 주소가 그대로였습니다.
- web을 다시 띄우자 17.2초 만에 준비됐습니다. 같은 주소에서 바뀐 화면(`marker-v2`)이 나왔고, 재시작 직후 요청 12번도 **12/12**였습니다.

## 23. 스튜디오를 Ctrl+C로 끄면 샌드박스가 남음

**구분:** 세션 복구를 실측하다가 발견. 세션 복구 이전부터 있던 스튜디오 종료 처리의 문제입니다

### 현상
세션 복구 실측의 마지막 단계에서 `pnpm --filter @b-studio/studio dev` 프로세스 그룹에 SIGINT를 보냈습니다. 터미널에서 Ctrl+C를 누를 때와 같은 조건입니다.
- 스튜디오는 2초 안에 끝났습니다.
- 샌드박스의 컨테이너 4개, 볼륨 4개, 네트워크 2개가 그대로 남았습니다.
- 세션 파일도 `ready` 상태였습니다.

스튜디오의 종료 처리는 신호를 받으면 세션마다 `docker compose down`으로 샌드박스를 지운 뒤 끝내도록 되어 있었습니다. README 검증 결과의 Ctrl+C 항목은 tsx로 실행한 CLI에서 확인한 것이라, 웹 스튜디오에서는 이 경로를 확인한 적이 없었습니다.

### 원인
Next.js 16.3.4 소스에서 두 가지를 확인했습니다.
- `next dev` 부모 프로세스(`cli/next-dev.js`)는 신호를 받으면 자식 서버 프로세스에 넘기고, `NEXT_EXIT_TIMEOUT_MS`(기본 100ms)가 지나면 자식을 SIGKILL합니다.
- 자식 서버(`server/lib/start-server.js`)도 SIGINT·SIGTERM 처리기를 등록해, 서버를 닫고 나면 `process.exit(130)`을 부릅니다.

스튜디오의 처리기는 샌드박스마다 1초 남짓 걸리는 `compose down`을 기다립니다. 그래서 정리가 끝나기 전에 프로세스가 사라졌습니다.

### 해결
정리가 끝나기를 기다리지 않습니다.
- 신호를 받으면 제공자가 돌려주는 정리 명령을 `detached`로 새 프로세스 그룹에 띄웁니다. 명령은 Docker는 `docker compose --project-name <id> down --volumes --remove-orphans`, Kubernetes는 네임스페이스 삭제입니다.
- 터미널의 Ctrl+C는 전경 프로세스 그룹에만 전달되고, 부모 프로세스가 강제 종료돼도 자식은 함께 끝나지 않습니다. 그래서 이 명령은 스튜디오가 끝난 뒤에도 끝까지 실행됩니다.
- 마지막 세션 상태는 동기식으로 기록합니다. 상태는 중지로 바꾸지 않습니다. 정리 명령이 실패해도 다음 실행의 복구([ADR-029](decisions.md#adr-029-세션-복구-세션-상태를-작업-복사본에-남기고-새-샌드박스로-이어서-작업한다))가 다시 정리합니다.

### 수정 후 검증
같은 조건(프로세스 그룹에 SIGINT)으로 다시 확인했습니다.
- 스튜디오는 신호를 받고 59ms 만에 끝났습니다.
- 신호를 보낸 뒤 771ms 만에 샌드박스의 컨테이너·볼륨·네트워크가 모두 0개가 됐습니다.
- 세션 파일은 `ready` 상태로 남았고, 기록한 프로세스는 이미 끝나 있었습니다.
- 스튜디오를 다시 켜자 뜬 지 1.7초 만에 세션이 "이전 샌드박스를 정리했습니다"와 함께 중지 상태로 표시됐습니다.

## 24. 복구한 세션 화면이 아직 진행 중인 것처럼 보임

**구분:** 세션 복구를 실제 브라우저(Playwright)로 확인하다가 발견. API 기반 실측 27개 항목은 모두 통과한 뒤였습니다

### 현상
복구한 세션 페이지에서 세 가지가 실제 상태와 달랐습니다.
- 샌드박스가 없는데 헤더의 서비스가 "빌드 중"이었습니다. 미리보기도 "처음 시작할 때는 의존성을 내려받느라 몇 분 걸릴 수 있습니다"라고 안내했습니다.
- 강제 종료로 끊긴 요청의 검증 게이트가 "확인 중"으로 남았습니다. 바로 아래에는 "오류: 스튜디오 서버가 멈춰 끝내지 못했습니다"가 표시돼 있었습니다.
- 헤더에서 샌드박스를 중지한 뒤에도 서비스 옆에 마지막으로 잰 메모리 사용량(379MiB / 1.00GiB)이 남았습니다.

### 원인
- **서비스 상태**: 서비스 상태 타입에 "실행하지 않음" 값이 없어, 복구한 스냅샷의 서비스를 `starting`으로 채웠습니다. 같은 프로세스에서 중지할 때도 서비스 상태를 바꾸지 않았습니다. 게다가 화면의 `service` 이벤트 처리는 주소가 비어 오면 이전 주소를 그대로 둡니다.
- **게이트**: 게이트 항목은 `verify_start` 이벤트로 생기고 `verify_result` 이벤트로 결과가 채워집니다. 결과 이벤트가 오기 전에 요청이 끝나면 채워질 기회가 없습니다. 요청이 도중에 예외로 끝나도 같은 일이 생깁니다.
- **사용량**: 헤더는 몇 초마다 받는 사용량을 서비스 상태와 관계없이 표시했습니다.

### 해결
- 서비스 상태에 `stopped`를 추가했습니다. 복구한 세션과 중지한 세션의 서비스는 주소를 지우고 "중지됨"(회색)으로 표시합니다. 미리보기는 이어서 작업하라고 안내합니다.
- 요청이 끝날 때(`run_finished`) 결과가 없는 게이트와 도구 호출을 "중단됨"으로 확정합니다. 서버 이벤트 형식은 바꾸지 않았으므로, 이미 저장된 기록을 재생해도 같은 결과가 나옵니다. 두 동작 모두 리듀서 단위 테스트로 고정했습니다.
- 중지된 서비스에는 사용량을 표시하지 않습니다.

### 수정 후 검증
같은 세션 페이지를 다시 열어 확인했습니다.
- 서비스 web·api는 "중지됨"으로, 미리보기는 "샌드박스가 없어 미리보기를 열 수 없습니다"로 보였습니다. 끊긴 게이트는 "검증 게이트 중단됨"으로 표시됐습니다.
- "이어서 작업" 버튼으로 새 샌드박스를 띄우자 헤더가 "준비됨"이 되고 메모리 사용량이 표시됐습니다.
- 이어서 "샌드박스 중지" 버튼을 누르자 컨테이너·볼륨·네트워크가 0개가 되고, 서비스는 주소 없이 "중지됨"이 됐습니다.
- 중지된 서비스에 사용량이 표시되지 않는 것은 사용량을 숨기는 수정을 넣고 페이지를 다시 연 뒤 확인했습니다.

## 25. 새 폴더에 만든 파일을 게이트가 옛 코드로 통과시킴

**구분:** 원격 변경 가져오기를 실측하다가 발견. [5번](#5-검증-게이트가-컴파일-에러가-있는-코드를-준비-완료로-통과시킴)에서 고친 반영 확인이 놓친 경우입니다

### 현상
원격 변경 가져오기 실측에서 데모 요청 1(주문 목록 API)이 **첫 게이트에서 바로 통과**했습니다. 이 요청은 일부러 오타(`return customerNam;`)를 넣었으므로 첫 게이트에서 실패해야 합니다.
- 게이트 결과는 "파일 반영 확인 0.2초, api 재시작 후 준비 완료, api 계약 변경 없음"이었습니다. 새 API를 추가했는데 계약이 그대로였으니, 5번 때처럼 옛 코드가 떠 있었던 것입니다.
- 오타가 든 파일은 체크포인트 `3413c10`으로 커밋돼 원격 브랜치에도 올라갔습니다.
- 다음 요청과 원격 변경 가져오기에서 api를 다시 띄우자 그제서야 `CustomerOrder.java:29: error: cannot find symbol`로 실패했습니다.

앞선 세션 복구 실측에서는 같은 요청이 첫 게이트에서 제대로 실패했습니다. 매번 재현되는 문제는 아니었습니다.

### 원인
5번의 반영 확인은 파일마다 **그 파일이 든 폴더의 목록**에 이름이 보이는지와 내용 해시만 확인했습니다.
- 요청 1은 새 폴더 `orders/`에 파일을 만듭니다.
- 새 폴더의 목록은 처음 읽는 것이라 바로 보입니다.
- 빌드 도구는 `src/main/java`부터 목록을 따라 내려가므로, **상위 폴더 목록에 `orders`가 보여야** 새 파일을 찾습니다.

같은 colima 마운트에서 실측했습니다. 오래 떠 있는 컨테이너가 목록을 한 번 읽어 캐시를 채운 뒤, 호스트에서 새 폴더와 파일을 만들고 0.3초 간격으로 확인했습니다.

| 확인 | 1회 | 2회 |
|---|---|---|
| 새 컨테이너에서 파일이 든 폴더 목록 (기존 반영 확인) | 0.3초 | 0.3초 |
| 새 컨테이너에서 상위 폴더 목록에 새 폴더가 보임 | 19.0초 | 18.5초 |
| 캐시를 채운 컨테이너에서 상위 폴더 목록에 새 폴더가 보임 | 19.0초 | 18.5초 |
| 캐시를 채운 컨테이너에서 `find`로 파일을 찾음 | 19.1초 | 18.6초 |

- 기존 확인은 0.3초 만에 통과했지만, 빌드 도구가 새 파일을 찾기까지는 약 19초가 걸렸습니다.
- 확인용으로 새로 띄운 컨테이너도 같은 캐시를 봅니다.
- 게이트가 그 사이에 api를 재시작하면 Gradle은 옛 소스 목록을 보고 바뀐 것이 없다고 판단해, 이전 클래스로 앱을 띄웁니다.
- 앞선 실측에서 잡혔던 것은, 기동 뒤 캐시가 만료되는 시점과 요청 사이의 간격이 달랐기 때문으로 보입니다. 이 시점을 맞춰 재현해 보지는 않았습니다.

### 해결
- 반영 확인 스크립트가 파일 경로의 **모든 상위 폴더 목록**에 다음 경로 이름이 보일 때까지 기다리게 했습니다.
- 스크립트를 한 곳에 모았습니다. 옛 목록을 돌려주는 가짜 `ls`로 "새 폴더 목록에는 보이지만 상위 폴더 목록에는 없는" 경우를 단위 테스트로 고정했습니다.
- Kubernetes 제공자는 파일이 있는지만(`[ -e ]`) 확인하고 있었습니다. 같은 스크립트를 파드 안의 절대 경로에 쓰도록 바꿨습니다. kind 클러스터에서는 다시 실측하지 않았습니다.

### 수정 후 검증
같은 원격 변경 가져오기 실측을 다시 실행했습니다(세션 기동 직후 요청 1).
- **첫 게이트**: 반영 확인이 **13.3초** 동안 상위 폴더 목록을 기다린 뒤 재시작했습니다. api가 오타로 컴파일에 실패해 게이트가 실패했습니다.
- **고친 뒤 게이트**: 반영 확인이 0.2초 만에 끝났고, 계약 비교에 `GET /api/orders` 추가와 `OrderResponse` 추가가 나타났습니다. 새 코드가 실제로 떠 있었다는 뜻입니다.
- **기록**: 체크포인트에는 고친 코드만 남았고, 이어진 요청 2도 정상적으로 체크포인트를 남겼습니다.

## 26. 되돌리기로 폴더가 통째로 사라지면 web이 Turbopack 오류로 종료됨

**구분:** 요청 취소를 실측하다가 발견. [13번](#13-되돌린-뒤-api가-지운-파일을-찾다가-기동하지-못함)·[25번](#25-새-폴더에-만든-파일을-게이트가-옛-코드로-통과시킴)과 같은 파일 공유 목록 지연이, 폴더를 지우는 쪽에서 드러난 경우입니다

### 현상
요청 취소 실측의 두 번째 실행에서, 게이트가 서비스를 다시 띄우는 중에 데모 요청 1을 취소했습니다. 되돌리기가 요청이 만든 파일 5개를 지우고 web과 api를 다시 띄웠는데, web이 기동하지 못했습니다.

```
FATAL: An unexpected Turbopack error occurred.
Error [TurbopackInternalError]: reading directory item in "/app/app/orders"
Caused by:
- No such file or directory (os error 2)
```

- 요청 1은 새 폴더 `web/app/orders/`에 화면을 만들고, 되돌리기는 이 폴더를 통째로 지웁니다.
- 같은 실측의 첫 번째 실행에서는 web이 정상적으로 떴습니다. 매번 나는 문제는 아니었습니다.
- api는 [13번](#13-되돌린-뒤-api가-지운-파일을-찾다가-기동하지-못함)의 조건부 재시도로 한 번 더 재시작해 준비됐습니다. web은 로그에 지운 **파일 이름**이 아니라 **폴더 경로**가 나와 재시도 대상이 아니었습니다.

### 원인: 반영 확인이 지운 폴더를 보지 않았다
[25번](#25-새-폴더에-만든-파일을-게이트가-옛-코드로-통과시킴)에서 고친 반영 확인은 파일마다 모든 상위 폴더의 목록을 봅니다. 지운 파일에서는 이 확인이 너무 일찍 끝났습니다.
- `web/app/orders/page.tsx`를 확인할 때 `web/app/orders` 폴더가 이미 없어 목록 읽기가 실패하고, 곧바로 "파일 없음"으로 통과합니다.
- 하지만 `web/app` 목록에는 지운 `orders`가 한동안 남습니다. 새로 뜬 web의 Turbopack은 `app` 목록을 따라 라우트를 찾다가 `orders`를 읽으려 하고, 실제로는 없어서 종료합니다.

같은 제공자 경로로 따로 재현했습니다.
- 샌드박스를 띄워 새 폴더에 화면을 만들고 web에 반영했습니다.
- 호스트에서 그 폴더를 지우고, 반영 확인이 끝나자마자 web을 다시 띄웠습니다.
- 동시에 새 컨테이너를 띄워 0.3초마다 `web/app` 목록을 확인했습니다.

| 시도 | 반영 확인 통과 | 상위 폴더 목록에서 사라짐 | 곧바로 다시 띄운 web |
|---|---|---|---|
| 1 | 0.19초 | 15.2초 | 준비됨 |
| 2 | 1.4초 | 15.9초 | **Turbopack 오류로 종료** |
| 3 | 0.14초 | 15.8초 | 준비됨 |

반영 확인은 0.1~1.4초에 끝났지만, 새 컨테이너가 보는 상위 폴더 목록에는 지운 폴더가 15~16초 동안 남았습니다. 그 사이에 web을 띄우면 Turbopack이 목록을 읽는 시점에 따라 실패합니다.

### 해결
- 반영 확인 대상에 **지운 파일과 함께 사라진 폴더**를 더합니다. 호스트에서 없어진 상위 폴더를, 남아 있는 폴더를 만날 때까지 거슬러 올라가며 모읍니다.
- 폴더는 내용 해시를 구할 수 없으므로, 상위 목록에 남아 있는 동안에는 "파일 없음"이 되지 않습니다. 목록에서 사라져야 통과합니다.
- 옛 목록을 흉내 내는 가짜 `ls`로 "폴더 안의 파일은 없음으로 보이지만 폴더는 아직 상위 목록에 있음"을 단위 테스트로 고정했습니다.
- Kubernetes 제공자도 같은 대상 목록을 씁니다. kind 클러스터로는 다시 실측하지 않았습니다.

### 수정 후 검증
같은 재현을 고친 코드로 세 번 다시 실행했습니다.

| 시도 | 반영 확인 통과 | 상위 폴더 목록에서 사라짐 | 곧바로 다시 띄운 web |
|---|---|---|---|
| 1 | 15.6초 (확인 40번) | 15.4초 | 준비됨 |
| 2 | 15.6초 (확인 41번) | 15.5초 | 준비됨 |
| 3 | 15.3초 (확인 39번) | 15.5초 | 준비됨 |

- 반영 확인이 상위 목록에서 폴더가 사라질 때까지 기다린 뒤 통과했고, 세 번 모두 web이 준비됐습니다.
- 목록 확인은 0.3초 간격에 컨테이너 기동 시간이 더해지므로, 3번처럼 반영 확인이 조금 먼저 끝난 것으로 기록되기도 합니다.
- 대가로 폴더를 지우는 되돌리기는 약 15초 더 걸립니다. 서비스가 실패한 뒤 다시 띄우는 것보다 한 번에 뜨는 쪽을 택했습니다.

## 27. 요청을 취소하면 게이트 실패가 한 번 기록됨

**구분:** 요청 취소를 실측하다가 발견

### 현상
게이트가 서비스를 다시 띄우는 중에 요청을 취소하는 실측이 확인 항목 14개 중 13개만 통과했습니다. 실패한 항목은 "끊긴 게이트는 결과 없이 끝남"이었습니다. 세션 파일의 기록 순서는 다음과 같았습니다.

| 순서 | 이벤트 |
|---|---|
| 18 | 게이트 시작 |
| 19 | 취소 중 |
| 20 | **게이트 결과: 실패** |
| 21 | 되돌림 |
| 22 | 요청 끝: 취소 |

화면은 이 기록을 그대로 그리므로, 사용자가 취소한 요청에 "검증 게이트 실패"가 먼저 쌓인 뒤 취소로 끝납니다. 에이전트가 만든 코드가 틀린 것처럼 보이게 됩니다.

### 원인
서비스 재시작 결과를 모으는 `restartOnce`가 모든 오류를 "재시작 실패"로 바꿨습니다.
- 취소 신호로 끊긴 `docker compose up`도 실패로 기록했습니다.
- 실패 원인을 알려 주려고 컨테이너 사용량과 최근 로그까지 모았습니다.
- 게이트는 이 보고서를 받아 결과 이벤트를 보냈습니다.

### 해결
- 신호가 중단된 뒤의 오류는 재시작 실패로 바꾸지 않고 그대로 던집니다. 로그도 모으지 않습니다.
- 게이트는 확인이 끝난 뒤 신호를 한 번 더 봅니다. 계약 조회처럼 오류를 결과로 바꾸는 단계에서 끊긴 경우도 보고하지 않기 위해서입니다.
- 가짜 샌드박스로 "재시작 중 취소하면 결과 이벤트가 없다"와 "로그를 읽지 않는다"를 테스트로 고정했습니다.

### 수정 후 검증
같은 실측을 다시 실행하자 끊긴 게이트의 결과 이벤트가 0개였습니다.

이 수정으로 새 문제가 하나 드러났습니다.
- 취소 요청을 곧바로 한 번 더 보내면 409("취소할 수 있는 요청이 없습니다")가 돌아왔습니다.
- 전에는 게이트가 로그를 모으는 동안 요청이 붙어 있어서 가려져 있었습니다. 게이트가 바로 멈추자 되돌리기에 들어가기 전에 요청이 세션에서 떨어졌습니다.
- 사용자가 취소한 요청이면 되돌리는 동안에도 붙여 두고, 요청이 끝날 때 떼도록 고쳤습니다.

| 실행 | 끊긴 게이트의 결과 이벤트 | 연달아 보낸 취소 두 번 |
|---|---|---|
| 수정 전 | 1개 (실패) | 202, 202 |
| 게이트 수정 후 | 0개 | 202, **409** |
| 요청을 되돌리는 동안 붙여 둔 뒤 | 0개 | 202, 202 |

## 28. 큰 파일을 열면 코드 강조가 화면을 1초 넘게 멈춤

**구분:** 문법 강조를 브라우저로 실측하다가 발견. 원인을 두 번 잘못 짚은 뒤 성능 트레이스로 확정

### 현상
코드 탭에서 파일을 연 직후의 가장 긴 작업(Long Task)을 줄 수별로 쟀습니다. 파일은 줄마다 80자, 토큰 15개인 조밀한 TSX입니다. 스튜디오는 사용자가 실행하는 방식과 같은 `next dev`로 띄웠고, 비교를 위해 같은 내용의 `.txt` 파일(강조하지 않음)도 열었습니다.

| 줄 수 | 평문(`.txt`) | 강조 |
|---|---|---|
| 500 | 50ms 미만 | 462ms |
| 1,000 | 71ms | 849ms |
| 1,500 | 95ms | 1,161ms |

평문 줄을 그리는 비용은 0.1초 미만이었고, 강조를 켜자 1,500줄에서 1초 넘게 입력이 막혔습니다.

### 가설과 검증: 두 번 잘못 짚었다

| 가설 | 실험 | 1,500줄의 가장 긴 작업 | 판단 |
|---|---|---|---|
| 토큰마다 만드는 `<span>`이 너무 많다 | 색이 같은 이웃 토큰과 공백을 합쳐 요소를 22,500개에서 16,500개로 줄임 | 1,163ms | 원인 아님 |
| 토큰마다 넣는 인라인 CSS 변수가 느리다 | 색 조합마다 CSS 클래스를 하나만 만들어(규칙 7개) 인라인 스타일을 0개로 줄임 | 1,226ms | 원인 아님 |
| 토큰화 자체가 느리다 | `performance.measure`로 토큰화만 잼 | 토큰화 580ms (500줄 191ms, 1,000줄 387ms) | 절반 정도만 설명함 |

### 원인: 성능 트레이스로 확정
Chrome 성능 트레이스로 1,500줄 파일을 열 때의 작업을 나눴습니다.
- 가장 긴 작업(1,263ms)은 거의 전부 JavaScript 실행(`v8.run` 1,262ms)이었고, 그 안에 토큰화가 들어 있었습니다.
- 스타일 계산(72ms)과 레이아웃(44ms)은 다른 작업에서 짧게 끝났습니다.

요소 수나 CSS가 아니라, **파일 전체를 한 작업에서 토큰화하고 그 결과를 한 번에 렌더링하는 것**이 화면을 막고 있었습니다. 줄 수에 비례해 길어지므로 줄 수 제한으로는 근본적으로 해결되지 않습니다.

### 해결
- 100줄씩 나눠 토큰화하고, 조각을 끝낼 때마다 그 줄까지 화면에 반영한 뒤 `setTimeout`으로 브라우저에 차례를 넘깁니다.
- 조각마다 Shiki가 돌려주는 문법 상태(`grammarState`)를 다음 조각에 넘깁니다. 조각 경계를 넘는 여러 줄 주석과 템플릿 문자열이 든 1,505줄에서, 나눠 강조한 결과가 한 번에 강조한 결과와 토큰·색까지 같음을 Node로 확인했고 단위 테스트로 고정했습니다.
- 이미 그린 줄은 다시 그리지 않도록 줄 컴포넌트를 `memo`로 둡니다.
- 파일이 바뀌면 남은 조각을 멈춥니다. 2,000자가 넘는 줄(압축한 코드)은 토큰화하지 않습니다.
- 앞의 두 실험(토큰 합치기, CSS 클래스)은 요소 수와 인라인 스타일을 줄이므로 그대로 두었습니다.
- 2,000줄이 넘으면 강조하지 않던 제한은 없앴습니다.

### 수정 후 검증

| 줄 수 | 가장 긴 작업 (전 → 후) | 끝까지 강조 (전 → 후) | 첫 조각이 보이기까지 |
|---|---|---|---|
| 500 | 462ms → 109ms | 0.73초 → 0.60초 | 0.45초 |
| 1,000 | 849ms → 90ms | 1.24초 → 0.98초 | 0.42초 |
| 1,500 | 1,161ms → 103ms | 1.75초 → 1.57초 | 0.48초 |
| 2,500 | 강조하지 않음 → 115ms | 2.89초 | 0.55초 |

- 입력을 막는 가장 긴 작업이 약 0.1초로 줄었고, 끝까지 강조하는 시간도 줄었습니다.
- 새로 연 페이지에서 콘솔 오류와 경고는 0개였습니다.

### 배운 점
- 요소 수와 CSS를 줄이는 두 실험이 모두 효과가 없었습니다. 추측으로 최적화하기 전에 트레이스부터 받았어야 했습니다.
- 기준을 함께 재야 합니다. 같은 내용의 평문 파일로 렌더링 비용이 작다는 것을 먼저 확인하고 나서야, 비용이 강조 쪽에 있다는 것을 좁힐 수 있었습니다.

## 29. 내 폴더에서 IDE로 만든 새 화면이 미리보기에 뜨지 않음

**구분:** 내 폴더 세션을 실제 Docker(colima `vz`, `mountType: sshfs`, `mountInotify: true`)로 검증하다가 발견

### 현상
- 내 폴더 세션에서 IDE가 하듯 호스트에서 `web/app/ide-check/page.tsx`(새 폴더와 새 파일)를 만들었습니다.
- 180초 동안 미리보기의 `/ide-check`가 뜨지 않았습니다.
- 같은 세션에서 에이전트가 만든 `/orders` 화면은 떴습니다. 에이전트 요청은 검증 게이트가 서비스를 다시 띄우기 때문입니다.

### 원인 조사
1. **컨테이너가 받는 변경 알림.** busybox `inotifyd`로 바인드 마운트한 폴더를 감시하면서 호스트에서 파일을 바꿨습니다.

| 호스트에서 한 일 | 컨테이너가 받은 알림 | 컨테이너에서 보이기까지 |
|---|---|---|

   내용은 바로 보였지만, colima는 호스트의 수정만 속성 변경으로 전달하고 **생성은 전달하지 않았습니다.**

2. **Next 개발 서버에서 확인.** `studio up`으로 orders 예제를 띄우고, 호스트에서 바꾼 뒤 미리보기 응답을 0.25~0.5초 간격으로 확인했습니다. 세 번에 나눠 쟀고, 매번 새 샌드박스로 시작했습니다.

| 호스트에서 한 일 → 컨테이너 안에서 한 일 | 결과 |
|---|---|
| 기존 `app/page.tsx` 수정 (두 번) → 없음 | 0.58초, 0.59초 뒤 반영 |
| 새 폴더 `app/hmr-new/page.tsx` → 없음 | 45초 동안 404 |
| 이어서 → 새 파일과 상위 폴더를 `touch` | 30초 동안 404 |
| 이어서 → 새 폴더를 옆 이름으로 옮겼다가 되돌림 | 0.72초 뒤 200 |
| 다른 새 폴더 → 만들자마자 옮겼다가 되돌림 | 명령 0.05초, 그 뒤 0.29초에 200 |
| 또 다른 새 폴더 → 부모 폴더에 숨긴 임시 폴더를 만들었다 지움 | 20초 동안 404 |
| 이미 있던 폴더에 새 `page.tsx` → 그 폴더에 임시 폴더를 만들었다 지움 | 0.55초 뒤 200 |
| 화면 파일 삭제 → 없음 | 20초 동안 200. 컨테이너가 삭제를 보기까지 20.2초·20.9초 |
| 화면 파일 삭제 → 곧바로 부모 폴더에 임시 폴더를 만들었다 지움 | 0.33초 뒤 404 |

   - 새 폴더는 컨테이너 안에서 옮겨야 개발 서버가 찾았습니다. 폴더 목록을 다시 읽게 하는 것만으로는 찾지 못했습니다.
   - 새 파일과 지운 경로는 부모 폴더에서 임시 폴더를 만들었다 지우면 바로 반영됐습니다. 컨테이너가 삭제를 볼 때까지(17~21초) 기다릴 필요도 없었습니다.
   - 지운 파일 자리에 같은 이름의 폴더를 잠깐 만들면 web이 종료되므로, 사용자 경로의 이름을 빌리는 방식은 새 폴더 이동에만 씁니다.
   - Turbopack이 내부에서 어떤 알림으로 경로를 다시 읽는지까지는 추적하지 않았습니다.

### 해결
- 스튜디오의 폴더 감시(`fs.watch`)가 만들기·지우기·이름 바꾸기로 알린 경로를 모으고, 호스트에서 새 폴더·새 파일·지운 경로로 나눕니다.
- 샌드박스 제공자의 `relayChanges`가 compose 설정의 바인드 마운트로 그 경로를 마운트한 서비스와 컨테이너 안 경로를 찾아, 그 컨테이너에서 알림을 만듭니다.
  - **새 폴더:** 옆 이름(`.b-studio-relay-…`)으로 옮겼다가 되돌립니다.
  - **새 파일, 지운 파일·폴더:** 부모 폴더에 숨긴 임시 폴더를 만들었다 지웁니다. 사용자 파일은 건드리지 않습니다.
  - 경로는 셸 문자열에 넣지 않고 위치 인자로 넘깁니다.
- 안전장치:
  - 마운트 폴더 자체와 그 상위 폴더는 옮기지 않습니다. 옮기면 서비스의 마운트가 흔들립니다.
  - 옮기는 새 폴더 안의 경로와 지운 폴더 안의 경로는 따로 알리지 않고, 같은 부모 폴더에는 한 번만 알립니다.
  - 옮겼다 되돌린 폴더가 다시 변경 알림으로 돌아오므로, 5초 안에 옮긴 폴더는 다시 옮기지 않습니다.
  - 옮긴 사이에 같은 이름이 다시 생기면 덮어쓰지 않고 옆 이름으로 남깁니다.
  - 요청·되돌리기를 처리하는 중에는 알리지 않습니다. 게이트의 반영 확인이 옮기는 순간의 파일을 놓칠 수 있고, 그때는 게이트가 서비스를 다시 띄워 반영하기 때문입니다.
  - 체크포인트를 남기기 전에 진행 중인 알림이 끝나기를 기다립니다. 임시 이름은 체크포인트 저장소(`info/exclude`)와 코드 화면에서 뺍니다.
- 알린 경로는 로그 탭에 `[b-studio] 폴더에서 만들거나 지운 경로를 개발 서버에 알렸습니다`로 남깁니다.
- 폴링(`watchOptions.pollIntervalMs`)은 쓰지 않았습니다. 19번에서 폴링을 켜면 페이지가 404가 되고 대기 중 CPU를 16.73% 쓰는 것을 확인했기 때문입니다.

### 수정 후 검증
내 폴더 세션 실검증(README의 "내 폴더에서 바로 작업")에서 IDE가 하듯 호스트에서 파일을 쓰고 지웠습니다. 이 동안 web 재시작 이벤트는 0번이었고, 컨테이너는 계속 실행 중이었습니다.

| IDE에서 한 일 | 미리보기 반영 |
|---|---|
| 새 화면 폴더 `web/app/ide-check/page.tsx` | 1.00초 (수정 전에는 180초 동안 뜨지 않음) |
| 그 화면을 다시 고침 | 0.36초 |
| 화면 파일만 지움 | 0.92초 뒤 404 |
| 지운 파일을 다시 만듦 | 0.94초 |
| 화면 폴더를 통째로 지움 | 0.92초 뒤 404 |

### 배운 점
- "컨테이너에서 파일이 보인다"와 "개발 서버가 알아챈다"는 다릅니다. 게이트의 반영 확인(5·25번)은 보이는지를 확인하지만, 요청 밖의 IDE 수정은 알림에 기대므로 따로 재야 했습니다.
- 알림 계층을 busybox로 먼저 좁히고 Next에서 방법마다 쟀습니다. 그래서 한 가지 방법으로 모두 처리하려다 web을 죽이는 방식(지운 파일 자리에 같은 이름 폴더)을 기능에 넣기 전에 걸러 냈습니다.

## 30. 답변의 표에서 긴 경로가 다른 열을 대화 밖으로 밀어냄

**구분:** 질문 모드 화면을 브라우저(Playwright, 1440×900)로 확인하다가 발견

### 현상
- 데모 질문의 답에 `| 위치 | 변경 |` 표가 있었습니다.
- 첫 열에 `api/src/main/resources/db/migration/V2__add_order_memo.sql` 같은 긴 경로가 들어가자, 대화 폭 안에서 둘째 열(변경)이 보이지 않아 가로로 스크롤해야 했습니다.
- 행 높이도 내용보다 크게 늘어났습니다. 둘 다 스크린샷으로 확인했습니다.

### 원인
- 답변 전체에 `overflow-wrap: break-word`(`break-words`)를 두고 있었습니다.
- MDN에 따르면 `break-word`는 줄바꿈 기회를 **min-content 크기 계산에 넣지 않습니다.** 반면 `anywhere`는 넣습니다.
- 그래서 자동 표 레이아웃이 긴 경로 한 칸의 폭을 그 열의 최소 폭으로 잡았고, 표가 대화 폭보다 넓어졌습니다.

### 해결
- 표 셀(`th`, `td`)에 `overflow-wrap: anywhere`를 두고, 표를 대화 폭에 맞췄습니다(`w-full`).
- 표를 감싼 가로 스크롤은 아주 긴 표를 위해 그대로 둡니다.

### 수정 후 검증
같은 데모 질문의 답을 같은 화면 크기로 쟀습니다.
- 표를 감싼 영역의 폭은 392px, 스크롤 폭도 392px로 넘치지 않았습니다.
- 두 열은 232px, 159px이고, 둘째 열이 영역 안에 보였습니다.
- 행 높이는 49~69px였습니다.

## 31. 운영 이미지의 web에서 /api 요청이 404가 됨

**구분:** 운영 배포(ADR-043)를 설계하면서 미리 확인. Next.js 문서에서 답을 찾지 못해 이미지를 두 벌 만들어 쟀습니다

### 현상
- 템플릿의 `next.config.ts`는 `API_BASE_URL` 환경 변수가 있을 때 `/api/:path*`를 백엔드로 넘기는 `rewrites`를 만듭니다.
- 개발 서버는 설정 파일을 실행 중에 읽으므로, compose `environment`에 값을 두면 동작합니다.
- 운영 이미지는 `next build`의 standalone 서버만 실행합니다. 이때 실행할 때만 넣은 값으로 `rewrites`가 동작하는지는 알 수 없었습니다.

### 원인 확인
가짜 백엔드(Caddy `respond`)를 같은 네트워크에 두고, orders 예제 web으로 이미지를 두 벌 만들어 `/api/ping`을 요청했습니다.

| 이미지 | 실행할 때 `API_BASE_URL` | `/api/ping` | `.next/routes-manifest.json`의 rewrites |
|---|---|---|---|
| 빌드 인자 없이 빌드 | 있음 | 404 (Next의 404 페이지) | 비어 있음 |
| `--build-arg API_BASE_URL=...`로 빌드 | 없음 | 200, 가짜 백엔드 응답 | `/api/:path*` 규칙이 들어 있음 |

`rewrites`는 빌드할 때 계산돼 매니페스트에 기록되고, standalone 서버는 실행할 때 넣은 환경 변수로 다시 계산하지 않았습니다.

### 해결
- 운영 Dockerfile의 빌드 단계에 `ARG API_BASE_URL`을 선언했습니다.
- 배포기는 Dockerfile이 `ARG`로 선언한 이름 중 compose `environment`에 값이 있는 것만 빌드 인자로 넘깁니다(`buildArgsFor`).
  - 개발용 compose에 같은 값을 두 번 적지 않아도 됩니다.
  - 선언하지 않은 환경 변수(DB 비밀번호 등)는 이미지 빌드 기록에 들어가지 않습니다.
- 실제 배포 검증에서 운영 주소의 web `/api/orders`가 200으로 api의 주문 목록을 돌려주는 것을 확인했습니다.

## 32. 스튜디오 standalone 결과물에 예제 프로젝트와 소스·테스트 파일이 들어감

**구분:** 스튜디오 컨테이너 이미지(ADR-044)를 만들면서 빌드 경고와 결과물을 확인하다가 발견

### 현상
- `output: "standalone"`을 켜고 `next build`를 하자 Turbopack 경고 "Dynamic filesystem access causes tracing of the whole project"가 10건 나왔습니다.
  - 위치: `projects.ts` 5곳, `sessions.ts` 1곳, `packages/agent/src/workspace.ts` 1곳, `packages/sandbox/src/docker/deploy.ts` 3곳
- 빌드는 성공했지만 `.next/standalone`(65MB)에 서버 실행에 필요 없는 파일이 들어 있었습니다.
  - `examples/orders` 폴더
  - `apps/studio`의 `app`, `components`, `lib` 원본, `Dockerfile`, `tsconfig.json`
- 결과물을 둔 채 `pnpm test`를 돌리자 결과물 안의 테스트 복사본까지 실행돼 39개 파일(325개)로 셌습니다. 원래는 35개 파일(287개)입니다.

### 원인 확인
- 경고가 가리킨 곳은 모두 실행할 때 정해지는 경로로 파일에 접근합니다.
  - 프로젝트 폴더(`B_STUDIO_PROJECTS_DIR`, 기본값 `process.cwd()/../../examples`)
  - 세션·배포 상태 폴더, 샌드박스 작업 폴더의 `realpath`, 운영 Dockerfile 읽기
- 정적 분석으로는 경로를 알 수 없어, Turbopack이 추적 기준 폴더 전체를 서버 파일로 넣었습니다. 경고 안내에 "경로를 하위 폴더로 고정하거나, 호출에 `/*turbopackIgnore: true*/`를 붙이라"고 나옵니다.

### 해결
1. 경고가 가리킨 호출의 경로 인자에 `/*turbopackIgnore: true*/`를 붙였습니다.
   - 경고가 0건이 됐고 `examples/`가 결과물에서 빠졌습니다.
   - 하지만 `components`와 `lib` 원본(테스트 파일 포함)은 남았습니다. 페이지의 추적 파일(`page.js.nft.json`)에 `node_modules` 밖의 파일이 49개 있었습니다.
2. 서버 코드는 번들 조각에 들어가 원본이 필요 없으므로, `outputFileTracingExcludes`로 모든 경로(`/*`)에서 `./components/**/*`, `./lib/**/*`를 뺐습니다.
   - `apps/studio`에는 `server.js`, `package.json`, `.next`, `node_modules`만 남았습니다. `node_modules` 밖의 `.ts`·`.tsx`는 0개입니다.
   - 크기는 63MB로 크게 줄지 않았습니다. 결과물 대부분이 `node_modules`(57MB)이기 때문입니다.
3. 결과물의 `server.js`를 직접 띄워 `/api/health`, `/api/projects`, `/`가 모두 정상으로 응답하는 것을 확인했습니다.

## 33. 컨테이너로 띄운 스튜디오가 세션을 만들지 못함 ("not in a git directory")

**구분:** 스튜디오 이미지를 실제 Docker(colima)에서 띄워 세션을 만드는 검증에서 발견 → 재현 후 수정

### 현상
- 이미지는 healthy가 됐고 `/api/projects`도 orders를 돌려줬습니다.
- 그런데 세션을 만드는 요청은 400으로 실패했습니다. 오류는 `git config 실패: fatal: not in a git directory`였습니다.
- 세션 폴더에는 복사된 파일과 `.git`이 이미 만들어져 있었습니다. 저장소가 없어서 난 실패가 아니었습니다.

### 원인 확인
같은 이미지를 새 컨테이너로 띄우고, 세션 폴더와 같은 마운트 경로에서 명령을 하나씩 실행했습니다.

| 위치 | 결과 |
|---|---|
| 마운트한 폴더에서 `git init` 후 `git config` | exit 128, `fatal: not in a git directory` |
| 같은 폴더에서 `git status` | `fatal: detected dubious ownership in repository` |
| 컨테이너 안의 `/tmp`에서 같은 순서 | exit 0 |
| 마운트한 폴더에서 `git -c safe.directory=<그 폴더> config` | exit 0 |

- 마운트한 폴더의 소유자는 uid 501(macOS 사용자)로 보였고, 스튜디오는 uid 0(root)으로 돌았습니다.
- Git은 현재 사용자가 소유하지 않은 저장소에서 동작을 거부합니다(`safe.directory`). `git config`는 이 거부를 저장소가 없다는 메시지로 보여 줘서 원인이 가려졌습니다.

### 해결
- `safe.directory`는 시스템·전역·명령 줄 설정에서만 읽습니다. 저장소 안의 설정으로는 우회할 수 없습니다.
- 세션 폴더는 실행 중에 새로 생기므로 경로를 미리 하나씩 등록할 수 없습니다.
- 폴더 아래를 한꺼번에 허용하는 `경로/*` 형식은 Git 2.46.0 릴리스 노트에 추가된 기능입니다. 이미지의 Git 2.39.5에서 재 보니 무시돼 exit 128이 났고, `*`는 exit 0이었습니다.
- 그래서 이미지의 시스템 설정에 `safe.directory = *`를 넣었습니다.
  - 이 컨테이너가 여는 저장소는 운영자가 마운트한 세션·프로젝트 폴더뿐입니다.
  - 에이전트 도구는 `.git` 경로를 쓰지 못합니다.
- 다시 빌드한 이미지에서는 세션이 17.5초에 준비됐습니다. 데모 요청 1은 게이트를 통과해 체크포인트를 남겼습니다.

## 34. 컨테이너로 띄운 스튜디오에서 체크포인트 배포가 바로 실패함

**구분:** 33을 고친 뒤 같은 검증의 배포 단계에서 발견 → 재현 후 수정

### 현상
- 세션을 중지하고 체크포인트 배포를 요청하자 0.5초 만에 실패 이벤트가 왔습니다.
- 오류는 `체크포인트를 꺼내지 못했습니다: tar: api/.dockerignore: Cannot change ownership to uid 0, gid 0: Permission denied`였습니다.
- macOS에서 스튜디오를 직접 띄운 배포 검증(ADR-043)에서는 같은 코드가 통과했습니다.

### 원인 확인
- 체크포인트는 `git archive`의 tar 스트림을 `tar -x`로 배포 폴더에 풉니다.
- 같은 이미지에서 커밋 하나짜리 저장소를 만들어 풀어 봤습니다.

| 조건 | 결과 |
|---|---|
| root, 마운트한 폴더, 옵션 없음 | exit 2, `Cannot change ownership to uid 0, gid 0: Permission denied` |
| root, 마운트한 폴더, `--no-same-owner` | exit 0 |
| root, 컨테이너 안의 `/tmp`, 옵션 없음 | exit 0 |

- `git archive`는 항목의 소유자를 uid 0으로 기록합니다.
- GNU tar(1.34)는 root로 풀면 기록된 소유자로 chown합니다. 마운트한 폴더는 이 chown을 거부했습니다.
- macOS에서는 스튜디오가 일반 사용자로 돌기 때문에 tar가 소유자를 바꾸지 않아 드러나지 않았습니다.

### 해결
- `exportTree`가 `tar -x --no-same-owner`로 풀게 했습니다. 꺼낸 파일은 빌드 입력으로만 쓰므로 원래 소유자가 필요 없습니다.
- macOS의 bsdtar도 같은 옵션을 받아, 체크포인트 단위 테스트 23개가 그대로 통과했습니다.
- 다시 빌드한 이미지에서 같은 배포가 파일을 꺼내고 운영 이미지 빌드와 전환까지 끝났습니다(78.2초, 진행 줄 194줄).

## 35. 문법 강조를 워커로 옮기려다 워커가 컴파일되지 않는 것을 확인함

**구분:** 코드 탭의 한계(강조가 화면 스레드에서 돈다)를 없애려고 시도하다가 빌드 결과물에서 발견 → 되돌림

### 현상
- 강조를 웹 워커로 옮기려고 토큰화(DOM이 필요 없는 부분)와 색 클래스(DOM이 필요한 부분)를 나누고, 워커를 `new Worker(new URL('../lib/highlight.worker.ts', import.meta.url))`로 만들었습니다.
- `next build`는 경고 없이 끝났고, 단위 테스트·타입 검사·lint도 모두 통과했습니다.
- 그런데 결과물에는 워커가 **컴파일되지 않은 TypeScript 원본 그대로** 들어 있었습니다.

### 원인 확인

| 확인 | 결과 |
|---|---|
| 결과물의 워커 파일 | `.next/static/media/highlight.worker.<해시>.ts` (1,602바이트, 첫 줄이 `import { tokenizeLines, type RawLine } from './highlight-core';`) |
| 클라이언트 조각이 참조하는 값 | `"/_next/static/media/highlight.worker.<해시>.ts"` — 워커 진입점이 아니라 정적 자산 주소 |
| `{ type: 'module' }`을 더해 다시 빌드 | 같은 `.ts` 자산, 해시도 그대로 |

- Turbopack이 이 형태를 워커 진입점으로 컴파일하지 않고 정적 자산으로 내보냈습니다.
- 브라우저는 워커를 만드는 데는 성공하고 그 파일을 **파싱할 때** 실패합니다. 그래서 `new Worker`를 감싼 try/catch로는 잡히지 않고, 대비책인 화면 스레드 강조로 넘어가지도 않습니다. 코드가 조용히 평문으로만 보이게 됩니다.

### 해결
- 워커 방식을 되돌리고, 화면 스레드에서 100줄씩 나눠 강조하는 방식을 그대로 두었습니다(가장 긴 작업 103ms, [트러블슈팅 28](#28-큰-파일을-열면-코드-강조가-화면을-1초-넘게-멈춤)).
- 코드 탭의 다른 두 한계(목록 500개, 경로로만 찾기)는 서버 쪽에서 해결했습니다. 강조를 워커로 옮기는 것은 번들러가 워커 진입점을 컴파일할 때까지 한계로 남겨 두었습니다.
- 빌드가 성공하고 경고도 없었기 때문에, 결과물을 직접 열어 보지 않으면 그대로 넘어갈 수 있는 문제였습니다.

## 36. 같은 프로젝트로 두 세션을 동시에 띄우면 api 빌드가 실패함

**구분:** 사람별 토큰 한도를 실검증하다가 발견(첫 세션을 띄운 채 두 번째 세션을 만들었음). 아직 고치지 않고 한계로 기록

### 현상
- 첫 세션이 도는 동안 같은 프로젝트로 두 번째 세션을 만들자, 두 번째 세션이 `컨테이너가 종료됐습니다 (마지막 확인: UND_ERR_SOCKET, 컨테이너 exited)`로 기동에 실패했습니다.
- 처음에는 6GiB VM의 메모리 부족을 의심했습니다. **아니었습니다.**

### 원인 확인

| 확인 | 결과 |
|---|---|
| `docker inspect`의 종료 정보 | `exit=1`, `oom=false` — 메모리 부족으로 죽은 것이 아님 |
| api 컨테이너 로그 | `Timeout waiting to lock journal cache (/cache/gradle/caches/journal-1). It is currently in use by another process.` 뒤 `BUILD FAILED in 1m 3s` |
| 잠금 주인 | `Owner PID: 32`, `Our PID: 32` — 두 컨테이너 안의 Gradle 프로세스 PID가 같아서 Gradle이 "죽은 잠금"으로 판별하지 못함 |
| 그때 메모리 | VM 가용 1.1~1.8GiB로 남아 있었음 |

- 샌드박스는 기동을 빠르게 하려고 Gradle 캐시를 볼륨으로 공유합니다([ADR-008](decisions.md#adr-008-볼륨을-샌드박스-전용과-공유-캐시로-나눈다)). 그 이득은 측정으로 확인한 것입니다(13.4초 → 10.9초).
- 그런데 Gradle은 캐시 폴더에 프로세스 단위 잠금을 걸어, 같은 캐시를 쓰는 두 빌드가 동시에 돌면 뒤에 온 쪽이 기다리다 실패합니다.

### 해결
Gradle 홈을 샌드박스 전용 볼륨으로 옮기고, 공유는 이미지에 구운 **읽기 전용 의존성 캐시**(`GRADLE_RO_DEP_CACHE`)로 대체했습니다. Gradle은 이 캐시를 잠금 없이 읽습니다.

고치는 동안 네 번 실패했고, 매번 로그로 원인을 확인한 뒤에 고쳤습니다. 남겨 둘 가치가 있는 과정입니다.

| 시도 | 결과와 원인 |
|---|---|
| Gradle 홈만 샌드박스 전용으로 바꿈 | 샌드박스가 **아예 뜨지 않음**. 빈 홈이라 `gradlew`가 배포판을 받으려 했고, 샌드박스는 네트워크가 격리돼 `UnknownHostException: services.gradle.org`로 즉시 종료 |
| 배포판을 이미지에 구움 | 기동은 진행되지만 의존성 jar을 받으려 함. 읽기 전용 캐시에 jar이 23개뿐이었고 그마저 플러그인 것이었음(문제의 `jakarta.activation-api`는 `.pom`만 있었음). `dependencies` 태스크는 메타데이터만 받는다 |
| `bootJar`로 굽기 | 이미지에 소스가 없어 `Main class name has not been configured`로 실패. 다만 로그에서 런타임 classpath 해결은 이미 일어난 것을 확인 |
| `doLast`에서 `configurations` 해결 | Gradle 9의 구성 캐시와 충돌: `Invocation of 'configurations' references a Gradle script object from a Groovy closure at execution time` |

마지막에는 설정 단계에서 classpath 파일 목록을 잡아 두는 `downloadDependencies` 태스크로 구웠습니다. 소스를 이미지에 넣지 않은 이유는, 에이전트가 소스를 고칠 때마다 그 층이 깨져 기동이 느려지기 때문입니다.

### 확인한 결과
- 이미지에 구운 읽기 전용 캐시: jar 131개(`jakarta.activation-api`, `postgresql` 포함), 잠금 파일 0개, 배포판 2개. 네트워크를 끊은 컨테이너에서도 `compileJava`까지 진행됨(의존성을 오프라인으로 해결)
- 빈 이름 볼륨이 이미지의 경로 내용을 물려받는지 따로 실측(표시 파일을 넣은 이미지로 확인)
- 같은 프로젝트로 두 세션을 동시에 띄우는 확인 4개 모두 통과: 첫 세션 23.5초, 두 번째 33.4초에 준비, 두 api 모두 `running`(종료 코드 0, OOM 아님), 샌드박스마다 자기 `api-gradle-home` 볼륨, 양쪽 web 화면 200과 api 계약 200
- **대가**: api 준비가 13.9초 → 21.1초로 느려졌습니다. 샌드박스마다 Gradle 홈을 새로 채우기 때문입니다
- 두 샌드박스를 동시에 띄우면 6GiB VM의 가용 메모리가 101MB까지 내려갔습니다. 같은 프로젝트의 동시 세션은 메모리 여유를 보고 쓰세요

## 37. Docker 실검증 프로젝트를 /private/tmp에 만들면 컨테이너 안 코드가 비어 보일 수 있음

**구분:** 네트워크 egress 규칙을 실제 Docker로 검증하다가 발견. 제품 코드는 아니고 검증 스크립트 위치 문제

### 현상
FastAPI 임시 프로젝트를 `/private/tmp` 아래 만들고 샌드박스를 띄웠더니 api 컨테이너가 바로 종료됐습니다.

| 확인 | 결과 |
|---|---|
| api 로그 | `error: Failed to spawn: fastapi`, `No such file or directory` |
| edge 로그 | 시작 로그만 있고 PyPI 접속 기록 없음 |
| 원인 | Docker build context는 CLI가 보내서 통과했지만, 런타임 bind mount인 `/private/tmp/.../api:/app`는 colima VM에서 보이지 않아 `/app`에 프로젝트 파일이 없었음 |

### 해결
Docker가 실제로 볼 수 있는 `/Users/...` 아래, 이번에는 저장소의 gitignore된 `.playwright-mcp/egress-*`에 임시 프로젝트를 만들었습니다.

그 뒤 같은 FastAPI 템플릿이 `/health` 200으로 준비됐고, uv 설치가 `files.pythonhosted.org:443`을 edge 프록시로 50번 통과한 감사 로그를 남겼습니다.
