# 구현 상태와 일정

README에 있던 "일정과 작업 방식"과 "구현 상태" 절을 옮긴 문서입니다. README는 핵심 설계와 측정 결과만 남기고 영역별 상태와 만든 순서는 여기서 관리합니다.

## 지원 범위

b-studio가 **지원한다고 말하는 범위**는 좁습니다: 한 세션에 요청 하나씩, 로컬 CLI 백엔드(claude-code), 로컬 Docker 샌드박스. 도그푸딩에서 매일 쓰며 고친 경로가 이것이고, 변경을 내보낼 때마다 실제로 돌려 보는 것도 이 경로입니다.

그 밖의 기능은 **실험**입니다. 코드는 그대로 있고 테스트도 돌지만, 기본 화면과 에이전트 도구에서는 숨깁니다. `B_STUDIO_EXPERIMENTAL=1`로 스튜디오를 띄우면 보입니다([설정](configuration.md#실험-기능-b_studio_experimental), ADR-166). 숨기는 것일 뿐 막지 않습니다. API와 페이지 주소, 벤치와 E2E는 그대로입니다.

"마지막 실제 확인"은 테스트가 아니라 **실제 환경에서 돌려 본 마지막 날**입니다. 기록이 없으면 없다고 적었습니다.

| 사내 API 정책 프록시 | 기록 없음 | 도그푸딩 프로젝트에 등록한 사내 API가 없다 |

### 이 구분이 뜻하는 것

- 마찰을 고칠 때 실험 경로까지 같이 고치지 않습니다. 대신 PR에 "이 경로는 확인하지 않았다"를 적습니다([작업 규칙](../AGENTS.md)).
- 실험 기능을 지원으로 올리려면 실제 환경에서 돌린 기록이 먼저 있어야 합니다.
- 한 분기 뒤(2027-01)에 쓰임을 보고, 그때도 쓰지 않는 것은 지울지 정합니다. 그 전에는 지우지 않습니다. 실험 기록(E1~E14)을 다시 돌릴 수단이기 때문입니다.

설계 판단은 [ADR](decisions.md)에 적었습니다. 이 절을 처음 쓸 때 77개였고 2026-10-07 기준 126개입니다.

- 판단마다 근거를 남겼습니다.
  - → 샌드박스 제공자를 추상화한 근거는 ADR-006에 있습니다.
  - → 완료 판정을 플랫폼에 맡긴 결정은 ADR-010에, 워크플로 단계를 게이트가 직접 실행해야 통과로 인정한다는 기준은 ADR-049에 적었습니다.
- 기존 ADR은 지우지 않습니다.
  - → 판단이 바뀌면 새 ADR에서 대체 관계를 밝히는 규칙을 [기여 가이드](../CONTRIBUTING.md)에 정해 뒀습니다.

예상 작업 시간이나 마감을 미리 적어 두고 실제와 비교하는 기록은 남기지 않았습니다. 위 단계 구분은 커밋 기록을 나중에 묶어 다시 구성한 것입니다.

2026-09-24부터는 새 기능·개선을 "착수 명세" 이슈로 시작해 문제·선택지·완료 조건·예상 시간을 먼저 적습니다. PR에서는 [템플릿](../.github/pull_request_template.md)의 "예상과 실제" 표에 둘을 나란히 적습니다. 현재 단계와 다음 계획은 [로드맵](../ROADMAP.md)에서 봅니다.

- 2026-09-30부터 10-06까지 두 바퀴 돈 도그푸딩(명세 기반 풀스택 개발, [검증 기록](verification.md#명세-기반-풀스택-도그푸딩))에서 나온 마찰 84건 중 83건(오해로 취소한 1건 제외)을 PR 53개(#299~#387, #409·410·413·415·417·421·425·427)와 실행 환경 업그레이드 1건으로 고쳤습니다.
- 이 기간의 설계 판단은 ADR-089부터 126까지입니다.
