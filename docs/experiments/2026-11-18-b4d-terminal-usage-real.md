# B4d 실측: 세션 터미널의 사용량 귀속과 턴 상한 (2026-11-18)

[ADR-213](../decisions.md), 이슈 #1282. 고치기 전 시험 출력은 [따로 남겼습니다](2026-11-17-b4d-terminal-usage.md).

이번 실측에서 보려던 것은 네 가지입니다.

- 실제 Claude Code 세션의 사용량이 그 실행에 붙는가
- 턴 상한이 걸리는가
- 사용량 소식(텔레메트리)이 도구 훅보다 얼마나 늦게 오는가. U2 임계의 근거입니다
- 쓰기가 많은 정상 세션이 끊김으로 잘못 막히지 않는가

**둘째 시나리오 도중 구독의 주간 사용 한도에 닿았습니다.** 그래서 마지막 항목은 재지 못했습니다(아래 "보지 못한 것"). 대신 그 멈춤에서 다른 결함 하나가 드러났습니다.

## 환경

- **기기와 실행 방식**
  - macOS arm64, Node 22.17, 로컬 Docker(Colima)
  - 실제 Claude Code CLI 2.1.325, 구독 로그인
  - 이 컴퓨터 방식 세션 터미널, 실험 스위치가 꺼진 서버
- **코드와 서버**
  - 코드는 브랜치 `feat/b4d-terminal-usage`(7009387)입니다.
  - 서버는 실측 전용 폴더와 3923번 포트로 띄웠습니다.
  - 네이티브 모듈은 마지막 Rust 변경 뒤에 빌드했습니다.
- **프로젝트**
  - 턴 상한: `mt`. 정적 `index.html`이고, `vf3`를 복사해 `workflow.maxTurns: 2`만 더했습니다.
  - 쓰기 12번: `vf3`
- **하네스** `measure-term.mjs`
  - 이번에 `max-turns`·`many-writes` 시나리오를 더했습니다.
  - `run_usage` 이벤트를 받은 시각도 함께 적게 했습니다.

## 결과

### 턴 상한(`max-turns`, 상한 2)

| 시각 | 일 |
|---|---|
| 14.2초 | 실행 `3aae6814` 열림(요청 훅) |
| 18.8초 | `run_usage` haiku(1,842ms 요청) → 턴 1 |
| 21.4초 | `run_usage` fable(4,507ms) → 턴 2, 상한에 닿음 |
| 26.6초 | `run_usage` fable(4,915ms) |
| 31.4초 | 첫 Edit가 쓰기 직전 훅에서 거절됨: "턴 상한(2)에 닿았습니다. 지금까지 한 것을 정리하고 턴을 끝내세요". CLI가 우회하지 않고 턴을 끝내 `done`(바뀐 파일 0개) |
| 32.3초 | `run_usage` fable이 **닫힌 뒤** 도착함. 끝 뒤 5초 창에 들어 같은 실행에 붙음 |

- 사용량 넷이 모두 그 실행에 붙었습니다. 실행 밖 사용량(`tokens` 빈 실행 id)은 없었습니다.
- **턴은 CLI 안의 작은 모델 호출(haiku)도 셉니다.** haiku는 Claude Code가 요청 요약 같은 일에 쓰는 작은 모델 호출입니다. 그래서 상한 2에서는 첫 Edit 전에 이미 상한에 닿았습니다.
  - 이 셈은 이번 변경 전부터 있던 셈입니다. 붙은 모델 호출이 모두 턴이고, 이 PR은 바꾸지 않았습니다.
  - 덜 세지 않는 쪽이라 고치지 않았습니다. 다만 작은 상한을 정할 때는 haiku 호출 몫을 생각해야 합니다.

### 쓰기 12번(`many-writes`)과 사용량 소식의 늦음

| 시각 | 일 |
|---|---|
| 13.9초 | 실행 `7dea7d9b` 열림 |
| 16.4초 | `run_usage` haiku(1,096ms) |
| 20.9초 | `run_usage` fable(5,445ms). README를 읽기로 정한 요청 |
| 26.9초 | **Edit 쓰기 직전 훅**(첫 쓰기) |
| 27.9초 | `run_usage` fable(6,673ms). **그 Edit를 정한 요청의 사용량**으로, 훅보다 1.0초 늦게 도착 |
| 27.9초 뒤 | CLI가 "You've hit your weekly limit"으로 턴을 끝냄 |
| 163.9초 | 정체 알림 "터미널 요청이 2분 넘게 움직임이 없습니다": 마지막 움직임 뒤 136초(정체 시간 120초, 감시 주기 30초라 상한은 150초) |
| 913.9초 | 하네스 시간 초과. 실행은 열린 채 남아 있었음 |
| 1064.0초 | 같은 실행에 두 번째 정체 알림 |

- **사용량 소식의 늦음**: 도구를 정한 모델 요청의 사용량이 그 도구의 쓰기 직전 훅보다 1.0초 늦게 왔습니다. 첫 묶음(haiku)은 실행이 열리고 2.5초 뒤에 왔습니다.
  - U2 임계는 쓰기 10개를 넘고 30초가 지나는 것입니다. 한 번 잰 값으로 보면 정상 세션이 거기에 닿을 여유는 크지 않습니다.
  - 다만 쓰기 12번 전체를 끝까지 보지 못했으니 "잘못 막히지 않는다"는 확인하지 못했습니다.
- **정체 감시 주기(U6)**: 고친 주기(정체 시간의 1/4)대로 정체 시간의 1.25배 안에 알렸습니다.

## 실측에서 드러난 다른 결함: API 오류로 끝난 턴의 실행이 닫히지 않는다

주간 한도에 닿자 CLI는 턴을 끝냈습니다. 화면에는 "Usage limit reached · continuing automatically at 2am"이 떴습니다. 하지만 실행은 닫히지 않았고 다음과 같이 남았습니다.

- 바뀐 `README.md`가 체크포인트 없이 남았습니다.
- 다음 요청("README.md의 첫 줄만 읽어서 알려 줘")이 새 실행으로 열리지 않고 그 열린 실행에 붙었습니다. 하네스는 "다음 요청 시작되지 않음"으로 봤습니다.
- 그 요청도 같은 한도 오류로 끝났습니다.

원인은 이렇습니다. 설치된 CLI(2.1.326) 실행 파일은 `StopFailure`를 이렇게 정의합니다.

> "Fires instead of Stop when an API error (rate limit, auth failure, etc.) ended the turn"

즉 API 오류로 끝난 턴에는 Stop 훅이 오지 않습니다. 그런데 관문은 `StopFailure` 훅을 설치하지 않습니다. 이 결함은 이번 변경(B4d)의 범위가 아니어서 따로 이슈로 다룹니다.

- 체크포인트가 생기지 않으니 검증 없는 내용이 나가지는 않습니다.
- 하지만 실행이 사람이 취소할 때까지 점유를 쥐고, 그 뒤의 요청을 모두 삼킵니다.

## 보지 못한 것

- **쓰기가 많은 정상 세션이 끊김으로 잘못 막히지 않는지**: 주간 한도로 첫 Edit 뒤에 멈춰 재지 못했습니다. 시험(가짜 OTLP)으로만 확인했습니다.
- **소식 늦음**: 실행 하나에서 한 번 쟀습니다(1.0초).
- **사람 몫 다시 쓰기(U1), 도구 호출이 연 실행의 첫 요청(U5)**: 실제 세션에서 일으키지 않았습니다. 기록 파일 쓰기 실패와 요청 훅 없이 도구가 실행을 여는 순간을 실제로 맞출 수 없어 시험으로만 확인했습니다.
- **desk 화면**: 보지 않았습니다.

## 정리

하네스는 세션마다 멈추기·지우기(200, 200)로 정리했습니다. 정리가 끝난 뒤 studio를 껐고, 두 세션의 컨테이너·네트워크·볼륨·세션 폴더가 남지 않은 것을 확인했습니다.
