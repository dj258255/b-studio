## 가설

> **H1**: S1(격리 병렬)에서 인터페이스로 엮인 과제는 통합이 실패한다.
>
> **H2**: S0(직렬화)은 통합 성공이 더 많지만 종단 시간과 뒤 작업 입력 토큰이 커진다.

## 이 실험이 정할 것

[#45](https://github.com/dj258255/b-studio/issues/45)에 실행 전에 적은 판정 규칙을 그대로 씁니다.

- H1이 맞으면 M3에서 조율 전략(S2 계약 먼저, S3 게시판, S4 통합 후 수리, S5 실패 서명 공유)을 같은 과제로 비교합니다.
- H1이 틀리면 "현재 조건에서는 중앙 조율로 충분"을 결정으로 남기고 M3를 하지 않습니다.

## 지표 정의

- **성공**: 계획이 `done`이고(통합 게이트 통과), 통합 결과에서 인수 검사를 모두 통과한 경우입니다. 인수 검사는 과제마다 api·web 경로에 HTTP 요청을 보내 기대 문구가 본문에 있는지 봅니다. 게이트와는 별개로 벤치가 돌립니다.
- **종단 시간**: 계획 시작부터 통합 판정까지입니다. **기동 합**은 레인·통합 세션의 샌드박스 기동 시간의 합이고, **게이트**는 모든 실행의 검증 게이트 시간의 합입니다.
- **토큰**: 로컬 CLI가 보고한 사용량입니다. 입력(캐시 제외)·캐시 읽기·캐시 쓰기·출력을 따로 셉니다. 구독이라 청구 금액은 없고 추정 비용은 0으로 두었습니다.
- **모델 호출**: 실행마다 모델 요청 수입니다. **최대 컨텍스트**는 한 호출의 입력(캐시 포함) 최댓값입니다.
- 반복이 3회라 비율 대신 건수로 씁니다.

### 실패의 원인: 필드 이름·모양을 서로 다르게 짐작했다

실패한 S1 실행마다 통합 결과의 코드를 보관해 비교했습니다(`evidence/`).

| 실행 | 과제 | api가 돌려준 것 | web이 기대한 것 | 인수 결과 |
|---|---|---|---|---|
| 9 | orders-list | `amount` | `totalAmount` | 500(undefined에 `toLocaleString`) |
| 18 | orders-list | `amount` | `totalAmount` | 500(같은 원인) |
| 13 | order-summary | `statusCounts` | `orderCountsByStatus` | 500(undefined에 `Object.entries`) |
| 22 | order-summary | `statusCounts`: 객체 배열(`List<StatusCount>`) | `statusCounts`: 맵(`Record<string, number>`) | 500(객체를 React 자식으로 그림) |
| 20 | order-detail | `deliveryNote` | `deliveryMemo` | **200**, 화면에 "메모 없음" |

이름이 달랐던 경우가 4건, 이름은 같고 모양이 달랐던 경우가 1건입니다.

- 과제 요청은 필드를 한국어로만 설명합니다("금액", "배송 메모"). 그래서 JSON 필드 이름은 각 모델이 정합니다.
- **S0**에서는 web 작업이 같은 세션에서 api 코드를 읽은 뒤 시작합니다. 엮인 과제 9회 모두 이름이 일치했습니다.
- **S1**에서는 web 레인이 자기 샌드박스의 api를 `http_request`로 확인하려 했지만, 격리된 샌드박스에는 다른 레인이 만든 엔드포인트가 없습니다. 결국 관례적인 이름을 짐작했습니다.
- S1이 성공한 실행도 정보를 주고받아서 맞춘 것이 아닙니다. 두 레인이 **우연히 같은 이름을 고른** 경우입니다. 예를 들어 `order-detail`에서는 api가 `deliveryMemo`를 고른 두 번은 성공했고, `deliveryNote`를 고른 한 번은 실패했습니다. web은 세 번 모두 `deliveryMemo`였습니다.

### 게이트가 이 실패를 잡지 못했다

실패 5건은 모두 **계획이 `done`, 즉 통합 게이트를 통과한 상태**였습니다. 인수 검사에서만 드러났습니다.

- 예제([`examples/orders/studio.yaml`](../../examples/orders/studio.yaml))의 게이트는 네 가지를 봅니다: web lint, api 단위 테스트, 홈(`/`) 화면 확인, api 자신의 OpenAPI 계약 변경. 과제가 새로 만든 페이지(`/orders` 등)는 어느 단계도 렌더링하지 않고, 계약 확인도 web이 그 계약을 어떻게 쓰는지는 보지 않습니다.
- `order-detail`의 실패는 상태 200이었습니다. 화면에 "메모 없음"을 그렸습니다. 상태 코드만 보는 검사로는 잡히지 않고, 기대 문구를 확인해야 드러납니다.

## 예상과 다른 점

- 첫 1회 탐색(orders-list S1)은 성공해서 H1과 반대로 보였습니다. 반복해 보니 같은 조합이 3회 중 1회만 성공했습니다. 한 번의 성공은 짐작이 맞은 경우였습니다.
- S1이 S0보다 빠를 것이라고 가정했지만, 엮인 과제의 종단 중앙값은 S1이 257.8초, S0가 275.9초로 18초(7%)만 짧았습니다. 레인 두 개가 샌드박스를 따로 띄우고(기동 합 약 83초 대 47초) 게이트도 따로 돌기 때문입니다. 기동과 게이트가 시간의 큰 몫을 차지했습니다(아래 비중 주의 참조).
- 실패가 통합 게이트에서 날 것이라고 예상했지만, 모두 게이트를 통과했습니다. 이 때문에 S5(검증기 실패 서명 공유)는 이 종류의 실패에 **쓸 신호가 없습니다**. E2에서 확인할 예측입니다.

## 배제한 원인과 남은 가능성

- **환경 실패**: 남은 컨테이너 0건입니다. api 인수 검사는 24회 모두 통과했습니다. 실패는 모두 web의 필드 접근 코드에서 났습니다.
- **쓰기 범위 위반·계획 거부**: 0건입니다.
- **모델 편차**: 같은 과제·전략에서 결과가 갈렸으므로 편차는 있습니다. 다만 S0는 이름을 읽고 맞추는 구조라 편차가 결과를 바꾸지 못했고, S1에서만 결과를 바꿨습니다.
- **남은 가능성**: 과제 요청에 영어 필드 이름을 적으면 S1도 대부분 성공할 것입니다. 그것은 사람이 계약을 미리 써 준 것이므로 S2(계약 먼저)의 수동판입니다. 이 실험은 요청에 계약이 없는 경우만 쟀습니다.

## 결론과 적용 범위

- **H1은 이 조건에서 확인했습니다.** 인터페이스로 엮인 과제에서 S1은 9회 중 5회 실패했고, S0는 9회 모두 성공했습니다. 독립 과제에서는 두 전략 모두 3/3이었습니다. 실패는 모두 레인 경계의 계약(필드 이름·모양) 불일치였습니다.
- **H2는 일부만 확인했습니다.** S0의 통합 성공이 더 많고, 뒤 작업의 입력이 커졌습니다(캐시 읽기 합 1.9배, `order-detail`의 최대 컨텍스트 86,559 대 30,295). 반면 종단 시간 차이는 7%로 작았습니다. 병렬로 얻는 시간을 샌드박스 기동과 게이트가 대부분 먹었습니다.
- **판정 규칙에 따라 M3을 진행합니다.** 조율 전략(S2~S5)을 같은 과제로 비교하는 E2를 돌립니다. 조율 메커니즘은 이미 [#76](https://github.com/dj258255/b-studio/pull/76)에 있습니다.
- **예상하지 못한 발견**: 통합 게이트가 5건을 모두 통과시켰습니다. 조율 전략과 별개로, 게이트에 레인 경계를 넘는 확인이 없다는 점 자체가 결함입니다. 이 결과는 [ADR-051](../decisions.md) 보강 절에 적습니다.

이 결론은 이 저장소의 예제(Spring Boot api와 Next.js web), `claude-sonnet-5`, 필드 이름이 요청에 없는 작은 과제 3개에서만 확인했습니다.
