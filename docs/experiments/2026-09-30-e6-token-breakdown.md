# 실험 E6: 토큰은 어디서 나오는가 — 그냥 Claude Code(P0)와 b-studio(S0)의 호출별 분해

- 날짜: 2026-09-30
- 관련 이슈: [#187](https://github.com/dj258255/b-studio/issues/187)(질문 등록), 측정 도구 [#185](https://github.com/dj258255/b-studio/issues/185)·[#190](https://github.com/dj258255/b-studio/issues/190), 조사 [검토 문서](../research/2026-09-30-token-reduction-sources.md)
- 커밋: [a6bd7d3](https://github.com/dj258255/b-studio/commit/a6bd7d3). 커밋을 고정한 작업 트리에서 돌렸습니다.
- 원자료: `~/.cache/b-studio/bench/coordination/e6-base/`. 6행의 핵심 열은 [`data/2026-09-30-e6-results.csv`](data/2026-09-30-e6-results.csv)에 옮겼습니다.
- 성격: **측정 실험**입니다. 조건마다 1회라 두 조건의 우열은 판정하지 않고, 토큰이 어디서 나오는지 비율만 봅니다.

## 왜 이 실험인가

- E3에서 b-studio(S0)는 성공 1건당 토큰을 그냥 Claude Code(P0)의 약 2배 썼습니다.
- E5에서 검증 게이트를 건너뛰어도 토큰은 줄지 않았습니다. 게이트는 모델을 부르지 않기 때문입니다.
- 토큰의 92~93%는 캐시 읽기였습니다. 합계는 "호출 수 × 문맥 크기"로 정해진다는 것까지만 알았습니다.
- 그래서 [#186](https://github.com/dj258255/b-studio/pull/186)으로 벤치가 모델 호출마다 기록을 남기게 했습니다. 남기는 값은 문맥 크기, 모델이 쓴 글자, 부른 도구와 결과 크기입니다. 이 기록으로 문맥 합을 넷으로 나눴습니다.
  - 고정 문맥: 세션 첫 호출 문맥 × 호출 수
  - 출력 재읽기
  - 도구 결과 재읽기
  - 비워서 줄어든 양

## 진행 중에 발견한 것 (결과를 보기 전)

1. **첫 시도를 무효로 했습니다.**
   - 첫 행(P0)을 분해해 보니 출력 토큰이 호출당 1~16으로 잡혔습니다. 로컬 Claude Code(SDK)는 응답 첫 조각의 사용량만 알려 주기 때문입니다.
   - 그 결과 `Write`로 쓴 파일 내용(모델 출력)이 `Write`의 도구 결과 재읽기로 잘못 잡혔습니다. `Write` 결과는 843자뿐인데 재읽기는 2.3만 토큰이었습니다.
   - [#191](https://github.com/dj258255/b-studio/pull/191)로 고쳤습니다. 이제 늘어난 문맥을 "모델이 쓴 글자 : 도구 결과 글자" 비율로 나눕니다. 고친 커밋에서 6회를 처음부터 다시 돌렸습니다.
2. **구독 모드에서는 오래된 도구 결과 비우기가 동작하지 않습니다.**
   - 비우기는 직접 API 루프에만 있습니다. 로컬 Claude Code 러너는 대화 기록을 Claude Code가 관리합니다.
   - Claude Code 자체 압축은 문맥이 거의 찰 때 동작해, 이 과제들에서는 한 번도 켜지지 않습니다(비워서 줄어든 양 0).

## 답 (질문은 [#187](https://github.com/dj258255/b-studio/issues/187)에 먼저 적음)

- **Q1 고정 문맥**: b-studio의 세션 첫 호출 문맥은 2,289토큰으로, P0(13,504)의 6분의 1이었습니다.
  - b-studio는 Claude Code 기본 시스템 프롬프트 대신 자체 프롬프트(4,448자)와 도구 11개(설명 4,397자)만 싣기 때문입니다.
  - 추가 토큰에서 고정 문맥이 차지하는 몫은 2%입니다. **도구 설명 줄이기(조사 후보 B)는 이 과제에서 효과가 거의 없습니다.**
- **Q2 도구 결과**: S0 문맥 합의 61%가 도구 결과를 다시 읽은 양이었습니다.
  - 가장 큰 것은 `run_in_service`(32.7%)였습니다. 30번 돌린 명령 결과 8만 자가 뒤 호출마다 다시 실렸습니다.
- **Q3 추가 토큰의 출처**: b-studio가 더 쓴 문맥 약 109만 토큰의 78%가 도구 결과 재읽기, 20%가 출력 재읽기였습니다.
  - 호출이 3.4배 많아, 쌓인 결과를 다시 읽는 횟수가 함께 늘었습니다.

## 원인에 대한 해석

- 시스템 프롬프트가 두 가지를 동시에 말합니다.
  - "`run_in_service`로 빌드·테스트를 돌리고, 끝내기 전에 `restart_service`·`http_request`로 확인하라."
  - 워크플로 안내: "턴을 끝내면 플랫폼이 재시작·계약·테스트를 직접 돌린다."
- 에이전트는 앞 문장을 따라 게이트가 어차피 할 확인을 스스로 하고, 그 결과가 매 호출 다시 읽힙니다.
- P0는 명령을 실행할 도구가 없어 이런 확인을 하지 못합니다. 그런데도 E3·E6에서 모두 성공했습니다.
- 이 해석은 도구 이름과 호출 수에서 나온 것입니다. `run_in_service`로 **무엇을** 돌렸는지(명령)는 기록에 없어 확인하지 못했습니다.

## 결정에 주는 영향

- 줄일 대상은 호출 수와 도구 결과, 특히 `run_in_service`입니다. 고정 문맥은 대상이 아닙니다.
- [#192](https://github.com/dj258255/b-studio/issues/192)로 자가 확인 lean 모드(`B_STUDIO_SELF_CHECK=lean`, 기본 끔)를 만들었습니다.
  - 프롬프트가 게이트와 겹치는 확인을 하지 말라고 안내합니다.
  - 성공한 명령 출력은 800자만 돌려줍니다.
- 효과와 성공률은 E7([#193](https://github.com/dj258255/b-studio/issues/193))에서 잽니다. 조건마다 9회, full과 lean을 번갈아 돌립니다.

이 결론은 이 저장소의 예제(Spring Boot api와 Next.js web), 작은 과제 3개, 조건별 1회에서만 확인했습니다. 과제가 크면 고정 문맥의 몫은 더 작아지고, 도구 결과의 몫은 더 커질 것으로 봅니다(추정).
