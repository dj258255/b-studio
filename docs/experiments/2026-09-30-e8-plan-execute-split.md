# 실험 E8: 계획은 큰 모델, 실행은 작은 모델은 비용을 줄이는가

- 날짜: 2026-09-30 (KST 15:45 ~ 20:56)

Sonnet 1회차 한 묶음만 [e6b77c1](https://github.com/dj258255/b-studio/commit/e6b77c1)에서 돌렸습니다. 두 커밋의 차이(#240 AGENTS.md 읽기, #242 계획 백엔드 수정)는 Sonnet 조건의 실행 경로를 바꾸지 않습니다. 예제에는 AGENTS.md가 없고, 계획 모델을 설정하지 않았기 때문입니다.

## 왜 이 실험인가

Cognition Devin Fusion은 큰 모델이 계획과 모호함 해소를 맡고 작은 모델이 실행을 맡게 했습니다. FrontierCode 1.1에서 과제당 $1.35에 63.1점을 냈습니다(Opus 5는 $3.51에 63.6점). Aider의 architect/editor 구성도 대부분 단독보다 나았습니다.

b-studio에 같은 구조를 넣었습니다(ADR-075). 큰 모델이 도구 없이 계획을 한 번 쓰고, 작은 모델이 그 계획을 붙인 요청으로 실행합니다. 이 구조가 우리 과제에서도 돈을 아끼는지 쟀습니다.

## 가설 (실행 전에 [#238](https://github.com/dj258255/b-studio/issues/238)에 적음)

- **H17**: E8-split의 성공 1건당 API 환산 비용은 E8-sonnet보다 30% 이상 적다.
- **H18**: E8-split의 성공은 E8-sonnet과 구별되지 않는다(차이 1건 이하).
- **H19**: 계획이 작은 모델을 돕는다. E8-split의 성공이 E8-haiku보다 많거나, 같다면 성공 1건당 비용이 적다.

## 조건

| 조건 | 설정 |
|---|---|
| E8-sonnet | S0, `--model sonnet` |
| E8-split | S0, `--plan-model opus --execute-model haiku --plan-always`. 게이트에서 반복 실패하면 계획 모델로 승급 |
| E8-haiku | S0, `--model haiku`. 계획과 승급 없음 |
| 공통 | 로컬 Claude Code 구독, 엮인 과제 3개(orders-list, order-detail, order-summary) × 3회. 반복마다 조건 순서를 돌림. 자가 확인은 벤치 기본인 full(E1~E7과 같음) |

**사전 등록과 다른 점: 단가.** 등록할 때는 Opus 5.5 단가를 적었습니다. 그런데 Claude Code의 `opus` 별칭은 실제로 `claude-opus-5`로 풀렸습니다(승급된 실행의 모델별 사용량에 그대로 찍힘). 그래서 계획과 승급에는 Opus 5 공식 단가를 썼습니다. Opus 5 단가는 $5/$25, 캐시 읽기 $0.50, 5분 캐시 쓰기 $6.25입니다. 나머지 단가는 등록한 대로입니다(Sonnet 5 $2/$10/$0.20/$2.50, Haiku 4.5 $1/$5/$0.10/$1.25).

## 결과

27회 모두 유효했습니다. 환경 실패, 하네스 실패, 한도 실패는 0건입니다.

| 조건 | 성공 | 토큰 합 | 모델 호출 | 성공 1건당 토큰 | API 환산 비용 합 | 성공 1건당 비용 | 종단 중앙값 |
|---|---|---|---|---|---|---|---|
| E8-sonnet | **9/9** | 4,200,085 | 231 | 466,676 | $2.099 | **$0.233** | 6.2분 |
| E8-haiku | 7/9 | 6,078,524 | 284 | 868,361 | $1.565 | $0.224 | 7.3분 |
| E8-split | 5/9 | 16,580,830 | 465 | 3,316,166 | $7.440 | **$1.488 (+538%)** | 15.2분 |

E8-split 비용 $7.44의 구성은 이렇습니다.
- 계획 호출: $2.63(토큰 14만)
- Opus로 승급된 실행 1건: $1.75
- Haiku 실행: 나머지

계획 호출만으로 Sonnet이 과제 9개를 모두 한 비용($2.10)보다 컸습니다.

|---|---|---|---|

| haiku r2 | order-summary | 인수 확인 | 같은 증상 |

- Haiku 단독의 실패 둘은 **게이트를 통과한 뒤** 인수 확인에서 잡혔습니다. 데이터를 받기 전 로딩 상태를 그대로 둔 화면입니다. 게이트의 화면 확인이 이 경우를 놓친다는 뜻이라 따로 봐야 합니다.
- split r3 order-summary는 모델이 틀린 것이 아니라 CLI 쪽 비정상 종료일 수 있습니다. 사전 등록대로 실패로 셌습니다. **이 건을 빼도** split은 5/8이고, 비용 결론은 그대로입니다.

### 어디서 늘었나 (실행 기록, 조건마다 9회 평균)

| 조건 | 파일 쓰기 | 파일 고치기 | 읽기(`read_file`·`list_files`) | `run_in_service` | 모델 호출(턴) | 최대 문맥 |
|---|---|---|---|---|---|---|
| sonnet | 4.4 | 0.1 | 14.8 | 8.6 | 25.7 | 29,549 |
| haiku | 3.7 | 1.2 | 13.1 | 4.6 | 31.6 | 31,086 |
| split | **11.2** | **5.4** | **24.0** | **12.8** | **58.4** | **62,268** |

계획을 받은 Haiku의 작업량은 Haiku 단독과 비교해 이렇게 늘었습니다.
- 파일 쓰기 3배
- 파일 고치기 4.5배
- 턴 1.8배
- 최대 문맥 2배

E6에서 잰 대로 토큰은 거의 "모델 호출 수 × 문맥 크기"이므로, 둘이 함께 두 배가 되자 토큰이 약 4배가 됐습니다.

계획 텍스트 자체는 벤치가 실행 뒤 세션 폴더를 지워 남지 않았습니다. 그래서 "계획이 과제보다 큰 설계(파일 분리, 추가 확인 단계)를 적었다"는 설명은 위 도구 호출 수에서 추론한 것입니다. 계획 원문으로 확인한 것은 아닙니다.

## 결론

- **H17 기각**: 성공 1건당 비용이 30% 적기는커녕 **538% 많았습니다**. 짝지은 9쌍 중 8쌍에서 split이 비쌌습니다(p = 0.008).
- **H18 기각**: 성공은 5/9 대 9/9로 4건 차이입니다(p = 0.082). 등록한 기준(차이 1건 이하)을 넘었습니다.
- **H19 기각**: split은 Haiku 단독보다 성공이 적고(5/9 대 7/9) 성공 1건당 비용은 6.7배였습니다. 계획은 이 과제들에서 작은 모델을 돕지 못했습니다.
- **Haiku 단독 대 Sonnet 단독**(등록 밖, 설명용):
  - 성공 1건당 비용은 거의 같았습니다(−4%). Haiku는 토큰을 86% 더 쓰지만 단가가 절반입니다.
  - 성공은 7/9 대 9/9입니다(p = 0.47).
  - 싼 모델로 바꾸는 것만으로는 돈이 줄지 않았습니다. Sonnet이 더 적은 턴으로 끝내기 때문입니다.

## 결정에 주는 영향

- **ADR-075는 기본 끔을 유지합니다.** 짧고 분명한 요청(이 과제들처럼 한두 문장)에서는 계획을 세우지 않습니다. 기본 `auto`는 이런 요청을 `simple`로 분류해 건너뜁니다. 이 실험은 그 판단이 맞았다는 근거입니다. `B_STUDIO_PLAN_BRIEF=always`는 실험용으로만 둡니다.
- 계획 프롬프트는 이 구조를 다시 재기 전에 먼저 고칩니다.
  - 과제 범위를 넘는 파일과 단계를 적지 않게 합니다("요청이 요구하는 최소 변경").
  - 계획 길이를 요청 크기에 맞춥니다.
- 벤치는 계획 텍스트를 결과에 남기도록 고칩니다. 이번에는 원문을 보지 못했습니다.

이 결론은 이 저장소의 예제(Spring Boot api와 Next.js web), 작은 과제 3개, 조건별 9회에서만 확인했습니다. Fusion이 쓴 것 같은 크고 모호한 과제에서 계획이 값을 하는지는 이 실험이 답하지 않습니다.
