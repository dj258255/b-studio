## 가설

E1의 결론이 다른 모델 계열에서도 유지되는가.

> **H1**: S1(격리 병렬)에서 인터페이스로 엮인 과제는 통합이 실패한다.
>
> **H2**: S0(직렬화)은 통합 성공이 더 많지만 종단 시간과 뒤 작업 입력 토큰이 커진다.

## 조건

E1과 같고 백엔드만 바꿨습니다.

| 항목 | 값 |

## 예상과 다른 점

- S1 엮인 과제 실패가 E1의 5/9보다 적은 3/9였습니다. `orders-list`는 E1에서 1/3이었는데 이번에는 3/3이었습니다. 두 레인이 같은 관례 이름(`amount`)을 골랐기 때문입니다. 이름을 맞춘 근거가 있는 것은 아니라 E1 결론의 "우연히 같은 이름을 고른 경우"에 해당합니다.
- S1이 S0보다 엮인 과제에서 25% 빨랐습니다(174.5초 대 232.1초, E1은 7%). 게이트 시간이 E1의 절반 아래라 병렬로 겹치는 몫이 상대적으로 컸을 수 있습니다. Codex 러너는 모델 시간(`modelMs`)을 0으로 남겨 모델 몫은 따로 재지 못했습니다.
- 처음 실행에서 한도 실패를 일반 실패로 센 것은 예상하지 못했습니다. 0단계 실측([Codex 실측](2026-10-28-codex-real.md))에서는 한도에 닿지 않아 이 경로를 보지 못했습니다.

## 결론과 적용 범위

- **H1은 방향은 같지만 이 표본으로는 확인하지 못했습니다.** 엮인 과제에서 S1은 9회 중 3회 실패했고 S0는 9회 모두 성공했습니다. 독립 과제는 두 전략 모두 3/3입니다. 실패는 모두 게이트를 통과한 뒤 인수 검사에서 드러났습니다. E1과 합치면 엮인 과제 S0 18/18 대 S1 10/18입니다.
- **H2는 이번에도 일부만 맞았습니다.** S0의 통합 성공이 더 많고 캐시 읽기 합이 1.16배입니다(E1은 1.9배). 종단 시간은 S0가 더 길었고 차이가 E1보다 컸습니다.
- 다른 모델 계열에서도 "격리 병렬은 레인 경계의 짐작에 기대고, 게이트가 그 실패를 잡지 못한다"는 E1의 관찰이 유지됩니다. 이미 넣은 조율(계약 먼저, 레인 경계 확인)을 바꿀 근거는 나오지 않았습니다.

이 결론은 이 저장소의 예제, ChatGPT 구독의 계정 기본 모델, 필드 이름이 요청에 없는 작은 과제 3개에서만 확인했습니다.

## 덧붙임: 두 AI에 규칙표로 나눠 보내기(#820)

같은 갈래에서 [#820](https://github.com/dj258255/b-studio/issues/820)의 마지막 항목도 실제 Docker와 로그인한 두 CLI로 확인했습니다([`routing-two-ai.ts`](data/2026-10-28-codex-e1b/routing-two-ai.ts), 결과 [`routing-two-ai.json`](data/2026-10-28-codex-e1b/routing-two-ai.json)). 규칙표는 "api의"가 든 요청을 Codex로, 나머지를 Claude Code(sonnet)로 보냅니다.

| 요청 | 간 곳 | 맞은 규칙 | 게이트 | 시간 |
|---|---|---|---|---|
| api `/api/ping`에 version 필드와 테스트 더하기 | Codex | "api의" 포함 | 통과 | 86초 |
| web 홈 제목 아래 문구 더하기 | Claude Code | 기본값 | 통과 | 67초 |

실행 기록 통계에 두 AI가 따로 쌓였습니다(각 1회 통과, 평균 토큰 Claude 44,424, Codex 64,516).
