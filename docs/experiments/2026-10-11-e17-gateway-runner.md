# 실험 17: 러너 대신 터미널의 에이전트 CLI에 관문만 붙여도 같은 결과가 나오는가

- 날짜: 2026-10-11
- 관련 이슈: [#670](https://github.com/dj258255/b-studio/issues/670), 추적 [#611](https://github.com/dj258255/b-studio/issues/611)
- 커밋: 본 실험(2차)은 `f60e02d`, 조건이 어긋난 1차는 `227769b`
- 원자료 경로: 벤치 36회는 [data/2026-10-11-e17-results.csv](data/2026-10-11-e17-results.csv)(1차·2차를 `batch` 열로 구분), 수리 확인 18회는 [data/2026-10-11-e17-repair.json](data/2026-10-11-e17-repair.json). 벤치의 원본 폴더는 `~/.cache/b-studio/bench/coordination/e17-*`(1차), `e17b-*`(2차)

## 가설

지금은 에이전트를 러너(Agent SDK를 감싼 코드)로 돌린다. 러너는 CLI의 내장 도구를 모두 끄고 b-studio 도구만 주며, 턴이 끝날 때 게이트를 돈다. 대신 CLI를 세션 작업 복사본에서 그대로 띄우고 b-studio는 바깥에서 도구(MCP)와 게이트(멈춤 훅)만 붙이는 방식(이하 관문)을 쟀다. 대화 화면을 터미널로 바꾸려는 방향의 전제가 서는지 보려는 것이다.

- H1(경계): 관문의 성공 건수가 러너와 1건 이내로 같다(9회 중).
- H2(수리): 게이트가 실패를 돌려준 실행 가운데 고쳐서 통과한 비율이 러너보다 낮지 않다.
- H3(비용): 성공 1건당 토큰이 러너의 ±20% 안이다.
- H4(막기): 에이전트가 내장 도구로 직접 고친 파일도 빠짐없이 게이트에 들어간다. 보호 경로를 고친 변경은 리뷰 단계가 막는다.

## 이 실험이 정할 것

- H1·H2·H4가 맞으면 관문을 실험 기능으로 넣는다. 기본값은 다른 사람이 써 본 관찰([#610](https://github.com/dj258255/b-studio/issues/610)) 뒤에 정한다.
- H2가 틀리면 러너를 유지하고, 터미널은 세션에 붙는 조작용 명령으로만 만든다.
- H4가 틀리면 넣지 않는다.
- 만드는 중에 더한 조건: CLI 프로세스를 운영체제 수준에서 가두기 전에는 기본으로 켜지 않는다(아래 "예상과 다른 점" 1).

## 조건

- 과제: 협업 벤치의 엮인 과제 3개(orders-list, order-detail, order-summary). Spring Boot api와 Next.js web을 한 레인에서 차례로 고친다. 판정은 기존 인수 확인.
- 팔
  - S0 러너: `runClaudeCodeAgent`. b-studio 지시문, b-studio 파일 도구.
  - G0 관문: `runClaudeGatewayAgent`(`B_STUDIO_GATEWAY=1`). 설치된 CLI 2.1.296을 `-p`로 실행. Claude Code 기본 지시문 + 짧은 b-studio 안내 + 프로젝트 안내, 내장 Read·Edit·Write·Glob·Grep, b-studio의 샌드박스 도구(서비스 안 명령·재시작·로그·요청·계약 조회)는 MCP, 멈춤 훅이 게이트를 부른다.
- 팔마다 과제 3개 × 3회. 반복마다 두 팔을 번갈아 돌렸다(1·3회차는 S0 먼저, 2회차는 G0 먼저).
- **2차(본 실험)**: 두 팔 모두 `--model claude-sonnet-5-5`, 자가 확인 `lean`(제품 기본값).
- **1차(조건이 어긋남, 결론에 쓰지 않음)**: `--model sonnet`, 자가 확인 `full`(벤치 기본값). 별칭 `sonnet`을 러너의 SDK는 `claude-sonnet-5`로, 설치된 CLI는 `claude-sonnet-5-5`로 풀어 두 팔의 모델이 달랐다.
- 같은 날, 같은 기계, 구독 로그인. 벤치가 도는 동안 다른 프로젝트의 컨테이너는 없었다.
- 수리 확인(H2)은 벤치 밖에서 따로 쟀다. 벤치 과제는 두 팔 모두 게이트를 한 번에 통과해서(36회 중 실패 0) 수리가 일어나지 않았다. 샌드박스만 가짜로 바꾸고(재시작이 파일 내용에 따라 실패하고 로그에 원인을 싣는다) CLI·모델·훅·게이트는 실제 것을 썼다.

## 지표 정의

- 성공: 인수 확인을 통과한 실행.
- 종단 시간: 세션을 만들 때부터 마지막 게이트가 끝날 때까지. 기동 뺀 시간은 여기서 샌드박스 기동 시간을 뺀 값.
- 모델 시간: CLI가 알려 주는 API 호출 시간의 합.
- 토큰 합: 입력 + 출력 + 캐시 읽기 + 캐시 쓰기. 환산 토큰은 `입력 + 캐시 읽기 × 0.1 + 캐시 쓰기 × 1.25 + 출력 × 5`.
- 게이트 실패: 게이트가 실패를 돌려준 횟수.
- 짝: 같은 과제·같은 회차의 S0와 G0. 9쌍.

## 예상과 다른 점

1. **가두지 않은 CLI는 호스트를 읽고 썼다.** 처음 구현은 내장 도구를 허용 목록에 넣고 묻지 않는 모드로 돌렸다. 커밋 보안 검토가 지적했고, 실제 CLI에서 `/etc/hosts` 읽기와 작업 폴더 밖 쓰기를 확인했다. 작업 복사본의 `.git`은 호스트의 git이 그대로 믿으므로(`.git/config`, 훅 폴더) 거기에 쓰면 호스트에서 코드가 실행된다. 러너가 내장 도구를 전부 끄는 까닭이 이것이었다. 고친 것은 두 겹이다: CLI 자신의 작업 폴더 가두기(편집 자동 수락 모드, 내장 도구는 허용 목록에 넣지 않음)와, 도구를 쓰기 직전의 훅에서 b-studio의 파일 도구와 같은 규칙으로 보는 경로 검사.
2. **경로 검사만으로는 닫히지 않는 틈이 남는다.** 검사는 훅에서, 실제 읽기·쓰기는 그 뒤에 CLI 프로세스에서 일어난다. 그 사이에 컨테이너 안의 명령이 검사한 경로를 밖을 가리키는 링크로 바꾸면 검사를 지난 호출이 호스트의 다른 파일에 닿는다. 다른 프로세스의 도구를 경로 검사로 가두는 한 없앨 수 없다. 검사와 CLI가 같은 글자를 다른 경로로 읽는 틈(`~`, 상대 경로, `..`, 패턴의 중괄호)은 받는 꼴을 좁혀 닫았다.
3. **H3은 틀렸다.** 토큰이 ±20% 안일 것으로 봤는데 관문이 1.38배였다. 호출 수와 최대 문맥은 같고 출력(1.51배)과 캐시 읽기(1.36배)가 컸다. Claude Code 기본 지시문과 도구 정의가 b-studio의 것보다 커서 호출마다 더 읽는 것으로 본다(E6에서 b-studio의 고정 문맥은 그냥 Claude Code의 1/6이었다). 출력이 왜 큰지는 가르지 않았다.
4. **1차의 "관문이 유리"는 조건 차이였다.** 같은 별칭을 두 팔이 다른 모델로 풀었다. 요약 표의 "요청한 모델"만 봐서는 보이지 않고 모델별 사용량을 펼쳐야 보였다.
5. **수리 확인의 첫 시나리오는 0/5였다.** 관문만 돌렸을 때는 "관문은 고치지 못한다"로 읽혔다. 러너로 같은 시나리오를 돌리자 러너도 0/3이었다. 시나리오가 고칠 수 없는 결함이었다.
6. 게이트 시간은 관문이 9쌍 모두 짧았다(58초 대 70초). 관문 쪽 에이전트가 서비스를 직접 다시 띄운 경우(`restart_service` 5회)가 있어 빌드가 데워졌을 수 있지만 확인하지 않았다.

## 배제한 원인과 남은 가능성

- 시간대 차이: 반복마다 두 팔을 번갈아 돌렸다. 2차의 여섯 묶음은 모두 9분 안팎으로 끝났다.
- 모델 차이: 2차는 두 팔 모두 `claude-sonnet-5-5`로 돈 것을 실행마다 확인했다. 다만 CLI가 내부에서 부르는 작은 모델은 다르다(러너의 SDK는 haiku 4.5, 설치된 CLI는 haiku 5.5). 입력 토큰의 차이(평균 1,186 대 2,917)가 여기서 나오고 토큰 합의 1% 안팎이다.
- 두 팔은 CLI의 판도 다르다. 러너는 SDK에 묶인 CLI를, 관문은 설치된 CLI를 쓴다. 관문의 뜻이 "사용자가 깐 CLI를 그대로 쓴다"라서 맞추지 않았다. 지시문의 차이와 CLI 판의 차이가 토큰에 각각 얼마를 보탰는지는 가르지 못한다.
- 과제 3개는 모두 작고(파일 3~4개) 게이트를 한 번에 통과한다. 큰 요청, 긴 세션(이어받기·압축), 되묻기, 실행 중 지시는 재지 않았다. 관문 러너는 그 가운데 되묻기와 실행 중 지시를 아직 받지 않는다.
- 수리 확인은 샌드박스가 가짜다. 실제 빌드 실패의 로그는 더 길고 지저분하다.
- 도구 호출 전 검사가 정상 호출을 막은 횟수는 세지 못했다(벤치가 경고 이벤트를 남기지 않는다). 막혔다면 그만큼 턴이 늘었을 것이다. 호출 수는 두 팔이 같았다.
- 대화형 터미널은 재지 않았다. 이 실험은 `-p`(한 번 실행)다. 요청의 시작과 끝을 훅으로 잡는 일, 사용자의 전역 설정·플러그인이 실린 상태, 게이트가 도는 1분 동안의 사용감은 다음 단계다.

## 결론과 적용 범위

이 과제 3개, 이 모델, 이 기계에서 본 것이다.

- **H1 확인**: 성공 9/9 대 9/9.
- **H2 확인(기구)**: 게이트가 돌려준 실패를 관문도 러너와 똑같이 고쳤다(5/5 대 5/5). 진짜 샌드박스의 실패에서는 확인하지 못했다.
- **H3 기각**: 관문이 토큰을 1.38배 쓴다. 시간은 같다.
- **H4 확인(조건부)**: 직접 고친 파일은 빠짐없이 게이트에 들어가고, 보호 경로·`.env`·링크·프로젝트 밖은 막힌다. 단 검사와 사용 사이의 바꿔치기 경쟁은 남는다.

정한 것(ADR-168):

- 관문 러너를 **실험 경로로 넣고 기본은 러너로 둔다.** 스위치는 `B_STUDIO_GATEWAY`이고 꺼져 있다. 믿는 요청(벤치)으로만 돌린다.
- 기본으로 올리는 조건은 셋이다. CLI 프로세스를 운영체제 수준에서 가두거나 컨테이너 안에서 돌려 바꿔치기 경쟁을 없앨 것, 대화형 터미널에서 다시 잴 것, 다른 사람이 써 본 관찰(#610).
- 토큰이 1.38배라는 값은 방향을 바꾸는 근거로 쓰지 않는다. 관문에서 얻으려는 것은 토큰이 아니라 러너를 백엔드마다 유지하지 않는 것과 CLI 본래의 사용감이고, 그것은 이 실험이 재지 않았다.
- 벤치의 기준선 팔(P0, `plain-baseline.ts`)은 처음 구현과 같은 설정(내장 도구를 허용 목록에 넣고 묻지 않는 모드)으로 호스트에서 돈다. SDK의 옵션으로 준 경우에도 CLI 인자와 똑같이 밖을 읽고 쓰는지는 확인하지 않았다. 믿는 과제만 돌리는 벤치 전용 경로지만 같은 노출일 수 있어 따로 이슈로 올렸다([#671](https://github.com/dj258255/b-studio/issues/671)). **뒤에 확인했다(2026-10-12):** SDK 옵션에서도 밖을 읽고 썼고, 같은 두 겹으로 가뒀다([트러블슈팅 141](../troubleshooting.md)).
