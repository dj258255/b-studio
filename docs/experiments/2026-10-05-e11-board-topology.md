# 실험 E11: 게시판 topology(star 대 mesh)는 성공을 지키면서 통신을 줄이는가

- 날짜: 2026-10-05
- 관련 이슈: [#392](https://github.com/dj258255/b-studio/issues/392) (가설 사전 등록)
- 커밋: 실행 시점 main `65c59a0`
- 원자료 경로: `~/.cache/b-studio/bench/e11/{mesh,star}-r{1,2,3}/results.jsonl`

## 가설

- **H26**: S3 게시판에서 레인 간 직접 읽기를 끊은 star의 성공은 mesh보다 3건 이상 적다.
- **H27**: star의 게시·읽기 바이트 중앙값은 mesh의 50% 이하다.
- **H28**: 성공 1건당 토큰은 두 조건이 ±15% 안이다.

선행 연구 맥락: AgentPrune은 통신 가지치기로 토큰 28~73% 절감을, GPTSwarm 계열 분석은 밀집 topology의 프롬프트 토큰이 2.4~5.3배라고 보고한다(둘 다 벤치마크 정답률 기준). 이 실험은 게이트·인수 검사로 성공을 판정하는 실제 코딩 과제에서 같은 질문을 잰다.

## 이 실험이 정할 것

star가 성공을 유지하면(H26 기각) 레인 간 직접 통신은 이 규모에서 성공의 활성 성분이 아니고, 무너지면 S3를 쓸 때 mesh를 기본으로 유지한다. 어느 쪽이든 기본 권장은 S2(계약 먼저, ADR-059)에서 바뀌지 않는다.

## 조건

| 항목 | 값 |
|---|---|
| 전략 | S3 게시판, `--topology mesh` 대 `--topology star` |
| 과제 | 엮인 과제 3개(orders-list, order-detail, order-summary) × 3회 = 조건당 9회 |
| 모델 | 로컬 Claude Code 구독, sonnet, 고정 계획(presetPlan), 자가 확인 lean(기본) |
| 실행 | 반복(r1~r3)마다 mesh ↔ star 교대, 직렬(`--concurrency` 없음), `--force`(아래 실행 기록) |
| hierarchical 제외 | 과제가 전부 2레인·그룹 없음이라 star와 같아진다 |

## 지표 정의

- 성공: 통합 세션의 인수 검사(`runAcceptance`) 전부 통과. Fisher 정확 검정(양측)으로 비교한다.
- 성공 1건당 토큰: 조건의 입력+출력+캐시읽기+캐시쓰기 합 ÷ 성공 수(실패 실행의 토큰 포함).
- 게시판 지표: 행의 `coordination`(게시 수, 읽기 수, 읽기 바이트).

## 결과

실행 명령(반복·topology마다):

```bash
pnpm bench:coordination --backend claude-code --model sonnet --strategies S3 \
  --topology <mesh|star> --tasks orders-list,order-detail,order-summary --repeats 1 --force \
  --out ~/.cache/b-studio/bench/e11/<topo>-r<n>
```

| 지표 | mesh | star |
|---|---|---|
| 성공 | **7/9** | **5/9** |
| 총 토큰 | 3,267,834 | 3,608,233 (+10.4%) |
| 성공 1건당 토큰 | 466,833 | 721,647 (+55%) |
| 게시 중앙값 / 읽기 중앙값 | 2 / 2 | 2 / 3 |
| 읽기 바이트(9행 정렬) | [0, 0, 0, 0, 0, 439, 451, 561, 1212] | [0, 0, 0, 0, 236, 282, 288, 339, 443] |
| 읽기 바이트 0인 행 | 5/9 | 4/9 |

## 예상과 다른 점

1. **H26 기각.** star가 레인 간 계약을 전혀 못 봐도 성공은 2건 차이(7/9 대 5/9, p = 0.620)로, 9쌍으로는 우연과 구별되지 않는다. E1의 S1(공유 없음) 4/9에서 기대한 붕괴는 없었다. E2에서 실패 서명만 공유한 S5가 8/9였던 것과 같은 방향이다 — star에서도 플랫폼 메모(실패 서명)는 읽힌다.
2. **H27 판정 불가 — 전제가 어긋났다.** mesh의 읽기 바이트 중앙값이 0이다(9행 중 5행이 0). 레인은 시작 직후 게시판을 읽는데, 상대 레인이 계약을 게시하기 **전**이라 빈 결과를 받는다. E2가 한 행에서 추정으로 적었던 읽기 타이밍 문제가 이번에는 다수 재현됐다. 비교할 "mesh의 통신량" 자체가 거의 없어서 star가 그 50% 이하인지는 물을 수 없는 질문이 됐다.
3. **H28 기각(등록한 기준으로).** 성공 1건당 토큰은 star가 +55%로 ±15%를 벗어났다. 다만 총 토큰은 +10.4%로 기준 안이다 — 차이의 원인은 통신 비용이 아니라 성공 분모(7 대 5)다.
4. mesh에서 읽기 바이트가 0인데 성공한 행이 3건 있다. 통신 없이도 두 레인의 구현이 우연히 맞물린 경우로, "mesh라서 성공"이라는 해석을 막는 증거다.

## 결론

- 이 규모(레인 2개, 풀 방식 게시판)에서 topology는 성공률의 활성 성분이 아니었다. 활성 성분은 **읽는 시점**이다: 계약이 게시되기 전에 읽으면 mesh도 star와 다를 게 없다. E2에서 계획 단계에 계약을 먼저 게시하는 S2가 9/9였던 것과 일관된다 — 통신의 가치는 연결이 있는가가 아니라 필요한 내용이 읽기 전에 게시돼 있는가에 있었다.
- AgentPrune류의 "가지치기로 토큰 절감" 주장은 이 규모에서 재현할 공간이 없었다. 쳐낼 통신이 애초에 거의 없다. 선행 연구의 전제(에이전트 수가 많고 밀집 broadcast)와 이 구조(레인 2개, pull 게시판)가 다르다는 것이 측정으로 확인된 셈이다.
- 기본 권장은 그대로다: 엮인 작업은 S2(ADR-059). S3를 쓸 거면 topology 조정보다 읽기 타이밍 보장이 먼저다(후속 이슈 [#393](https://github.com/dj258255/b-studio/issues/393)).

## 실행 기록(사고 포함)

- 1차 배치(11:52~13:58)는 18회 전부 샌드박스 빌드에서 실패했다. colima VM 안 DNS가 일시적으로 끊겨 `eclipse-temurin:25-jdk` 베이스 이미지의 토큰 발급(`auth.docker.io`)이 `no such host`로 실패했다. 레인이 모델을 돌리기 전이라 구독 사용량은 거의 쓰지 않았다. DNS 복구를 확인하고 베이스 이미지 4개를 선적재한 뒤 2차 배치(15:49~17:14, 85분)로 측정했다.
- 메모리 가드가 다른 프로젝트 컨테이너 39개(합계 약 8.6GiB)를 보고 시작을 거부해 `--force`로 진행했다(VM 여유 6.2GiB, 직렬 1개 샌드박스 상한 약 2.8GiB). 다른 컨테이너가 상주한 상태의 측정이라 종단 시간에는 소음이 있을 수 있다. 토큰·성공 지표에는 영향이 없다.

## 범위와 한계

- 레인 2개·과제 3개×3회다. topology 효과의 규모 주장은 못 하고, 에이전트가 많은 밀집 통신 구조로 일반화할 수 없다.
- 성공 1건당 토큰은 분모(성공 수)에 민감하다. 9회 표본에서 2건 차이가 +55%를 만든다.
- 비용은 구독 CLI라 토큰으로만 적었다(단가 환산 생략).
