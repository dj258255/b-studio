# 실험: 검사 동안 파일을 바꿨다 되돌리는 백그라운드 프로세스를 무엇으로 막는가 (#765 2안·3안)

- 날짜: 2026-10-27
- 관련 이슈: [#765](https://github.com/dj258255/b-studio/issues/765), 1안 [#771](https://github.com/dj258255/b-studio/pull/770), ADR-132 덧붙임
- 커밋: main `582e66b`에서 갈라진 작업 트리
- 원자료: [`data/2026-10-27-verify-background/`](data/2026-10-27-verify-background/)(`options.json`, `recreate.json`, `provider.json`과 잰 스크립트)

## 질문

게이트는 검사 시작과 끝에 작업 복사본의 지문을 견준다. 검사 동안 백그라운드 프로세스가 파일을 A→B로 바꿨다가 끝나기 전에 A로 되돌리면, 테스트는 B로 통과하고 앞뒤 지문은 A로 같아 A가 "검증됨"으로 커밋된다. 1안(터미널 에이전트 컨테이너 멈추기)은 들어갔다. 남은 곳은 이번에 다시 띄우지 않은 서비스 컨테이너다. 에이전트가 `run_in_service`로 `nohup … &`를 남기면 그 프로세스는 검사 동안 살아 있다.

이슈의 두 후보를 예제 프로젝트에서 쟀다.

- 2안: 선언한 검사 앞에 프로젝트를 마운트한 서비스를 모두 다시 만든다.
- 3안: 서비스 안에서 `docker exec`로 띄운, PID 1의 자손이 아닌 프로세스를 끝낸다.

## 가설

- 3안은 PID 1의 자손인지로 exec 잔여물을 가를 수 있고, 2안보다 훨씬 싸다.
- 2안은 바뀌지 않은 서비스를 다시 만드느라 검사 한 번에 수십 초를 더한다.

## 조건

- 프로젝트: `examples/orders`(Spring Boot api + Next.js 16.4.3 web + Postgres). 실제 Docker(Colima 기본 VM, CPU 6, 메모리 10GiB). 같은 VM에 다른 프로젝트의 kind 클러스터(약 6GiB)가 떠 있었다.
- 샌드박스는 제품과 같은 `LocalDockerProvider`로 띄웠다. 각 항목 3회.
- 백그라운드 프로세스 흉내: `sh -c 'nohup sh -c "while true; do sleep 1; done" >/dev/null 2>&1 &'`(api), `setsid`로 세션을 새로 만든 같은 루프(web).
- 검사 시간은 예제의 선언 검사 두 개(`web-lint`, `api-unit`)를 서비스 안에서 돌린 시간이다.

## 결과

### 1. exec로 남긴 프로세스는 PID 1의 자손이 된다 (busybox:1.37, 실측)

```
PID   PPID  COMMAND
    1     0 /sbin/docker-init -- sleep 3600
   14     1 sh -c while true; do sleep 1; done     ← exec로 남긴 것
```

셸이 끝나면 고아가 된 프로세스는 PID 1 밑으로 옮겨진다(`--init` 유무와 상관없다). 그래서 이슈에 적은 3안의 기준("PID 1의 자손이 아닌 것")으로는 이 프로세스를 찾을 수 없다. 세션 id는 다르다: exec로 들어온 프로세스는 새 세션을 받고(sid=9, 23), 서비스 본 프로세스의 자식은 PID 1의 세션(sid=1)이다. 프로세스는 남의 세션에 들어갈 수 없다(setsid는 새 세션만 만든다).

### 2. 세션 기준으로 끝내면 Spring Boot 서비스가 죽는다 (orders, 3회 모두)

| 회차 | web에서 찾은 것 | api에서 찾은 것 | 끝낸 뒤 web | 끝낸 뒤 api |
|---|---|---|---|---|
| 1 | 루프 2개 | 루프 2개 + **java 2개(sid=38)** | 200 | **응답 없음(컨테이너 종료)** |
| 2 | 루프 2개 | 루프 2개 + java 2개 | 200 | 응답 없음 |
| 3 | 루프 2개 | 루프 2개 + java 2개 | 200 | 응답 없음 |

api의 PID 1은 Gradle wrapper이고, 실제 서버(bootRun JVM)는 Gradle이 새 세션(sid=38)으로 띄운다. "PID 1과 세션이 다르면 끝낸다"는 서버 자신을 끝낸다. 찾기와 끝내기는 서비스마다 0.1~0.2초였다.

### 3. 검사 시간과 2안의 비용 (orders)

| 회차 | web-lint | api-unit | 다시 만들기 web | 다시 만들기 api | 둘을 함께 |
|---|---|---|---|---|---|
| 1 | 2.9초 | 21.7초 | 6.4초 | 13.5초 | 12.9초 |
| 2 | 4.1초 | 8.4초 | 6.4초 | 12.2초 | 21.8초 |
| 3 | 2.6초 | 7.7초 | 6.4초 | 14.4초 | 13.3초 |

다시 만들기는 게이트의 재시작과 같은 `up --build --force-recreate`와 준비 대기다(`recreate.json`). 다시 만든 뒤 첫 화면(`GET /`)은 33~44ms, 첫 계약 조회는 87~129ms로 데워진 때와 차이가 없었다(`.next`·Gradle 캐시가 볼륨에 남는다). 2회차의 21.8초는 같은 VM의 다른 부하로 보인다. 2안은 api가 바뀌지 않은 게이트마다 12~14초를 더한다. 선언 검사(10~25초)의 절반에서 한 배다.

### 4. 고친 안: 기준선과 견줘 찾고, 찾은 서비스만 다시 만든다 (orders, 3회)

서비스가 준비된 직후 PID 1과 세션이 다른 프로세스 목록(pid와 시작 시각)을 기준선으로 남기고, 게이트가 검사 전에 다시 읽어 기준선에 없던 것이 있으면 그 서비스를 2안처럼 다시 만든다.

| 회차 | 기동 직후 찾은 것 | 루프를 남긴 뒤 찾은 것 | 찾기 시간 | 다시 만든 뒤 찾은 것 | 다시 만든 뒤 api |
|---|---|---|---|---|---|
| 1 | 없음 | web 2개, api 2개(루프만) | 0.28초 | 없음 | 200 |
| 2 | 없음 | web 2개, api 2개 | 1.7초 | 없음 | 200 |
| 3 | 없음 | web 2개, api 2개 | 0.26초 | 없음 | 200 |

Gradle이 띄운 서버는 기준선에 있어 찾지 않았다. setsid로 세션을 새로 만든 루프(web)도 찾았다. 2회차 찾기 1.7초는 같은 기계에서 단위 테스트 전체를 돌리던 때다.

## 예상과 다른 점

- 3안의 기준(PID 1의 자손인가)은 쓸 수 없었다. 고아는 PID 1의 자손이 된다.
- 세션으로 가르는 것도 그대로는 쓸 수 없었다. 서비스가 스스로 다른 세션을 만드는 경우가 예제의 Spring Boot에 바로 있었다.

## 결정

고친 안을 쓴다(ADR-132 덧붙임).

- 끝내지 않고 다시 만든다. 서비스가 다른 세션으로 띄운 서버를 잘못 끝내지 않고, 셸이 없는 이미지에서도 같게 동작한다.
- 확인하지 못한 서비스(셸이 없음, 읽기 실패)와 찾기 자체가 실패한 경우는 다시 만든다. 모르면 막는 쪽이다.
- 기준선은 제공자 기억에만 있다. 스튜디오를 다시 띄우면 비어 있어, 첫 게이트가 다른 세션 프로세스를 가진 서비스(Gradle)를 한 번 다시 만든다. 그 뒤로는 기준선이 생긴다.
- 평소 비용은 찾기 0.3초 안팎이다. 2안의 12~14초는 백그라운드 프로세스가 실제로 있을 때만 든다.

## 배제한 원인과 남은 가능성

- 다시 만든 뒤 첫 요청이 느려져 화면 확인이 길어질 가능성: 첫 화면과 계약 조회가 데워진 때와 같아 배제했다.
- 막지 못하는 것: 이 컴퓨터 방식 터미널의 호스트 셸(컨테이너 밖)과, 개발 서버가 다시 읽어 들인 코드가 서버 프로세스 안에서 하는 일(새 프로세스가 생기지 않는다). 뒤의 것은 에이전트가 서비스 코드를 바꿔 개발 서버가 읽게 한 뒤 되돌려야 한다. 서비스 파일이 바뀐 채로 게이트에 오면 그 서비스는 이미 다시 만들어진다.
- 서비스가 준비된 뒤에 스스로 다른 세션 프로세스를 새로 띄우는 경우: 그 서비스를 필요 없이 다시 만든다(느려질 뿐 잘못 통과하지 않는다). 예제에서는 보지 못했다.

## 결론과 적용 범위

예제 프로젝트(Spring Boot + Next.js)와 Colima에서만 확인했다. exec 잔여물은 세션 id로 찾을 수 있지만, 그것만으로 끝내면 Gradle 서비스가 죽는다. 준비 직후 기준선과 견줘 찾고 그 서비스를 다시 만들면, 평소 비용 0.3초 안팎으로 run_in_service의 백그라운드 프로세스를 검사에서 떼어 낼 수 있다.
