# 검증 기록과 알려진 한계

이 문서는 “구현되어 있음”과 “실제 환경에서 확인함”을 구분합니다. 재현 과정과 원인 분석이 필요한 항목은 [트러블슈팅](troubleshooting.md), 설계 근거는 [ADR](decisions.md)에 있습니다.

## 자동 검사

```bash
pnpm test
pnpm typecheck
pnpm --filter @b-studio/studio lint
pnpm --filter @b-studio/studio build
```

CI는 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)을 기준으로 실행합니다.

## 실제 환경에서 확인한 범위

| 영역 | 확인 방법 | 결과 |
|---|---|---|
| Docker 샌드박스 | 주문 예제의 web·api·db 기동과 종료 | 준비 판정, URL 출력, 정리 확인 |
| 에이전트 검증 게이트 | 의도적으로 컴파일 오류를 만든 scripted E2E | 실패 반환 뒤 수정·통과 확인 |
| 웹 스튜디오 | 데모/로컬 모드와 실제 브라우저 | 대화, 미리보기, API, 로그, 코드, 기록 탭 확인 |
| 체크포인트 | Git 변경과 PostgreSQL 덤프 비교 | 저장, 취소, 실패, 되돌리기 확인 |

| 자원·네트워크 | 실제 Docker 컨테이너 | 메모리/CPU 상한, egress 차단과 허용 확인 |
| 시크릿·정책 프록시 | 로그·명령·HTTP·Git 경로 | 주입, 마스킹, 커밋 거부, 호출 정책 확인 |

| Kubernetes | kind + agent-sandbox | 네임스페이스, Sandbox, gVisor, 준비 판정 확인 |
| 멀티 모델 라우터 | 로컬 호환 공급자 + Docker | 공통 도구 계약, 선택 설명, 관측 저장 확인 |
| Agent Fleet | 2개 독립 후보 E2E | 분리된 브랜치·샌드박스, 결과 비교와 선택 확인 |
| 워크플로 강제 | `pnpm e2e:agent` 3개 시나리오, 실제 Docker | 통과 시나리오 2개에서 web 컨테이너 `pnpm lint`와 `/` 화면 확인을 게이트가 실행하고 5개 검증 단계 통과 기록. 계약이 깨진 시나리오는 test 단계를 실행하지 않고 failed |
| 헤드리스 브라우저 화면 확인 | Chromium 실제 실행 단위 테스트 + `pnpm e2e:agent`(web `/`를 390x844로 렌더링) | 클라이언트가 만든 문구 읽기, 스크립트 예외·`console.error`·404 리소스 수집, 모바일 가로 넘침 510px 측정. 실제 Next 개발 서버에서 3개 시나리오 통과 |
| 배포 조건 전 과정 | `pnpm e2e:deploy-gate`, 실제 Docker·배포 API 라우트 | 검증 기록 없는 체크포인트 409 거부, 스크립트 예외 화면을 실제 브라우저 확인이 실패시킨 뒤 수정 통과, 트레일러 기록, 202 수락과 운영 릴리스 완료·운영 주소 응답까지 확인 |
| 예제 api 테스트 | `pnpm e2e:agent`(개발 서버가 도는 api 컨테이너) + 같은 명령을 컨테이너에서 직접 실행 | `bootRun` 중에도 Gradle 잠금 충돌 없이 `api-unit` 통과. 단언을 일부러 틀리게 바꾸면 `1 test completed, 1 failed`로 실제 실패하는 것까지 확인 |
| 작업 분해 | `pnpm e2e:task-plan`, 실제 Docker 세션 3개 | 레인 2개 동시 실행, 같은 레인의 a2가 a1 파일을 읽음, 다른 레인의 범위 밖 쓰기 차단, 통합 세션에서 파일 3개 재적용 뒤 5개 검증 단계 재통과 (98.1초) |
| 샌드박스 이미지 정리 | 실제 Docker에서 세션 종료 뒤 이미지 확인 | 수정 전 세션마다 `studio-<프로젝트>-<id>-*` 이미지가 남아 디스크를 채웠고, 수정 뒤 배포 조건 E2E 종료 시 남은 샌드박스 이미지 0개 |
| Pi 정책 확장 | 단위 테스트 + Pi 0.73.1의 `loadExtensions`·`ExtensionRunner`로 실제 로드 | 로드 오류 없음. 보호 경로·프로젝트 밖 쓰기, `&&` 뒤 `git push`, `.env` 읽기 차단과 일반 읽기·쓰기 허용, 시스템 프롬프트 안내까지 10개 확인. 모델을 붙인 전체 세션은 아님 |
| 운영 배포 | 실제 Docker와 고정 주소 | 새 릴리스 전환, 상태, 롤백, 제거 확인 |
| 인증과 한도 | token/proxy 모드, 실제 모델 | 세션 권한, 사용자별·세션별 토큰 차단 확인 |
| 동시 요청 확인(`concurrency_check`) | 가짜 요청 함수 단위 테스트 | 10개를 실제로 동시에 보냄(최대 동시 수 확인), 성공 건수·상태 분포·`then` 값 판정, 출처 밖 경로 거부, 타임아웃 실패. **실제 Docker 샌드박스에서는 아직 돌리지 않음** |
| 화면 로드 시간 예산(`maxLoadMs`) | 가짜 브라우저 러너 단위 테스트 + 실제 Chromium(`measureLoad`) | 워밍업 뒤 로드 측정, 예산 초과 실패 문구(`로드 2,340ms (예산 2,000ms)`), 예산을 적은 확인만 재어 `metrics.loadMs`에 기록(예산이 없으면 워밍업·측정 없음), 재지 못하면 실패 |
| Command Code 백엔드 | 실제 계정(계정 기본 모델), `bench:coordination --backend commandcode --tasks independent --strategies S0` | 1차: 같은 레인 두 번째 작업이 `No session … found to resume`으로 실패(실행마다 임시 HOME·작업 폴더를 지워 세션을 잃음). 세션별 고정 상태 폴더로 고친 2차: api 165초·web 44초(앞 세션 이어받음), 인수 검사 2/2, 남은 컨테이너 0 ([#61](https://github.com/dj258255/b-studio/pull/61), [트러블슈팅 47](troubleshooting.md)) |
| PR 미리보기·계획 이슈화 | 로컬 Gitea 1.27.3(Docker)에 `repository.ts`의 실제 함수를 직접 호출 | 이슈 3개 생성, `Closes #4`·`#5`가 든 PR 생성, 같은 PR 재요청 시 409 → 기존 PR 재사용, PR 병합 뒤 이슈 #4·#5 `closed`. Gitea는 하위 이슈 API가 없어 `{supported:false}` → 체크리스트로 대체. 스튜디오 화면 흐름은 [#128](https://github.com/dj258255/b-studio/issues/128)로 남김 |
| 토큰 탭 모델별 비용 | 데모 모드 스튜디오 + 실제 브라우저, 로컬 확인용으로 가공한 세션 기록 복사본 | 모델별 표(haiku $0.0428, sonnet $0.0757), 합계 $0.1184·"모델별 단가", 승격 줄 표시. 토큰 0인 `scripted` 행이 "단가 없음"으로 남는 문제를 찾아 고침([#141](https://github.com/dj258255/b-studio/pull/141)). 390px 확인은 창 크기 조절이 적용되지 않아 못 함 |
| 기준선·도구 결과 예산·승격 | 실험 E3, 실제 Docker·로컬 Claude Code 구독, 27회 | 그냥 Claude Code(P0) 9/9·성공 1건당 토큰 217,711, b-studio S0 9/9·437,427, Haiku 시작 6/9·승격 0회. S0 캐시 읽기는 E1보다 −34% ([보고서](experiments/2026-09-29-e3-baseline-budget-escalation.md)) |

## 동시성·부하 확인

`pnpm test`에 "읽고 → 고치고 → 다시 쓰는" 경로의 lost update 검사가 들어 있습니다. 각 경로의 원본(메모리인지 파일인지)과 동시 갱신에서 무엇이 남아야 하는지를 고정합니다.

| 경로 | 원본 | 동시 갱신 검사 | 결과 |
|---|---|---|---|
| 세션 상태 저장 (`session-store.writeSession`) | 메모리 스냅샷을 파일로 write-through | 같은 파일에 두 저장을 동시에 | 임시 파일 이름을 호출마다 달리해 저장이 실패·유실되지 않고 온전한 스냅샷 하나가 남음 ([트러블슈팅 44](troubleshooting.md#44-같은-세션-파일에-두-저장이-겹치면-임시-파일-이름이-부딪혀-저장이-통째로-사라짐)) |
| 작업 분해 계획 저장 (`task-plans.persist`) | 메모리 계획 객체를 통째로 write-through(동기) | 레인들이 동시에 끝나도 | 모든 레인 결과가 계획 파일에 남음 |
| Agent Fleet 저장 (`fleets.persist`) | 메모리 객체를 통째로 write-through(동기) | 멤버들이 동시에 끝나도 | 모든 멤버 결과가 Fleet 파일에 남음 |
| 사람별 토큰 합계 (`usage-state.addUserUsage`) | 파일이 원본, 쓰기를 직렬 큐로 | 같은 사람 20회 동시 가산, 서로 다른 사람 동시 가산 | 하나도 잃지 않고 두 번 다 더해짐 |
| 로그인 무효화 (`auth-state.update`) | 파일이 원본, 쓰기를 직렬 큐로 | 세션 무효화와 사용자 무효화를 동시에 | 둘 다 남음 |

Node는 단일 스레드라 이 검사들은 "읽고 → 고치고 → 다시 쓰는" 사이에 `await`가 끼는 인터리빙만 잡습니다. 여러 프로세스가 같은 파일을 동시에 고치는 경우는 재지 않습니다.

### 부하 스모크 (Docker·모델 없이)

```bash
pnpm bench:studio-load [--sessions 5] [--rate 50] [--duration 5] [--out out.json]
```

기준선(2026-09-29, MacBook Pro 32GiB, 가짜 샌드박스 제공자, 모델 호출 없음):

| 조건 | 세션 생성 p50 / p95 | SSE 첫 이벤트 p95 | 이벤트 전달 p95 | 이벤트 보냄 / 떨어짐 | RSS 시작 → 최고 |
|---|---|---|---|---|---|
| 세션 5 · 세션당 초당 50 · 5초 | 211.4 / 236.9ms | 2.0ms | 0.0ms | 1,261 / 0 | 184.4 → 196.7MiB |
| 세션 20 · 세션당 초당 100 · 10초 | 217.8 / 235.0ms | 1.0ms | 0.0ms | 21,183 / 0 | 183.6 → 205.2MiB |

스튜디오 서버의 세션 관리·이벤트 전달 계층은 이 범위에서 병목이 아닙니다. 실제 한계는 샌드박스(Docker VM 메모리·디스크)와 외부 저장소 요청 한도 쪽입니다([트러블슈팅](troubleshooting.md), [#116](https://github.com/dj258255/b-studio/issues/116)). 이후 PR에서 같은 조건의 수치가 크게 벌어지면(예: RSS 2배, 떨어진 이벤트 발생) 회귀로 봅니다.

가짜 샌드박스 제공자로 세션 N개를 만들고, 실제 SSE 라우트(`app/api/sessions/[id]/events/route.ts`)로 연결을 열어 둔 채 가짜 이벤트를 흘려보내 세션 생성 지연·SSE 첫 이벤트 지연·이벤트 전달 지연(p50·p95)·RSS·떨어진 이벤트 수를 표와 JSON으로 남깁니다. 재는 것과 한계는 [`apps/studio/bench/load/README.md`](../apps/studio/bench/load/README.md)에 있습니다. 기준선 수치는 메인 세션이 실행해 이 문서에 남깁니다.

### 두 세션 동시 기동 (Docker 필요)

```bash
pnpm e2e:two-sessions
```

같은 프로젝트(`examples/orders`)로 세션 두 개를 동시에 만들고 둘 다 ready가 되는지 확인합니다(트러블슈팅 36번 회귀). 실제 Docker가 필요하므로 CI 자동 검사에는 넣지 않고 필요할 때 손으로 돌립니다.

## 재현용 명령

```bash
pnpm test
pnpm typecheck
pnpm e2e:agent
pnpm e2e:fleet
pnpm e2e:deploy-gate
pnpm e2e:task-plan
pnpm e2e:two-sessions
pnpm bench:boot examples/orders 3
pnpm bench:studio-load
```

E2E는 이미지 다운로드, 컨테이너 생성, 포트 사용, 모델 인증 또는 로컬 브라우저 상태에 영향을 받습니다. 공유 개발 환경에서는 실행 전에 남은 샌드박스와 사용 가능한 자원을 확인하세요.

## 알려진 한계

- API 키를 사용하는 실제 외부 공급자 경로는 자격 증명이 있는 환경에서 별도 확인이 필요합니다.
- GitHub와 GitLab PR API는 계약 테스트를 갖지만, 실제 원격에서의 전체 흐름은 Gitea 실검증과 구분해야 합니다.
- Kubernetes 검증은 로컬 kind 기준입니다. 관리형 클러스터 차이는 별도 검증이 필요합니다.
- Docker 소켓을 마운트하는 운영 방식은 호스트 수준 권한을 가질 수 있습니다.
- 로컬 Claude Code 로그인 모드는 개인 PC 전용입니다.
- 배포 롤백은 데이터베이스 마이그레이션을 되돌리지 않습니다.
- `browser_check`의 `browser` 모드는 렌더링 문구·스크립트 예외·콘솔 오류·실패한 요청·가로 넘침만 봅니다. `steps`로 클릭·입력·키 입력·선택자 대기를 선언해 상호작용 뒤의 화면을 확인할 수 있지만, 정해 둔 네 동작만 실행하고 임의 스크립트는 돌리지 않습니다. 시각적 레이아웃을 픽셀 단위로 비교하지는 않습니다. 브라우저가 없는 환경에서는 실패로 끝납니다.
- `concurrency_check`는 부하 테스트가 아니라 **동시성 정합성**만 봅니다. 같은 요청을 동시에 보내 정확히 몇 건 성공했는지, 이어서 읽은 상태가 기대와 맞는지 확인할 뿐, 처리량·지연·지속 부하는 재지 않습니다. DB 트랜잭션 격리 수준과 타이밍에 따라 결과가 흔들릴 수 있어 임계값은 넉넉히 잡아야 합니다. **한 번의 실패를 재시도로 덮지 않습니다**(재시도하면 경합이 숨습니다). 실제 Docker 샌드박스에서 아직 실행해 보지 않았습니다.
- `pageChecks[].maxLoadMs`는 개발 서버 콜드 스타트(첫 컴파일)를 피하려고 워밍업 이동을 한 번 한 뒤 재지만, 호스트나 Colima VM이 느릴 때는 정상 코드도 예산을 넘을 수 있습니다. CI·공유 서버처럼 자원이 일정하지 않은 환경에서는 예산을 넉넉히 두거나 로컬에서만 켜세요. 로드 시간은 예산을 적은 확인만 재어 `metrics.loadMs`에 남깁니다(재려면 페이지를 한 번 더 열어야 하기 때문입니다).
- 예제의 `test` 단계는 web `pnpm lint`와 api `./gradlew test`입니다. 빌드 출력 폴더(`/app/build`)는 개발 서버와 계속 공유하므로, 자동 재시작 도구(devtools 등)를 넣으면 테스트가 돌 때마다 개발 서버가 다시 뜰 수 있습니다. api 컨테이너에서는 `bootRun`이 계속 돌고 있어 프로젝트 캐시(`/app/.gradle`)를 같이 쓰면 Gradle 잠금이 부딪히므로, 테스트는 `--project-cache-dir`로 개발 서버와 분리한 캐시에서 돌립니다. 같은 이유로 개발 서버 옆에서 테스트를 돌리면 메모리 최대치가 약 1.7GiB에 닿아 예제 api 한도를 1536m에서 2048m로 올렸습니다([트러블슈팅 41번](troubleshooting.md#41-개발-서버-옆에서-api-테스트를-돌리면-컨테이너-한도-1536mib를-넘어-oom으로-실패함), [#70](https://github.com/dj258255/b-studio/issues/70)).
- Pi 확장은 호스트에서 동작해 샌드박스·게이트·체크포인트를 거치지 않으며, bash 명령 판정은 우회할 수 있어 보안 경계가 아닙니다. 다만 Pi나 편집기로 바꾼 현재 작업 트리의 변경은 `studio verify <프로젝트 경로>`로 에이전트와 같은 게이트에 넣어 확인할 수 있으며, 이 명령은 판정만 하고 체크포인트를 만들지 않습니다. 계약 비교 기준이 실행 시점의 현재 코드라서, 편집기에서 이미 깬 계약은 이 명령으로 잡지 못합니다.
- 작업 분해 E2E의 계획은 로컬 호환 모델이 정해 둔 JSON입니다. 실제 모델이 적절한 쓰기 범위로 나누는지는 모델 품질에 달려 있고, 틀린 계획은 실행 전에 거부될 뿐 좋은 계획으로 고쳐지지 않습니다. 다만 계획은 레인을 돌리기 전에 사람이 승인해야 하므로, 잘못 나뉜 쓰기 범위는 실행이 시작되기 전에 사람이 막을 수 있습니다.
- 작업 분해 통합은 파일 생성·수정과 삭제를 함께 다시 적용합니다. 레인이 지운 파일은 통합 세션에서도 `delete_file`로 지우고, 파일 이름을 바꾼 변경은 삭제와 생성으로 처리됩니다. 통합 세션의 원본에도 없는 파일은 `delete_file`이 실패해 통합 전체가 멈추므로 지울 목록에서 뺍니다. 서버가 재시작되면 레인이 모두 끝나 통합만 남은 계획은 `interrupted`로 남아 `POST /api/task-plans/[id]/resume`로 통합만 다시 시도할 수 있고(레인은 다시 돌리지 않습니다), 레인이 끝나지 않은 계획은 샌드박스가 사라져 실패로 남습니다.
- `Workflow-Passed` 트레일러는 체크포인트 작성자와 커밋 작성자 이메일이 같은, 스튜디오가 만든 커밋에서만 읽습니다(앞뒤 공백 제거, 대소문자 무시). 원격 동기화로 가져온 커밋처럼 다른 작성자가 적은 트레일러는 검증 통과 기록으로 읽지 않습니다.
- 별도 라이선스가 아직 선언되어 있지 않아 외부 사용·배포 권한을 자동으로 부여하지 않습니다.
- 부하 스모크(`pnpm bench:studio-load`)는 가짜 샌드박스 제공자로 돌아 컨테이너 기동·이미지 빌드·의존성 설치 시간을 재지 않습니다. 여기서 재는 것은 스튜디오 서버 안쪽(세션 관리·이벤트 버스·SSE 직렬화)의 지연이고, 실제 SSE 라우트를 프로세스 안에서 직접 불러 네트워크·프록시 홉은 빠집니다.
- 동시 쓰기 검사는 Node가 단일 스레드라 "읽고 → 고치고 → 다시 쓰는" 사이에 `await`가 끼는 인터리빙만 잡습니다. 여러 프로세스가 같은 파일을 동시에 고치는 경우(예: 두 스튜디오 프로세스가 같은 세션 폴더를 여는 경우)는 `owner.pid`로 막을 뿐 자동 검사로는 재지 않습니다.

새 검증을 추가할 때는 사용한 환경, 입력, 기대 결과, 실제 결과를 함께 기록하세요.
